💡 kubectl 診斷 Pod 啟動失敗的完整流程

Pod 卡在 Pending / CrashLoopBackOff / ImagePullBackOff 時，按順序執行四個 kubectl 指令就能找到根因。從 Status/Events 欄位判斷是 ImagePull 問題、CrashLoop（應用錯誤）、OOMKilled（記憶體不足）還是 Pending（資源不夠）。

# 1. 看整體狀態
kubectl get pods -A

# 2. 看詳細事件（最關鍵）
kubectl describe pod <pod> -n <ns>

# 3. 看應用日誌（CrashLoop 時加 -p 看 crash 前 log）
kubectl logs <pod> -n <ns> --previous

# 4. 看集群事件（有時 describe 不夠）
kubectl get events -n <ns> --sort-by='.lastTimestamp'

💭 原理：describe 的 Events 區塊記錄了 scheduler、kubelet 的決策日誌；ImagePullBackOff 是 registry/name/tag 問題，CrashLoopBackOff 是應用啟動後立即退出，OOMKilled 是 memory limit 不足，Pending 通常是 CPU/Memory 資源不夠分配。

💡 GitHub PR 流程：gh CLI

用 GitHub CLI（gh）可以在 terminal 直接完成 PR 的建立、review、合併，不用開瀏覽器。標準流程：開 feature branch → commit → push → gh pr create → review → gh pr merge。

# 開 branch 並推送
git checkout -b feature/xxx
git add . && git commit -m "feat: xxx"
git push -u origin feature/xxx

# 建立 PR（--fill 自動用 commit msg 當 title + body）
gh pr create --title "標題" --body "說明" --fill

# 檢視 PR 狀態
gh pr status
gh pr view --web

# 合併（三種模式：merge / squash / rebase）
gh pr merge --squash --delete-branch

# 切回 main 並更新
git checkout main && git pull

💭 原理：gh pr create 會自動偵測當前 branch 和 upstream，算出 diff 範圍；--squash 將整個 branch 壓成一個 commit 再合併，保持 main 歷史乾淨；--delete-branch 自動清理遠端 branch。

💡 Cloudflare DNS 管理：Proxy vs DNS only

Cloudflare DNS 每個 record 可以選擇開啟 Proxy（橙色雲朵）或 DNS Only（灰色雲朵）。Proxy mode 會隱藏 origin IP、提供免費 TLS/SSL、DDoS 防護、CDN 加速；DNS only 直接解析到 origin IP，適合 API server 或不要快取的服務。

# 用 Cloudflare API 管理 DNS record（自動化）
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "A",
    "name": "example.com",
    "content": "1.2.3.4",
    "proxied": true,
    "ttl": 120
  }'

# 查看現有 records
curl -s "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $CF_API_TOKEN" | jq '.result[] | {name, type, content, proxied}'

💭 原理：開啟 Proxy 時 Cloudflare 會終止 TLS、回源到 origin（用 80 或 443），並快取靜態資源；DNS only 時 DNS 直接回 origin IP，流量不經過 Cloudflare 邊緣。WebSocket 和 SSH 建議用 DNS only 避免 Proxy 相容性問題。

💡 Docker 多階段建置縮小 Image

多階段建置（multi-stage build）讓你在同一個 Dockerfile 用多個 FROM 指令，前面的 stage 裝編譯工具和依賴，最後一個 stage 只複製必要 artifacts。最終 image 不含編譯器、原始碼、中間檔案，體積可縮小 10 倍以上。

# Example: Go 應用的多階段 Dockerfile
# Stage 1: 編譯
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server

# Stage 2: 最小 runtime
FROM alpine:3.19
RUN apk --no-cache add ca-certificates
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]

💭 原理：每個 FROM 開始一個新 stage，—from=builder 只從前一 stage 拷貝指定檔案，builder stage 的 layer 都被丟棄。Go 靜態編譯（CGO_ENABLED=0）可搭配 scratch image 做到最小化。查看 image 層：docker history img:tag。

💡 Helm values 分層覆蓋原則

Helm 的 values 有三層覆蓋機制：預設值（chart 內 values.yaml）→ 環境值（如 values/production.yaml）→ CLI 參數（—set）。後面的層級會合併（merge）覆蓋前面的同名 key，不是全部取代。適合 dev/staging/production 不同環境用不同 values 檔案。

# 目錄結構
chart/
├── values.yaml            # 預設值（最低優先級）
├── values/
│   ├── development.yaml   # 開發環境覆蓋
│   └── production.yaml    # 生產環境覆蓋

# 部署指令
helm upgrade --install myapp ./chart \
  -f values/development.yaml \
  --set image.tag=v1.2.3 \
  -n myapp

# 查看最終渲染結果（debug 用）
helm template myapp ./chart \
  -f values/production.yaml \
  --set image.tag=v1.2.3 | less

# 查看目前 release 的 values
helm get values myapp -n myapp

💭 原理：Helm 用 Go template 的 merge 邏輯，深層合併 map，但 list 會整個取代（不會 element-wise merge）。—set 是最終覆蓋層，但容易打錯 key name（Helm 不會檢查），建議 production 用完整的 values 檔案而非 —set。

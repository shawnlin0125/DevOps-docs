💡 kubectl 診斷 Pod 啟動失敗的完整流程

用 kubectl 四步驟排查 Pod 啟動問題：看狀態 → 看 Events → 看容器輸出 → 看集群事件。從 Status/Events 欄位能快速判斷問題類型。

# 1. 查看 Pod 狀態（關注 STATUS 和 READY 欄位）
kubectl get pods -n <namespace>

# 2. 查看 Pod 詳細事件和 Conditions
kubectl describe pod <pod-name> -n <namespace>

# 3. 查看容器 stdout/stderr
kubectl logs <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous  # 前一次重啟的 log

# 4. 查看集群層級事件（過濾特定 namespace）
kubectl get events -n <namespace> --sort-by='.lastTimestamp'

💭 原理：kubectl describe 的 Events 和 Conditions 區段包含 error pulling image、OOMKilled、back-off restarting 等核心資訊；Events 是集群層級記錄，describe 是 Pod 層級。

💡 Docker 多階段建置縮小 Image

Dockerfile 中用多個 FROM 指令區分 build stage（裝所有 deps 做編譯）和 runtime stage（只複製 artifacts）。Go 可以 FROM scratch（static binary），Node.js 用 standalone output。

# Dockerfile 範例：Go 專案多階段建置
# Stage 1: Build
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server .

# Stage 2: Runtime
FROM scratch
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]

# 查看 image 大小
docker images | grep <name>

💭 原理：每個 FROM 開始一個新 stage，只有 COPY --from=builder 的檔案會進入最終 image。建置工具（gcc、go、npm）留在 builder stage，不佔 runtime image 空間。

💡 查 OOM 紀錄：dmesg OOM Killer 診斷

OOM Killer 紀錄存在核心環緩衝區。K8s 中 Pod 被 OOMKilled 時，kubectl describe pod 的 Last State 會顯示 Reason: OOMKilled。若 Node 所有 Pod 的 memory limits 總和超過實體 RAM，OOM 會連鎖殺 Pod。

# 查 OOM Killer 紀錄（核心訊息）
sudo dmesg -T | grep -i oom

# OOMKilled 時的 kubectl 診斷
kubectl describe pod <pod-name> -n <namespace>
# 在 Containers[].LastState 區查看
#   Last State: Terminated
#     Reason: OOMKilled
#     Exit Code: 137

# 查看 node 記憶體壓力
kubectl describe node | grep -A 8 Allocated
free -h                               # 系統層級記憶體
cat /proc/meminfo | grep -i oom       # OOM 相關核心參數

💭 原理：OOM Killer 由核心在記憶體不足時觸發，選 oom_score 最高的 process 殺（rss + swap + 父程序權重）。Process exit code 137 = SIGKILL(9)，而 139 = SIGSEGV(11)，兩者不同。

💡 GitHub PR 流程：gh CLI

完整 PR 流程從開 branch 到 merge 全部可用 gh CLI 完成，不需開瀏覽器。已 clone 的 repo 直接操作，gh 自動對應 remote 和目前 branch。

# 完整 PR 流程
git checkout main && git pull           # 確保 main 最新
git checkout -b feature/xxx            # 開功能分支
# ... 修改程式碼 ...
git add . && git commit -m "feat: xxx"
git push -u origin feature/xxx         # 第一次 push 需設 upstream
gh pr create --title "feat: xxx" --body "Summary of changes"
# 等 CI pass 和 review
gh pr merge --squash                   # squash merge（或 --rebase）
git checkout main && git pull          # 回 main 拉最新

# 其他常用 gh 指令
gh pr view -w                          # 瀏覽器打開 PR 頁面
gh pr checkout 42                      # 切到 PR #42 的 branch
gh pr list --state open                # 列出開啟的 PR

💭 原理：gh 使用 GitHub API 操作 PR，不需手動設定 remote。--squash 把 feature branch 所有 commits 壓成一個，維持 main 線性歷史。gh pr create 會自動偵測當前 branch 名稱和 commit 訊息。

💡 Helm values 分層覆蓋原則

Helm values 有三層覆蓋：Chart 內 values.yaml（預設值）← -f 載入環境檔案 ← --set CLI 覆蓋。後面的層級會 merge 覆蓋前面的同名 key。用 helm get values 查看目前生效值。

# 分層覆蓋示範
# 1. values.yaml（Chart 內建預設值）
# replicaCount: 1
# image:
#   tag: latest

# 2. values/production.yaml（環境覆蓋）
# replicaCount: 3
# image:
#   tag: v1.2.3

# 3. CLI 部署時套用
helm upgrade --install my-app ./chart \
  -f values/production.yaml \
  --set image.tag=v1.2.4 \
  -n production

# 查看最終生效值
helm get values my-app -n production
helm get values my-app -n production --all  # 顯示所有層級的來源

# 預覽 template 渲染結果
helm template my-app ./chart \
  -f values/production.yaml \
  --debug

💭 原理：Helm 用後進先覆蓋（last-write-wins）策略。--set 優先級最高但容易因 typo 出錯（無法檢查 key 是否存在）。建議 production 使用 -f 載入檔案 + CI 自動化，--set 只用於臨時測試。

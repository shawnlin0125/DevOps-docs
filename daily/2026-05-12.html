📂 Staging/Production 環境分離

💡 Helm 多環境部署：values 分層覆蓋

values.yaml 放預設值，values/staging.yaml 和 values/production.yaml 覆蓋環境差異（DB size、replicas、domain）

helm upgrade --install korean-learning ./helm/korean-learning -f values/production.yaml -n korean-learning
helm upgrade --install korean-staging ./helm/korean-learning -f values/staging.yaml -n korean-staging --create-namespace

💭 Helm 的 values 是 merge 而非 replace：values.yaml → values/staging.yaml → --set，後面的 key 覆蓋前面的。不用維護兩份 Helm chart

💡 ResourceQuota：CPU 96% 危機與 staging 降配策略

單節點 k3s CPU requests 達 1450m/1500m（96%），staging 部署失敗。解決：staging 服務只用 10m CPU request

kubectl describe quota -n korean-staging
kubectl get events -n korean-staging | grep Insufficient
# staging values: cpu request 10m, limit 250-500m
# production values: cpu request 100-250m

💭 requests 決定 scheduling（能不能放進 node），不是實際用量。staging 不需要高 requests，設 10m 即可；limits 保留 burst 能力

💡 nodePort 條件化：ClusterIP service 不能指定 nodePort

Helm template 中 nodePort 欄位必須用 {{ if eq .Values.serviceType "NodePort" }} 包住，不然 ClusterIP 模式會報錯

# frontend-service.yaml template fix
ports:
  - port: 3000
    targetPort: 3000
    {{- if eq .Values.frontend.serviceType "NodePort" }}
    nodePort: {{ .Values.frontend.nodePort }}
    {{- end }}

💭 K8s API 拒絕 ClusterIP service 帶 nodePort 欄位；Helm 渲染時會把未定義的 nodePort 設為 null，造成 YAML parsing 錯誤

💡 Staging `imagePullPolicy: Never` 的風險

Helm --set 覆蓋 image 路徑為 Docker Hub 時，k3s containerd 找不到本地 image → ErrImageNeverPull

kubectl get pods -n korean-staging | grep ErrImageNeverPull
kubectl describe pod <pod> -n korean-staging | grep -A5 Events
# Fix: kubectl set image 改回本地 image，再 helm upgrade 重設

💭 imagePullPolicy: Never + 非本地 image = 死局。建議 staging 用 IfNotPresent（有本地用本地，沒有就 pull），production 可以用 IfNotPresent 或 Always

💡 PostgreSQL PVC 大小規劃：prod 10Gi vs staging 5Gi

Production 和 staging 的 PostgreSQL PVC 分開設定，避免 staging 佔用過多資源

# values/production.yaml
postgres:
  storage: 10Gi
# values/staging.yaml
postgres:
  storage: 5Gi

💭 staging 資料不重要可以隨時清掉，PVC 給 5Gi 就夠；production 需要更多空間且要備份（cron job pg_dump）

📂 伺服器資源評估

💡 K8s 資源評估：kubectl top + describe node

用 kubectl top 看實際用量、kubectl describe node 看 Allocated resources（request/limit 分配比例）

kubectl top nodes
kubectl top pods -A
kubectl describe node | grep -A 8 "Allocated resources"
free -h
df -h /
uptime

💭 kubectl top 是 metrics-server 的即時數據（實際用量）；describe node 的 Allocated 是 scheduler 視角（request/limit 佔比）。兩者都要看

Kuberneteskubectl資源評估monitoring

💡 CPU overcommit 不危險，RAM overcommit 會死人

CPU overcommit（limits 總和 > 實體核數）只是 throttle；RAM overcommit 會觸發 OOM Killer 無差別殺 Pod

sudo dmesg -T | grep -i oom
kubectl get events -A | grep OOM

💭 CPU 是可壓縮資源（throttle），RAM 是不可壓縮資源（OOM Kill）。K8s OOM Killer 看的是 limits 不是 requests，limits 總和超過實體 RAM 時風險極高

💡 kp1 · kubectl 診斷 Pod 啟動失敗的四步驟流程 kubectl,debug,pod,logs,events

當 Pod 無法啟動時，依序執行以下四步驟診斷：kubectl get pods 查看整體狀態（PHASE 欄位：Pending/Running/CrashLoopBackOff/ImagePullBackOff）；kubectl describe pod <name> 看完整 Events 與 Conditions（資源不足→Pending，Image 拉不到→ImagePullBackOff）；kubectl logs <name> 看容器輸出（應用層錯誤）；kubectl get events --sort-by='.lastTimestamp' 看集群層級事件。快速判別四種常見狀態：ImagePullBackOff→image 不存在或 tag 打錯；CrashLoopBackOff→容器啟動後立即崩潰（看 logs）；OOMKilled→記憶體超限；Pending→資源不足或 PVC 綁定失敗。

# Step 1: 看所有 Pod 狀態
kubectl get pods -n <namespace>

# Step 2: 看詳細 Event
kubectl describe pod <pod-name> -n <namespace>

# Step 3: 看容器 log
kubectl logs <pod-name> -n <namespace>

# Step 4: 看集群事件（時間排序）
kubectl get events --sort-by='.lastTimestamp' -n <namespace>

💭 原理：這四步驟從上層（Pod Status）到中層（Events/Conditions）到底層（Logs），涵蓋 K8s scheduler、kubelet、container runtime 三層的錯誤資訊，避免跳步驟漏掉線索。

💡 kp2 · k3s containerd 鏡像管理完整流程：離線部署 k3s,containerd,Docker,imagePullPolicy,離線部署

k3s 預設使用 containerd 而非 Docker，因此不能用一般的 docker push/pull 部署鏡像。離線部署完整流程：用 Docker build 好鏡像 → docker save img:tag -o img.tar 匯出成 tar 檔 → 傳到 k3s 節點 → sudo k3s ctr images import img.tar 匯入 containerd → kubectl apply -f deploy.yaml 部署。注意 imagePullPolicy: Never 或 IfNotPresent，避免 k3s 嘗試從外部 registry 拉取。確認 containerd 中已有鏡像用 sudo k3s ctr images list | grep <name>。

# 在一台有 Docker 的機器上
docker build -t myapp:latest .
docker save myapp:latest -o myapp.tar

# 在 k3s 節點上
sudo k3s ctr images import myapp.tar

# 確認匯入成功
sudo k3s ctr images list | grep myapp

# Deployment 需指定 imagePullPolicy: Never
kubectl apply -f deploy.yaml

💭 原理：k3s 內嵌 containerd 而非 Docker，所以用 k3s ctr（containerd 原生 CLI）管理鏡像。docker save 匯出 OCI 格式 tar，ctr import 解包放入 containerd 的 content store，K8s 從 containerd 拉取本地鏡像。

💡 kp3 · systemd 服務管理三指令：systemctl、journalctl、daemon-reload systemd,systemctl,journalctl,daemon-reload,服務管理

Linux 服務管理三核心指令：systemctl list-units --state=failed 一次列出所有失敗的服務（快速健康檢查）；journalctl -u <service> -n 50 --no-pager 看特定服務最近 50 行 log（等同 systemd 版的 kubectl logs）；systemctl daemon-reload 在修改 .service unit file 後重載 systemd 設定。其他常用：systemctl status <service> 看服務狀態+最近 log、systemctl restart <service> 重啟、systemctl enable --now <service> 開機啟動並立即運行。

# 列出所有失敗的服務
systemctl list-units --state=failed

# 看特定服務的 log（最近 50 行）
journalctl -u nginx -n 50 --no-pager

# 修改 unit file 後重載 systemd
sudo systemctl daemon-reload
sudo systemctl restart my-service

# 開機啟動並立即啟用
sudo systemctl enable --now my-service

💭 原理：systemd 是 Linux PID 1 的 init 系統，管理所有服務生命週期。透過 unit file（.service/.timer/.path）宣告服務行為，systemctl 是控制介面，journalctl 是日誌查詢工具，daemon-reload 重新掃描 unit files 目錄。

💡 kp4 · Git stash 暫存管理：切換分支前的安全網 Git,stash,stash pop,stash list,暫存管理

當工作區有未 commit 的改動但需要緊急切換分支時，git stash 將當前改動暫存起來（工作目錄恢復乾淨）；回來後用 git stash pop 還原最近一次暫存。進階用法：git stash -u 連 untracked 檔案一起暫存（新建的檔案也不會遺失）；git stash list 看所有暫存記錄（LIFO 堆疊）；git stash apply stash@{2} 還原指定暫存但不刪除；git stash drop stash@{0} 刪除指定暫存。適合切分支修緊急 bug 或試實驗性改動前先存檔。

# 暫存目前改動（含 untracked 檔案）
git stash -u

# 看所有暫存
git stash list

# 還原最近暫存並刪除
git stash pop

# 還原特定暫存（不刪除）
git stash apply stash@2

# 刪除特定暫存
git stash drop stash@0

💭 原理：stash 本質是特殊的 commit-like 物件存在 .git/refs/stash 中（不是分支），採用 LIFO 堆疊結構——最近 stash 的在最上面（stash@0），pop 永遠還原最後一個暫存。

💡 kp5 · 網路排查四指令：curl / dig / ss / nc 對應 OSI 四層 network,curl,dig,ss,nc,OSI,debug

網路故障排查四把瑞士刀，分別對應 OSI 模型的不同層級：curl -v http://host（應用層 L7）— 看完整 HTTP request/response header，包含 SSL/TLS 握手過程；dig +short domain（應用層 DNS）— 快速查域名解析結果；ss -tlnp（傳輸層 L4）— 看哪些 port 在 listen 以及所屬 process（取代過時的 netstat）；nc -zv host port（傳輸層 L4）— 測試目標主機的 port 是否開放。四者搭配幾乎能排除所有網路問題。

# L7 HTTP/HTTPS 診斷（看 SSL 握手、header）
curl -v https://example.com

# DNS 查詢
dig +short example.com

# 看本機 listening port 與所屬 process
ss -tlnp

# 測試遠端 port 是否開放
nc -zv example.com 443

💭 原理：curl 測試服務端到端可用性（含 TLS/HTTP），dig 查 DNS 解析鏈（local cache → 權威 DNS），ss 看本機 socket 監聽狀態（確認服務確實有 bind port），nc 做 TCP 連線測試（從 client 角度確認網路通不通）。

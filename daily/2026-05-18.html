💡 kubectl 診斷 Pod 啟動失敗的完整流程：get pods → describe → logs → get events

當 Pod 無法啟動時，用四步驟系統性排查：kubectl get pods 看 Status 欄位（ImagePullBackOff / CrashLoopBackOff / OOMKilled / Pending），kubectl describe pod 看 Events 區段（最後幾行通常就是失敗原因），kubectl logs 看應用層錯誤，kubectl get events 補足 scheduler 層級的事件。每一步都有明確的排查對象，不需要盲目猜測。

# Step 1: 快速概覽 — 看 Pod 狀態
kubectl get pods -n <namespace> -o wide

# Step 2: 深入細節 — Events 區段是診斷關鍵
kubectl describe pod <pod-name> -n <namespace> | tail -40

# Step 3: 應用層錯誤 — 看容器 log
kubectl logs <pod-name> -n <namespace> --tail=50
kubectl logs <pod-name> -n <namespace> --previous  # CrashLoop 時看上一次的 log

# Step 4: 叢集層級事件 — 補足 scheduler 視角
kubectl get events -n <namespace> --sort-by='.lastTimestamp' | tail -20

💭 原理：這四步驟對應 K8s 的三層架構：scheduler（get events）、kubelet（describe pod）、container runtime（logs）。逐層排查確保你不會在應用層錯誤時去改 scheduler 設定，也不會在 scheduler 排程失敗時去 debug 程式碼。

💡 k3s containerd 鏡像管理完整流程：docker build → docker save → ctr import → kubectl apply → rollout restart

k3s 內建 containerd 而非 Docker daemon，且通常不使用外部 registry。當 imagePullPolicy: Never 時，需要手動把本機 Docker image 匯入 k3s 的 containerd image store。完整流程：docker build 產出 image → docker save 匯出 tar → sudo k3s ctr images import 匯入 containerd → kubectl apply 更新 deployment → kubectl rollout restart 觸發 Pod 重建使用新 image。

# Step 1: 本機 build image
docker build -t myapp:v1.2.0 .

# Step 2: 匯出為 tar（k3s containerd 認得 docker image tar 格式）
docker save myapp:v1.2.0 -o /tmp/myapp-v1.2.0.tar

# Step 3: 匯入 k3s 的 containerd image store
sudo k3s ctr images import /tmp/myapp-v1.2.0.tar

# Step 4: 確認 image 已匯入
sudo k3s ctr images ls | grep myapp

# Step 5: 更新 deployment（imagePullPolicy: Never 時用本地 image）
kubectl set image deployment/myapp myapp=myapp:v1.2.0 -n <ns>
# 或直接 kubectl apply -f deployment.yaml

# Step 6: 強制重建 Pod（確保使用新 image）
kubectl rollout restart deployment/myapp -n <ns>

💭 原理：k3s 為了輕量化，用 containerd 取代 Docker daemon，但 containerd 的 image store 和 Docker 的 image store 是獨立的（/var/lib/rancher/k3s/agent/containerd/ vs /var/lib/docker/）。docker save + ctr images import 就是在兩個 store 之間做「搬運」，讓 containerd 能認得並執行 Docker 產出的 image。

💡 Linux 資源監控三指令：uptime、free -h、df -h，快速判斷 CPU/RAM/Disk 瓶頸

三個指令各對應一種資源：uptime 看 load average（過去 1/5/15 分鐘的平均 CPU 排隊數），free -h 看記憶體（重點看 available 不是 free），df -h / 看磁碟使用率。關鍵判讀：load average > CPU 核心數表示有 process 在排隊等 CPU；free 很低不代表 RAM 不夠（Linux 會拿閒置 RAM 做 cache），要看 available 欄位。

# CPU 負載 — load average 三個數字對應 1/5/15 分鐘
uptime
# 解讀：若 load average > CPU 核心數（nproc），表示 CPU 壅塞中

# RAM 使用 — 重點看「available」，不是「free」
free -h
# free 低不代表 RAM 不夠：Linux 拿 free RAM 做 disk cache，必要時會釋放
# available = free + 可回收的 cache/buffer，才是真正可用量

# Disk 使用 — 看 Use% 欄位
df -h /
# 超過 85% 要開始注意，超過 95% 可能觸發 Pod eviction（kubelet 的 disk pressure）

💭 原理：uptime 的 load average 是 run queue + uninterruptible sleep 的平均值，不只是 CPU 使用率。即使 CPU idle 但 I/O blocked 的 process 也會推高 load average。free -h 的 available 是 kernel 估算的「可立即分配給新 process 的記憶體」，包含 free + 可丟棄的 page cache，遠比 free 更有參考價值。

💡 Git 復原操作三利器：reset --soft、restore、reflog

git reset --soft HEAD~1 退回最近一次 commit 但保留所有 staged 改動（commit 變成未 commit 的 staged 狀態），適合「commit 內容沒錯但 message 寫錯」的情境。git restore <file> 丟棄工作區的未 staged 改動（等同 checkout 舊語法）。git reflog 是救命稻草——所有 HEAD 移動記錄（commit、reset、merge、rebase）都存在這裡，即使你 git reset --hard 誤刪了 commit，也能從 reflog 找回 SHA 並 git checkout 回來。

# 退回最近一次 commit，保留 staged 改動（適合改 commit message）
git reset --soft HEAD~1
git commit -m "新的 commit message"

# 丟棄某個檔案的工作區改動（回復到上次 commit 的狀態）
git restore path/to/file

# 丟棄所有工作區改動
git restore .

# 救命稻草：看所有 HEAD 移動記錄，找回誤刪的 commit
git reflog
# 找到你要的 commit SHA，然後：
git checkout <commit-sha>         # 暫時回到那個 commit 的狀態
# 或
git reset --hard <commit-sha>     # 永久回到那個 commit（謹慎！）

💭 原理：Git 的物件模型是 append-only——commit 物件一旦建立就永遠存在於 .git/objects/，直到 garbage collection（預設 90 天後）。git reset 只是移動 HEAD 指標，不是刪除 commit。git reflog 記錄了所有 HEAD 的移動歷史，所以即使 commit 從 branch 歷史中「消失」，只要 reflog 還有記錄、object 還沒被 GC，就能救回來。

💡 Helm 常用操作：list、history、rollback、get values 四指令覆蓋日常維運

helm list -A 列出所有 namespace 的 Helm release；helm history <release> -n <ns> 看某個 release 的版本歷史與部署狀態；helm rollback <release> <rev> -n <ns> 退回指定版本（不會建立新的 revision，直接回到舊版）；helm get values <release> -n <ns> 查看目前部署所用的 values（有助於確認覆蓋設定是否如預期）。

# 列出所有 namespace 的 Helm release
helm list -A

# 查看某個 release 的部署歷史（含成功/失敗狀態）
helm history monitoring -n monitoring

# 退回指定版本（第 3 個 revision）
helm rollback monitoring 3 -n monitoring

# 查看目前的 values（合併後的結果，包含 values.yaml + --set）
helm get values monitoring -n monitoring

# 查看所有 values（含 chart 預設值）
helm get values monitoring -n monitoring --all

💭 原理：Helm 的 revision 機制是 immutable 的——每次 helm install 或 helm upgrade 都會建立一個新的 ConfigMap/Secret 儲存當時的 values 和 manifest（預設上限 10 個 revision）。helm rollback 不會修改舊 revision，而是用舊 revision 的資料建立一個新的 revision（內容和舊版相同但 revision number 遞增），所以你可以 rollback 之後再 rollback 回來，revision 歷史不會丟失。

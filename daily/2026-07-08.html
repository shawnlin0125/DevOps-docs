💡 KP1 · kubectl top 資源診斷：即時用量 vs Scheduler 視角 kubectl,top,resources,capacity,scheduler

kubectl top nodes 看各節點即時 CPU/Memory 使用量（來自 cgroup 統計），kubectl top pods -A 看每個 Pod 即時用量（找出吃資源的 Pod）。kubectl describe node <node> | grep -A 8 Allocated 看該節點已分配的 request/limit 總和佔比——這是 scheduler 在排 Pod 時看的數字。兩者對比很重要：top 是「實際用多少」，Allocated 是「設定要保留多少」。Alocated 接近 100% 時新 Pod 會 Pending（Unschedulable）。

# 看所有節點即時 CPU/Memory 用量
kubectl top nodes

# 看所有 Pod 即時用量（找出異常吃資源的 Pod）
kubectl top pods -A

# 看特定節點的資源分配佔比（scheduler 視角）
kubectl describe node  | grep -A 8 Allocated

# 快速找出 Unschedulable 節點
kubectl get nodes | grep -v Ready

💭 原理：kubectl top 透過 metrics-server 抓取 kubelet cAdvisor 收集的即時 cgroup 統計資料；describe node Allocated 是 scheduler 在排程時計算的 request/limit 佔比。即時用量低不代表可以再塞 Pod——scheduler 只看 request，不管實際用量。

💡 KP2 · Linux 資源監控三指令：uptime / free / df Linux,monitoring,uptime,free,df,load average,memory,disk

三個 Linux 資源監控必知指令：uptime 顯示 load average（1/5/15 分鐘平均排隊執行緒數），比較 load average vs CPU 核心數——load > 核心數表示 CPU 排隊中。free -h 看記憶體使用，重點看 available 欄位（不是 free）——Linux 會拿閒置 RAM 做 page cache，所以 free 低不代表記憶體不足。df -h / 看磁碟使用率（掛載點空間），搭配 df -i / 看 inode 是否耗盡（inode 滿了檔案系統會報 Disk Full 即使還有空間）。

# 看 load average（1/5/15 分鐘平均排隊數）
uptime

# 看記憶體（重點看 available）
free -h

# 看磁碟空間
df -h /

# 看 inode 用量（inode 滿了也會報 Disk Full）
df -i /

💭 原理：load average 統計的是正在運行 + 不可中斷睡眠（D state）的執行緒總數，超過核心數 = CPU 成為瓶頸。free 指令的 available 是系統估算「可立即分配給新程式的記憶體」（free + 可回收的 cache），比 free 準確。df 查 /proc/mounts 和 statfs syscall，inode 數在格式化時決定（mkfs -i 可調）。

💡 KP3 · Git 復原操作：reset / restore / reflog 三種情境 Git,reset,restore,reflog,復原

Git 三種復原操作對應不同情境：git reset --soft HEAD~1 退回最近一個 commit 但保留工作區和 staging 區的改動（適合 commit 錯內容後重新 commit）；git restore <file> 丟棄工作區未暫存的改動（取代舊版 git checkout --）；git reflog 看所有 HEAD 移動記錄——即使 git reset --hard 誤刪 commit 也能找回（reflog 裡有每個移動的 SHA）。

# 退回最近 commit 但保留改動（重新 commit）
git reset --soft HEAD~1

# 丟棄工作區改動（檔案回到上次 commit 狀態）
git restore 

# 看所有 HEAD 移動記錄（救回誤刪的 commit）
git reflog

# 救回誤刪的 commit（從 reflog 找 SHA 然後 checkout）
git checkout

💭 原理：git reset 移動 HEAD 指標和 branch ref（--soft 不碰 index/working tree，--mixed 重設 index，--hard 全部重設）。git restore 直接改工作區檔案內容（restore 是 2.23 引入的 checkout 拆分管線）。reflog 是本機的 HEAD 移動歷史記錄（存在 .git/logs/HEAD），commit 被 GC 前都能從 reflog 找回（預設 90 天過期）。

💡 KP4 · Helm 常用操作：list / history / rollback / get values Helm,list,history,rollback,get values,release,revision

Helm 版本生命週期管理四指令：helm list -A 看所有 namespace 的所有 release（STATUS: deployed/failed/pending）；helm history <release> -n <ns> 看指定 release 的 revision 歷史（每次 upgrade/install 產生一個 revision）；helm rollback <release> <rev> -n <ns> 退回指定 revision（等同於用該 revision 的 manifest 做一次 upgrade）；helm get values <release> -n <ns> 看目前 release 的 values（含所有覆蓋層級合併後的結果）。

# 看所有 release
helm list -A

# 看 release 版本歷史
helm history  -n 

# 退回指定版本
helm rollback   -n 

# 看目前 release 的合併後 values
helm get values  -n 

# 限制保留 revision 數量（避免 etcd 膨脹）
helm upgrade --history-max 5  .

💭 原理：Helm 每次 upgrade/install 產生一個新 revision（Secret 資源中儲存完整 manifest + values），rollback 只是將目標 revision 的 manifest 重新 apply 到集群。revision 累積過多會佔用 etcd 空間，建議 --history-max 設 5-10。get values 顯示的是 values.yaml、外部 values 檔案、--set 合併後的最終結果。

💡 KP5 · Cloudflare DNS 管理：Proxy Mode vs DNS Only Cloudflare,DNS,Proxy,DNS only,CDN,API

Cloudflare DNS 記錄有兩種模式：Proxy mode（橘色雲朵）——流量經過 Cloudflare CDN 代理，隱藏真實 origin IP（DDoS 防護 + 快取），同時提供免費 SSL/TLS 終止（Flexible/Full/Strict）；DNS only（灰色雲朵）——直接將域名解析到 origin IP，Cloudflare 只做 DNS 代管不做代理。用 Cloudflare API 可自動化管理 DNS 記錄：列出區域→創建/更新/刪除 DNS 記錄，支援批量操作。注意切換 Proxy 模式時建議關閉 SSL 回退，避免代理快取舊記錄。

# 用 Cloudflare API 列出所有 DNS 記錄
curl -s -X GET "https://api.cloudflare.com/client/v4/zones//dns_records"   -H "Authorization: Bearer "   -H "Content-Type: application/json" | jq '.result[] | {name, type, content, proxied}'

# 創建 DNS 記錄（A 記錄 + Proxy 模式）
curl -s -X POST "https://api.cloudflare.com/client/v4/zones//dns_records"   -H "Authorization: Bearer "   -H "Content-Type: application/json"   -d '{"type":"A","name":"example.com","content":"1.2.3.4","proxied":true}' | jq .

# 數位工具：dig 檢查 DNS 記錄狀態
dig +short example.com
dig example.com +noall +answer

💭 原理：Proxy 模式時 Cloudflare 的 Anycast 邊緣節點取代 origin server 直接接收請求（origin IP 隱藏），同時提供 CDN 快取和 HTTP/2 到 HTTP/1.1 回源轉換。DNS only 模式僅提供權威 DNS 解析服務，流量直連 origin server。API 使用 RESTful HTTP + Bearer Token 認證，ZONE_ID 可從 dashboard 或 API 取得。

💡 kubectl 看資源使用：top nodes / top pods / describe node Allocated

三種查看 K8s 資源使用的方式，各回答不同問題：kubectl top nodes 看 node 層級的即時 CPU/RAM 用量；kubectl top pods -A 看每個 pod 的即時用量（可加 --sort-by=memory 排序）；kubectl describe node | grep -A 8 Allocated 看 scheduler 視角的 request/limit 佔比（非即時）。top 是「現在用了多少」，describe Allocated 是「最多能用到多少」。

# Node 層級即時用量
kubectl top nodes
# → NAME              CPU(cores)   CPU%   MEMORY(bytes)  MEMORY%
#   vm-1-243-ubuntu   325m         16%    3764Mi         74%

# Pod 層級即時用量（排序）
kubectl top pods -A --sort-by=memory | tail -10

# Scheduler 視角的資源配額佔比
kubectl describe node vm-1-243-ubuntu | grep -A 8 Allocated
# → Allocated resources:
#   Resource       Requests    Limits
#   cpu            1525m/2000m  3200m/4000m
#   memory         4864Mi/7680Mi  8192Mi/15360Mi

💭 原理：kubectl top 讀取 kubelet 的 cAdvisor/metrics-server 數據，是即時的實際用量。describe node Allocated 從 node status 讀取所有 pod 的 requests/limits 總和，是 scheduler 判斷能否調度新 pod 的依據。兩者不同：top 看健康度，Allocated 看容量規劃。

💡 Docker 多階段建置（multi-stage build）縮小 image 大小

Dockerfile 中可以用多個 FROM 語句，每個 FROM 是一個獨立的建置階段。第一階段（build stage）包含所有建置工具（compiler、dev dependencies），第二階段（runtime stage）只 COPY 建置產物，不帶任何工具鏈。這樣可以大幅縮小最終 image：Go 專案可 FROM scratch（純 static binary 4-15MB）、Node.js 可 FROM nginx:alpine（只 COPY 靜態檔案 10-20MB，不含 Node runtime）。

# === Go 多階段建置範例 ===
# Build stage
FROM golang:1.23-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app ./cmd/server

# Runtime stage — 只需要 binary
FROM scratch
COPY --from=builder /app /app
EXPOSE 8080
ENTRYPOINT ["/app"]
# → image 大小：~12MB（vs golang:alpine ~300MB）

# === Next.js 靜態站台範例 ===
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build && npm run export
# → out/ 資料夾

FROM nginx:alpine
COPY --from=builder /app/out /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
# → image 大小：~10MB（vs node:alpine ~120MB）

💭 原理：Docker image 由多層 layer 組成，每一行 RUN/COPY 指令都新增一層。多階段建置的精髓是最終 image 只包含 runtime stage 的 layer，build stage 的 layer（compiler、dev packages、source code）全部在 final image 中消失。FROM scratch 是最小的 base image（0 bytes），但僅適用於 static binary。

💡 systemd 服務管理：查看失敗服務、查 log、重載設定

systemd 是現代 Linux 的 init 系統，管理所有服務。三個常用診斷指令：systemctl list-units --state=failed 快速查看有哪些服務已失敗；journalctl -u <service> -n 50 --no-pager 查看該服務最近 50 行 log（取代去 /var/log 翻檔案）；systemctl daemon-reload 在修改 .service 檔案後重載配置。搭配 systemctl status <service> 可看服務的完整狀態。

# 查看所有失敗的服務
systemctl list-units --state=failed
# → UNIT                        LOAD   ACTIVE SUB    DESCRIPTION
#   hermes-gateway.service      loaded failed failed Hermes Gateway

# 查看特定服務的最新 log
journalctl -u hermes-gateway -n 50 --no-pager
# → May 29 03:00:01 vm systemd[1]: Starting Hermes Gateway...
# → May 29 03:00:15 vm hermes[12345]: Error: port 8080 already in use

# 查看服務狀態（含最近 log 片段）
systemctl status hermes-gateway --no-pager
# → ● hermes-gateway.service - Hermes Gateway
# →    Loaded: loaded (/etc/systemd/system/hermes-gateway.service; enabled)
# →    Active: failed (Result: exit-code) since ...

# 修改 service file 後重載
sudo systemctl daemon-reload
sudo systemctl restart hermes-gateway

💭 原理：systemd 使用 cgroups 追蹤服務狀態，透過 journald 收集 stdout/stderr。journalctl 比傳統 /var/log 檔案更快且支援結構化查詢（按 unit、priority、time 過濾）。systemctl daemon-reload 讓 systemd 重新讀取 /etc/systemd/system/ 下的 unit file 變更，不重啟服務。

💡 GitHub PR 標準流程：branch → commit → push → PR → review → merge

標準的 GitHub PR 流程是團隊協作的基礎。從 main branch 開 feature branch → 多次 commit → push → 用 gh CLI 或 GitHub UI 開 PR → code review → merge（建議 squash merge 或 merge --no-ff）。gh CLI 可大幅簡化流程，特別是 gh pr create 和 gh pr merge。

# === 完整 PR 流程 ===

# 1. 開 feature branch
git checkout main
git pull origin main
git checkout -b feature/add-health-endpoint

# 2. 開發 & commit
git add .
git commit -m "feat: add /health endpoint for liveness probe"

# 3. push 到遠端
git push -u origin feature/add-health-endpoint

# 4. 開 PR（gh CLI）
gh pr create \
  --title "feat: add /health endpoint" \
  --body "新增 /health 端點供 K8s liveness/readiness probe 使用" \
  --reviewer @team-lead

# 5. PR 通過 CI Gate 後 merge
gh pr merge --squash --delete-branch
# → 完成後自動切回 main + pull

# 6. 或手動 merge（保留 merge commit）
git checkout main
git merge --no-ff feature/add-health-endpoint
git push origin main

💭 原理：Git feature branch workflow 的核心是隔離開發（branch）、審查（PR review）、自動驗證（CI Gate）。gh pr merge --squash 把 branch 上所有 commit 壓成一個 commit 合進 main，保持 main 歷史乾淨。--no-ff（no fast-forward）則保留 merge commit，方便追蹤哪個 PR 引入了哪些變更。

💡 Cloudflare DNS 管理：Proxy mode（orange cloud）vs DNS only（gray cloud）

Cloudflare DNS 有兩種模式：Proxied（橙色雲朵）將流量經由 Cloudflare 邊緣伺服器代理，隱藏 origin IP、提供免費 TLS/SSL、DDoS 防護、CDN 加速；DNS only（灰色雲朵）只做 DNS 解析，流量直接到 origin server。兩者各有適用場景：需要安全防護和 HTTPS 用 Proxied，需要 WS/WSS 串流或不想經過 Cloudflare 過濾用 DNS only。

# === Proxied（orange cloud）=== ✅ 推薦
    
# DNS 查詢結果：Cloudflare edge IP
dig +short vendor-demo.shawnlin.online
# → 104.21.77.199 (Cloudflare)
# → 172.67.211.112 (Cloudflare)

# curl 走 Cloudflare proxy
curl -v https://vendor-demo.shawnlin.online
# → * Server certificate: *.shawnlin.online (Let's Encrypt)
# → * server: cloudflare
# → * cf-ray: a02b...

# === DNS only（gray cloud）===

# DNS 查詢結果：真實 origin IP
dig +short direct.shawnlin.online
# → 43.167.10.119 (origin server)

# === 用 Cloudflare API 管理 DNS record ===
# 建立 Proxied A record
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "A",
    "name": "vendor-demo",
    "content": "43.167.10.119",
    "ttl": 120,
    "proxied": true
  }'

💭 原理：Proxied 模式中，Cloudflare 是反向代理，client ↔ Cloudflare 走 HTTPS（即使 origin 只有 HTTP），Cloudflare ↔ origin 走 HTTP（或自訂）。DNS only 時 Cloudflare 只回傳 origin IP，client 直接連 origin。需要 TLS/SSL 但 origin 沒有自簽憑證時，Proxied 免費提供 Let's Encrypt 憑證。但 Proxied 可能因 WAF 規則攔截正常流量（如 vendor-demo 連線問題）。

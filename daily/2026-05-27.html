🐱 k3s 部署流程與 timestamp tag 繞過緩存（stock-analysis 功能更新）

💡 k3s containerd 完整部署四步驟（docker build → save → ctr import → kubectl set image）

k3s 使用 containerd 而非 Docker runtime，鏡像管理流程為：docker build 產出 Docker image → docker save 匯出 tar → sudo ctr -n k8s.io images import 匯入 containerd 的 k8s namespace → kubectl set image 觸發 rolling update。k3s 不依賴 Docker registry，本地 containerd image store 就是鏡像來源。

# 完整 k3s 部署四步驟（Next.js static export → Docker → containerd → k3s）
# Step 1: 建置 Next.js static export
rm -rf out .next && npx next build
mkdir -p out/data
# （從 running pod 拉取資料檔案到 out/data/）

# Step 2: 打包 Docker image（timestamp tag 避免快取問題）
TAG="stock-analysis:v$(date +%s)"
sudo docker build --no-cache -t $TAG .

# Step 3: 匯入 k3s containerd（注意 namespace 是 k8s.io）
sudo docker save $TAG | sudo ctr -n k8s.io images import -

# Step 4: 更新 deployment 觸發 rolling update
sudo kubectl -n stock-analysis set image deploy/stock-analysis stock-analysis=$TAG
sudo kubectl -n stock-analysis rollout status deploy/stock-analysis

💭 原理：k3s 預設使用 containerd 而非 dockerd。docker build 產出的 image 存在 Docker 的 image store（/var/lib/docker），containerd 看不到。必須透過 docker save + ctr import 跨 runtime 傳遞 image。ctr 的 -n k8s.io 是指定 Kubernetes 用的 containerd namespace。

💡 Timestamp Docker tag 繞過 k3s imagePullPolicy: Never 的 image digest 緩存

k3s deployment 設定 imagePullPolicy: Never 時，kubelet 只檢查本地 containerd 是否有同名 image。若用固定 tag（如 stock-analysis:latest），重新 docker build 後 containerd 內的舊 image digest 不變，k3s 不會重新拉取。解法：每次 build 用 timestamp 作為唯一 tag（stock-analysis:v$(date +%s)），強制 k3s 識別為新 image。

# ❌ 固定 tag 問題：containerd 內已有 stock-analysis:latest
# docker build -t stock-analysis:latest → ctr import → kubectl set image
# k3s: "我已經有 stock-analysis:latest 了，不用重新拉"（實際上內容不同！）

# ✅ Timestamp tag 解決：每次都是全新 tag
TAG="stock-analysis:v$(date +%s)"  # 例：stock-analysis:v1779848611
sudo docker build --no-cache -t $TAG .
sudo docker save $TAG | sudo ctr -n k8s.io images import -
sudo kubectl -n stock-analysis set image deploy/stock-analysis stock-analysis=$TAG

# 驗證：確認 Pod 使用新 image
sudo kubectl -n stock-analysis get pods -o jsonpath='{.items[*].spec.containers[*].image}'

💭 原理：imagePullPolicy: Never 時，kubelet 只做本地 image lookup by tag name。如果 tag 相同，即使底層 digest 已變，kubelet 也不會察覺——因為它根本不比對 digest。timestamp tag 用唯一名稱繞過這個比對漏洞，但副作用是 containerd 內會累積大量舊 image（需定期清理 sudo ctr -n k8s.io images rm）。

💡 docker build 前確認 COPY 指令的來源目錄存在（避免 missing file）

當 Dockerfile 使用 COPY out/ /usr/share/nginx/html/ 時，若 rm -rf out 後忘了重建 out/data/ 目錄，docker build 會順利完成（COPY 只複製 out/ 下存在的內容），但部署後應用缺少必要檔案。實務做法：build 前先從 running pod 拉取資料檔到 out/data/，確保完整。

# ❌ 常見陷阱：clean rebuild 後忘了放回資料檔
rm -rf out .next && npx next build
# out/ 此時只有 _next/ 和 .html，沒有 data/
sudo docker build -t stock-analysis:latest .
# 部署後 → /data/scan-results.json 404！

# ✅ 正確流程：build 前補齊所有必要檔案
rm -rf out .next && npx next build
mkdir -p out/data
# 從 running pod 拉取最新資料
sudo kubectl -n stock-analysis exec deploy/stock-analysis -- cat /usr/share/nginx/html/data/scan-results.json > out/data/scan-results.json
sudo kubectl -n stock-analysis exec deploy/stock-analysis -- cat /usr/share/nginx/html/data/stock-list.json > out/data/stock-list.json
# 確認檔案存在再 build
ls -la out/data/
sudo docker build --no-cache -t stock-analysis:v$(date +%s) .

💭 原理：Docker 的 COPY 指令不會報錯如果來源目錄缺少某些檔案——它只複製「存在的內容」。這和 cp 的行為不同（cp 會報 missing）。解決方案是在 build 腳本中加入防禦性檢查（test -f out/data/scan-results.json || exit 1），或使用 Makefile target 確保依賴關係。

🐱 TWSE 成交量單位陷阱與 kubectl exec 熱修復（stock-analysis 成交量 Bug）

💡 TWSE API TradeVolume 欄位單位是「股」，不是「張」（1 張 = 1,000 股）

TWSE OpenAPI 和 FinMind API 的成交量欄位（TradeVolume）單位都是「股」（shares），不是台灣股市慣用的「張」（1 張 = 1,000 股）。設定成交量門檻時若直接寫 MIN_VOLUME = 5000，實際篩選的是 5 張而非 5,000 張。此 bug 導致篩選結果出現大量不符標準的低成交量股票。

# ❌ Bug：把「股」當成「張」
MIN_VOLUME = 5000  # 實際只篩掉 5 張以下的股票（幾乎沒篩）

# ✅ 修正：張數 × 1,000
MIN_VOLUME = 5_000_000  # 5,000 張 × 1,000 股/張

# 驗證：TWSE API 回傳的 TradeVolume 確實是股數
curl -s "https://openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL" | \
  python3 -c "import json,sys; d=json.load(sys.stdin); [print(f'{x[\"Code\"]} {x[\"Name\"]} vol={int(x[\"TradeVolume\"]):,}股 = {int(x[\"TradeVolume\"])/1000:,.0f}張') for x in d if x['Code']=='2330']"
# 輸出範例: 2330 台積電 vol=35,234,567股 = 35,235張

# 修正後掃描結果：878 檔 → 180 檔（大量低成交量股票被正確排除）

💭 原理：這是 API 文件閱讀陷阱——TWSE API 的欄位說明可能只寫「成交數量」而不標註單位。台灣股市的習慣單位是「張」，但 API 欄位的原始值幾乎都是「股」。所有涉及成交量比對的程式碼（前端過濾、後端掃描、條件判斷）必須統一使用「股」作為內部單位，避免混用。

此 bug 導致儀表板推薦買入的股票中有成交量僅 400-530 張的低流動性標的。修復後掃描器重新執行，候選股票從 878 降至 180，通過 MACD v1 的從 22 降至僅 3 檔。

💡 kubectl exec ... -- tee 直接寫檔進 running pod（純資料更新，免 rebuild image）

當只需更新 Pod 內的靜態資料檔案（如 JSON、設定檔），不需走完整 rebuild → docker build → redeploy 流程。可以直接用 kubectl exec 將新檔案內容 pipe 進容器內覆蓋舊檔。適合頻繁更新的資料檔（掃描結果、報表），大幅節省部署時間。

# 方法一：將本地檔案 pipe 進 pod（單行寫入）
cat scan-results.json | sudo kubectl -n stock-analysis exec -i deploy/stock-analysis -- tee /usr/share/nginx/html/data/scan-results.json > /dev/null

# 方法二：從 pod 拉出 → 修改 → 推回（互動式修復）
sudo kubectl -n stock-analysis exec deploy/stock-analysis -- cat /usr/share/nginx/html/data/scan-results.json > /tmp/scan.json
# 用 Python 或 jq 修改 /tmp/scan.json ...
# 推回 pod
cat /tmp/scan.json | sudo kubectl -n stock-analysis exec -i deploy/stock-analysis -- tee /usr/share/nginx/html/data/scan-results.json > /dev/null

# 驗證修改生效
sudo kubectl -n stock-analysis exec deploy/stock-analysis -- head -c 200 /usr/share/nginx/html/data/scan-results.json

# ❌ 注意：此法不適合會重啟的 Pod（重啟後回到 image 原始內容）
# ✅ 適合：頻繁更新的靜態資料、緊急修復、不需永久化的設定調整

💭 原理：kubectl exec 的 stdin pipe（-i）讓你可以像寫入本地檔案一樣寫入容器內檔案。tee 在這裡的作用是同時寫入檔案和 stdout（> /dev/null 丟棄 stdout）。容器檔案系統是 ephemeral 的——Pod 重啟後所有 exec 寫入的內容都會消失，回到 image 的原始狀態。如果資料是由外部程序（如 cron 掃描腳本）定期寫入 hostPath volume，則不需要用 exec。

🐱 Hermes Cron 排程 timeout 與資料源時間管理（stock-analysis 排程問題）

💡 Hermes cron script mode 120s 硬限制：長時間任務需改用 agent mode

Hermes 的 cron job 在 no_agent（script mode）下有 120 秒的硬性 timeout。如果執行的腳本超過 2 分鐘（如全市場掃描需 20 分鐘），會被強制中斷且不會重試。解法：將 cron job 從 script mode 切換為 agent mode，agent mode 沒有 timeout 限制。

# ❌ Script mode（no_agent）：有 120s 硬限制
# hermes cronjob create --schedule "0 14 * * 1-5" \
#   --command "python3 /home/ubuntu/scripts/scan-all-stocks-v3.py" \
#   --mode no_agent
# → 掃描 20 分鐘 → 120s 被 kill → 失敗

# ✅ Agent mode：無 timeout 限制
# hermes cronjob update  --mode agent
# 或建立時直接指定：
# hermes cronjob create --schedule "0 14 * * 1-5" \
#   --prompt "執行全市場 MACD v1 掃描" \
#   --mode agent
# → Agent 自己管理腳本執行，無 timeout 上限

# 檢查目前 cron job 的 mode
hermes cronjob list  # 查看 output_mode 欄位

# 手動觸發測試（確認修復後可用）
hermes cronjob trigger

💭 原理：Hermes cron 的 script mode 設計用於快速腳本（健康檢查、簡單 curl），底層有 subprocess timeout 保護機制防止 zombie process。Agent mode 則讓 Hermes agent 自行管理執行生命週期，適合長時間批次任務。這個差異在文件不明顯，容易誤用。

當天兩次排程都因 timeout 失敗：14:00 的排程因 broken symlink（script not found）失敗，15:04 的重試因 120s timeout 中斷。掃描最終透過手動背景執行完成（20 分鐘）。

💡 CronJob broken symlink 排查與維運策略

Cron job 設定的腳本路徑是一個 symlink（~/.hermes/scripts/scan-wrapper.py → /home/ubuntu/scripts/scan-wrapper.py），但目標檔案不存在（broken symlink）。排查步驟：ls -la 確認 symlink 指向 → 檢查目標是否存在 → 若目標已移動則修復 symlink 或直接複製檔案。

# 排查 broken symlink
ls -la ~/.hermes/scripts/scan-wrapper.py
# lrwxrwxrwx ... scan-wrapper.py -> /home/ubuntu/scripts/scan-wrapper.py  ← 紅色閃爍 = broken

# 確認目標檔案是否存在
test -f /home/ubuntu/scripts/scan-wrapper.py && echo "存在" || echo "不存在（broken symlink）"

# 修復方法一：更新 symlink 指向正確路徑
rm ~/.hermes/scripts/scan-wrapper.py
ln -s /home/ubuntu/scripts/scan-wrapper.py ~/.hermes/scripts/scan-wrapper.py

# 修復方法二：直接複製檔案（避免 symlink 耦合）
cp /home/ubuntu/scripts/scan-wrapper.py ~/.hermes/scripts/scan-wrapper.py

# 修復方法三：讓 cron 直接指向實際檔案路徑（最簡單）
# 更新 cron job command 從 symlink 改為實際路徑

💭 原理：Symlink 只是指向目標路徑的指標，不包含實際內容。當目標檔案被移動、刪除、或目錄結構改變時，symlink 會變成 dangling（broken）。Cron job 對 broken symlink 的行為等同 file not found。最佳實踐：cron job 盡量使用絕對路徑指向實際檔案，或在部署腳本中加入 symlink 完整性檢查。

💡 資料源更新時間影響排程設計：TWSE 14:30 vs FinMind 18:00

台灣股市 13:30 收盤，但不同資料源的資料可用時間不同：TWSE 官方 OpenAPI 約 14:30 更新當日資料，FinMind 第三方 API 約 18:00 才完成更新。排程時間必須晚於資料源更新時間，否則掃描到的是前一天資料。目前 cron 設定為 14:00（盤後 30 分鐘），對 TWSE 來說可能太早。

# 資料可用性時間線（台灣股市）
# 13:30  收盤
# 14:00  目前 cron 排程（⚠️ TWSE 資料可能尚未更新）
# 14:30  TWSE OpenAPI 當日資料可用（官方交易所）
# 18:00  FinMind 第三方 API 完成更新

# 建議排程時間
# TWSE 來源：14:30 之後（保守設 15:00）
# FinMind 來源：18:00 之後（保守設 18:30）

# 實務作法：在掃描腳本開頭檢查資料日期
import requests, json
resp = requests.get("https://openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL")
data = json.loads(resp.text)
# 檢查第一筆資料的日期是否為今天
if data and data[0].get("Date"):
    print(f"TWSE 資料日期: {data[0]['Date']}")
    # 若日期不是今天 → 退出或 retry

💭 原理：資料 pipeline 的排程時間是「資料可用時間 + 處理時間 + 緩衝」的組合。資料源更新時間不是文件寫的，而是實測出來的（TWSE 實際 API 行為 vs FinMind 文檔）。生產排程應該比資料可用時間晚 30-60 分鐘作為安全邊際，並在腳本中加入資料日期檢查做防禦。

🐱 k3s 緊急 Pod 修復與 Cloudflare CDN 快取管理（stock-analysis dashboard 掛了）

💡 緊急修復要先繞過 CDN 快取：curl pod IP 直接驗證（而非走 domain）

當網站掛掉需要緊急修復時，瀏覽器或 curl 透過 domain 存取的是 Cloudflare CDN 快取層，可能看到舊的快取內容或 stale error page。正確做法：先取得 Pod IP（kubectl get pods -o wide），直接 curl Pod 的 cluster IP + port，繞過 CDN 和 ingress，確認 Pod 本身的實際狀態。

# Step 1: 取得 Pod IP（繞過 CDN/ingress 的直連路徑）
sudo kubectl -n stock-analysis get pods -o wide
# NAME                              READY   STATUS    IP           NODE
# stock-analysis-66fd9dff58-vxg4m   1/1     Running   10.42.0.45   k3s-node

# Step 2: 直連 Pod IP 測試（不經 CDN，不經 ingress）
curl -s http://10.42.0.45:80/data/scan-results.json | head -c 300

# Step 3: 對比 CDN 路徑（經過 Cloudflare + ingress）
curl -s https://stock.shawnlin.online/data/scan-results.json | head -c 300

# 如果兩個結果不同 → 問題在 CDN 快取或 ingress 路由
# 如果 Pod IP 也回錯誤 → 問題在 Pod 內部

💭 原理：現代網站架構中，請求路徑通常是：Client → Cloudflare CDN → Ingress Controller → Service → Pod。每一層都可能快取或修改回應。診斷時從最底層（Pod IP）往上排查，可以快速定位問題層級。Pod IP 正常但 domain 異常 = CDN/ingress 問題；Pod IP 異常 = 應用層問題。

💡 kubectl exec -i + pipe 做 in-place 熱修復：Python 轉換 JSON → 寫回 pod

本次 dashboard 掛掉的原因是 Python 掃描器輸出的 scan-results.json 使用 snake_case 欄位（change_pct），而前端 TypeScript 期待 camelCase（changePct）。緊急修復：用 Python 轉換 JSON key → pipe 進 pod 覆蓋檔案。2 分鐘內恢復服務，無需走 rebuild 流程。

# 緊急修復流程（snake_case → camelCase in-place）
# Step 1: 從 pod 拉出原始 JSON
sudo kubectl -n stock-analysis exec deploy/stock-analysis -- \
  cat /usr/share/nginx/html/data/scan-results.json > /tmp/scan.json

# Step 2: Python 轉換 key（snake_case → camelCase）
python3 -c "
import json, re
with open('/tmp/scan.json') as f:
    data = json.load(f)
def to_camel(s):
    return re.sub(r'_([a-z])', lambda m: m.group(1).upper(), s)
results = [{to_camel(k): v for k, v in r.items()} for r in data['results']]
print(json.dumps({'results': results}, ensure_ascii=False))
" > /tmp/scan-fixed.json

# Step 3: pipe 回 pod 覆蓋原檔
cat /tmp/scan-fixed.json | sudo kubectl -n stock-analysis exec -i deploy/stock-analysis -- \
  tee /usr/share/nginx/html/data/scan-results.json > /dev/null

# Step 4: 驗證修復
sudo kubectl -n stock-analysis exec deploy/stock-analysis -- \
  head -c 200 /usr/share/nginx/html/data/scan-results.json
# 確認看到 "changePct" 而非 "change_pct"

💭 原理：這是 "hotfix via data transform" 模式——不修改應用程式碼，而是修正輸入資料的格式讓既有程式碼可以正確處理。Python 一行 dict comprehension 做 key mapping 比 sed 安全（sed 可能誤改 value 中的底線）。注意：kubectl exec -i 的 pipe 有大小限制（約幾 MB），超大檔案需分段或改用 kubectl cp。

💡 Cloudflare cf-cache-status header 確認快取狀態（HIT / MISS / EXPIRED / DYNAMIC）

Cloudflare proxy（orange cloud）會自動快取靜態資源。緊急修復 Pod 內容後，CDN 可能仍回傳舊快取。用 curl -I 檢查 cf-cache-status header：HIT 表示從 CDN 快取回應、MISS 表示回源、EXPIRED 表示快取過期已重新抓取、DYNAMIC 表示不緩存。

# 檢查 Cloudflare 快取狀態
curl -I https://stock.shawnlin.online/data/scan-results.json 2>/dev/null | grep -i cf-
# cf-cache-status: HIT     ← CDN 正在用快取版本（可能不是最新的！）
# cf-cache-status: MISS    ← CDN 回源 fetch 新內容
# cf-cache-status: EXPIRED ← 快取過期，已重新 fetch
# cf-ray: 8a3b...          ← Cloudflare edge node ID

# 完整看所有 Cloudflare 相關 header
curl -sI https://stock.shawnlin.online/ | grep -iE '^(cf-|cache|age|server)'
# cf-cache-status: DYNAMIC
# cache-control: public, max-age=0, must-revalidate
# server: cloudflare

# 強制繞過 CDN 快取（開發/緊急時用）
curl -s -H "Cache-Control: no-cache" -H "Pragma: no-cache" \
  https://stock.shawnlin.online/data/scan-results.json | head -c 200

# Cloudflare 手動 purge cache（透過 API 或 Dashboard）
# Dashboard: https://dash.cloudflare.com/ → Caching → Purge Everything

💭 原理：Cloudflare 的 proxy mode 在 origin server 前面插入全球 CDN。靜態檔案（JSON、JS、CSS）預設會被快取，快取時間由 origin 的 Cache-Control header 或 Cloudflare 的 Page Rules 決定。緊急修復時最大的陷阱就是：你修好 Pod 了，但 CDN 還在餵舊內容。MISS/HIT 告訴你使用者看到的是哪個版本。

💡 Pod 內直接修改是暫時的：永久修復需要程式碼 fix + rebuild + redeploy

用 kubectl exec ... tee 寫入 Pod 內檔案的修改是 ephemeral（暫時的）。Pod 重啟、重新部署、node 故障遷移後，所有 exec 修改都會消失，回到 Docker image 的原始狀態。緊急 hotfix 只是爭取時間，永久修復仍需改程式碼 → rebuild image → redeploy。

# 暫時修復（緊急時用，2 分鐘恢復服務）
cat fixed.json | kubectl exec -i pod -- tee /data/file.json > /dev/null

# 永久修復流程（事後必須完成）
# 1. 修改原始碼（例：app/page.tsx 加入 snake_case→camelCase 轉換）
# 2. Clean rebuild
rm -rf out .next && npx next build
# 3. Docker build + k3s deploy
sudo docker build --no-cache -t stock-analysis:v$(date +%s) .
sudo docker save stock-analysis:v$(date +%s) | sudo ctr -n k8s.io images import -
sudo kubectl -n stock-analysis set image deploy/stock-analysis stock-analysis=stock-analysis:v$(date +%s)
# 4. 等 rolling update 完成後，kubectl exec 修改消失，但程式碼已自帶修正

# ⚠️ 常見失誤：做完 hotfix 就以為修好了，結果下次 deploy 又掛
# 檢查清單：
# □ 原始碼已修改並 commit？
# □ Docker image 已 rebuild？
# □ k3s deployment 已 rolling update？
# □ 確認 Pod 內的檔案是 image 內建版本（非 exec injected）？

💭 原理：容器檔案系統是 overlay filesystem（image layer + container layer）。kubectl exec 寫入的內容存在 container layer，Pod 刪除時一起消失。只有寫入 Dockerfile（image layer）的內容才會持久。這是容器的核心設計——immutable infrastructure——hotfix 是對這個設計的暫時繞過，不是長期策略。

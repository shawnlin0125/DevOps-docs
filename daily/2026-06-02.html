🔧 k3s 部署 Pipeline

💡 kp1: k3s 部署前必須完全清除建置快取

Next.js 增量建置不會覆蓋既有 out/ 目錄中的舊檔案。若不清除直接 docker build，Docker 的 COPY 層會保留上次的 out/ 內容，導致部署的仍是舊版頁面。

rm -rf out .next && npx next build

💭 原理：Next.js 的 next build 對已存在的 out/ 檔案採非破壞性寫入，只新增不覆蓋。手動清除才能保證 100% 乾淨匯出。這個陷阱在輪廓式編譯（Turbopack）下更常見。

💡 kp2: 使用唯一 timestamp tag 繞過 k3s image digest 快取

k3s 搭配 imagePullPolicy: Never 時，Pod 根據 image digest（SHA256）決定是否重拉。即使重新匯入相同名稱的 tag，k3s 仍使用舊 digest，除非 tag 不同。

TAG="stock-analysis:v$(date +%s)"
sudo docker build --no-cache -t $TAG .
sudo docker save $TAG | sudo ctr -n k8s.io images import -
sudo kubectl -n stock-analysis set image deploy/stock-analysis stock-analysis=$TAG

💭 原理：containerd 的 image store 以 digest 為主鍵。re-import 同 tag 的新 image 時，舊 digest 不會自動失效。唯一 tag 強制 kubelet 辨識為新 image 觸發重拉。

💡 kp3: Docker legacy builder 快取 COPY 層必須用 --no-cache 避開

Docker legacy builder 會對 COPY out/ ./ 這類指令做 layer 快取。如果 out/ 的檔案 mtime 沒變或內容被快取判定為相同，就會沿用舊 layer，導致新靜態檔案沒進去。

sudo docker build --no-cache -t $TAG .

💭 原理：Docker 的 layer 快取比對每個 COPY 檔案的 checksum，但若在新容器內重新產生相同內容的檔案（如 CI 重複 build），hash 可能相同。--no-cache 強制跳過所有快取重新執行每個指令。

💡 kp4: k3s containerd 鏡像匯入指令

k3s 預設不使用 Docker CLI 或 Docker registry，而是透過 containerd（namespace k8s.io）管理鏡像。部署本地建置的 image 時：docker build → docker save → pipe 進 ctr images import。

sudo docker save $TAG | sudo ctr -n k8s.io images import -

💭 原理：docker save 輸出 tar stream，pipe 給 ctr images import 直接寫入 containerd 的 content store，繞過 Docker registry。k3s 的 containerd 使用獨立 namespace k8s.io，不是預設的 default。

💡 kp5: k3s containerd namespace 為 k8s.io

查詢 k3s 的 containerd 鏡像清單必須指定 namespace，否則預設 namespace（default）不會顯示 k8s 使用的鏡像。

# ✅ 正確：指定 k8s.io namespace
sudo ctr -n k8s.io images ls

# ❌ 錯誤：crictl 不適用於鏡像管理（只能看容器）
sudo crictl images

💭 原理：k3s 安裝時將 containerd 的 k8s 相關 namespace 設為 k8s.io 以隔離 kubernetes 與系統容器的鏡像。若不指定 namespace，ctr images ls 只會顯示 default namespace 的鏡像，通常是空的。

💡 kp6: 部署前必須從 Running Pod 複製資料到建置目錄

rm -rf out 會同時刪除 out/data/ 中的掃描結果。Docker build 時必須先重建 out/data/ 並從已在運行的 Pod 複製最新資料。

mkdir -p out/data
sudo kubectl exec -n stock-analysis deploy/stock-analysis -- \
  cat /usr/share/nginx/html/data/scan-results.json > out/data/scan-results.json

💭 原理：out/data/ 包含動態產生的掃描結果（不在版控中），由 cron 掃描器定時寫入。部署時若從頭 build，資料目錄會消失，Pod 重啟後直到下次掃描前頁面都無資料可顯示。

💡 kp7: imagePullPolicy: Never 的 digest 快取行為

當 Deployment 設為 imagePullPolicy: Never 時，kubelet 完全依賴本地 containerd image store 的 digest。同一個 tag 重複匯入不同內容的 image 後，Pod 仍使用舊 digest 啟動。

# 驗證 Pod 實際使用的 image digest
sudo kubectl get pods -o jsonpath='{.items[0].status.containerStatuses[0].imageID}'

💭 原理：kubelet 在 container 建立時從 CRI（containerd）查詢 image 的 digest 並鎖定。ctr images import 雖然能 overwrite 同名的 tag，但 containerd 的 reference store 可能保留舊 mapping。唯一 tag 是唯一可靠解法。

⏰ Hermes Cron 排程除錯

💡 kp8: Hermes cron no_agent mode 有 120 秒硬性超時限制

Hermes 的 no_agent script cron job 有不可設定的 120 秒超時保護。全市場掃描腳本因需逐一查詢每檔股票 API，至少需 5-10 分鐘，必然觸發 timeout。

# 工作區手動執行（無超時限制）
terminal(background=true, command="python3 -u scan-all-stocks-v3.py", timeout=3600)

💭 原理：no_agent mode 的 cron job 由 Hermes gateway 的簡化執行器驅動，設計上為輕量腳本（health check、curl）服務。掃描類長時間任務應使用 agent-mode cron（無 timeout，但消耗更多 token）或 background terminal。

💡 kp9: Hermes cron 腳本必須實體複製到 ~/.hermes/scripts/

Hermes cron job 的 script: 欄位指定腳本路徑時，只能位於 ~/.hermes/scripts/ 目錄內，不支援絕對路徑或 symlink（symlink 會被偵測為 path traversal 拒絕執行）。

# ✅ 正確：實體複製
cp /home/ubuntu/scripts/scan-wrapper.py ~/.hermes/scripts/

# ❌ 錯誤：symlink 會被拒絕
ln -s /home/ubuntu/scripts/scan-wrapper.py ~/.hermes/scripts/

💭 原理：Hermes 的安全機制限制 cron script 只能在沙箱目錄 ~/.hermes/scripts/ 內，防止路徑穿越攻擊。更新腳本後必須重新手動複製，兩邊不會自動同步。

💡 kp10: 背景程序 stdout buffering 改用 /tmp/ status file 輪詢

Python 背景程序在 stdout 被重導向時，即使使用 flush=True 或 PYTHONUNBUFFERED=1，Hermes 的 background process manager 仍可能緩衝輸出。改用寫入 /tmp/scan-status.json 狀態檔並定期讀取更可靠。

# 在掃描腳本中定期寫入狀態
import json
with open("/tmp/scan-status.json", "w") as f:
    json.dump({"progress": i, "total": total, "status": "running"}, f)

# 由外部定期輪詢
cat /tmp/scan-status.json

💭 原理：檔案寫入是 fsync 後原子化的（小於 PIPE_BUF 的 JSON），不像 pipe/stdout 受 buffer 層級影響。JSON status file 可同時解決進度追蹤和中途 crash 狀態保存兩個問題。

🔍 監控與除錯

💡 kp11: 五處 MACD 條件副本必須保持同步

MACD 動能篩選條件在 codebase 中重複定義了五個獨立副本：backtest engine、StrategyCheck 元件、三個 page 元件的 runScan/runBatch。修改條件時必須同步更新所有五處。

# 搜索所有 MACD 條件定義的位置
grep -rn "hasMomentumBuy\|momentum\|MACD動能" lib/backtest.ts components/StrategyCheck.tsx app/page.tsx app/strategy/page.tsx app/quick/page.tsx

💭 原理：歷史因素導致條件定義散落在 backtest（原始實作）和 UI 元件（後來加入即時掃描功能）之間。理想做法是提取到共用 module（如 lib/strategy-conditions.ts），但尚未重構前只能靠手動同步。

💡 kp12: 部署後驗證 compiled chunk 的 function 數量

Next.js Turbopack static export 可能會意外 tree-shake 掉 client-side JavaScript 中的 function（如 window.open）。部署後檢查 compiled chunk 中特定 function 的出現次數可確認 tree-shaking 正常。

# 驗證 window.open 在 page chunk 中的出現次數
grep -c 'window.open' out/_next/static/chunks/*.js

# 若為 3，表示三個頁面的呼叫都正確保留

💭 原理：Turbopack（Next.js 的 Rust 編譯器）在 static export 時會做 aggressive tree-shaking。如果某個 function 被編譯器判定為「未使用」，即使 runtime 有條件式引用也會被移除。post-deploy grep 驗證是低成本檢查手段。

# 1. 清除快取並重建
rm -rf out .next && npx next build

# 2. 從 Running Pod 複製最新資料
mkdir -p out/data
sudo kubectl exec -n stock-analysis deploy/stock-analysis -- \
  cat /usr/share/nginx/html/data/scan-results.json > out/data/scan-results.json

# 3. 建置並匯入 containerd
TAG="stock-analysis:v$(date +%s)"
sudo docker build --no-cache -t $TAG .
sudo docker save $TAG | sudo ctr -n k8s.io images import -

# 4. 更新 Deployment 並驗證
sudo kubectl -n stock-analysis set image deploy/stock-analysis stock-analysis=$TAG
sudo kubectl -n stock-analysis rollout status deploy/stock-analysis

# 查看 Pod 實際使用的 image digest
sudo kubectl get pods -o jsonpath='{.items[0].status.containerStatuses[0].imageID}'

sudo ctr -n k8s.io images ls

# 背景掃描腳本手動執行

# 檢查掃描進度

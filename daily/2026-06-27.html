💡 kubectl 診斷 Pod 啟動失敗的完整流程

Pod 啟動失敗四步驟排查：kubectl get pods → kubectl describe pod → kubectl logs → kubectl get events。從 Status/Events 欄位判斷 ImagePullBackOff（鏡像不存在）、CrashLoopBackOff（容器不斷重啟）、OOMKilled（超過記憶體限制）、Pending（資源不夠排程）。describe 的 Events 段落記錄 kubelet 對 Pod 的每一個操作與錯誤原因，是最快定位問題的入口。

# 1. 看 Pod 狀態
kubectl get pods -n 

# 2. 詳細描述（Events 段落最關鍵）
kubectl describe pod  -n 

# 3. 看容器 log
kubectl logs  -n 
kubectl logs --previous  -n    # 前一次 crash 的 log

# 4. 看叢集層級事件（超過 1h 的會消失）
kubectl get events -n  --sort-by='.lastTimestamp'

💭 這四步驟從狀態摘要→詳細事件→應用層日誌→叢集層事件，由外而內逐步縮小問題範圍。Events 記錄了 kubelet 對 Pod 的每一個操作（拉取鏡像、掛載 volume、健康檢查失敗），是 K8s 除錯的黃金入口。

💡 Docker 多階段建置縮小 Image：builder → runtime 瘦身法

多階段建置（multi-stage build）讓 Dockerfile 可以有多個 FROM 指令。第一個 stage（builder）裝所有編譯工具和依賴做建置，第二個 stage（runtime）只複製最終 artifacts。Go 靜態 binary 可用 FROM scratch 讓 image 最小化（～5MB），Node.js 可用 standalone output。查看 image 大小用 docker images | grep <name>。每個 RUN/COPY 指令都會增加一層，多階段讓 builder 層在建置完後被丟棄。

# Multi-stage Dockerfile 範例（Go）
# --- Stage 1: builder ---
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# --- Stage 2: runtime ---
FROM scratch
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]

# 查看 image 大小
docker images | grep myapp

💭 每個 FROM 宣告一個獨立建置階段，只有最後一個 FROM 的內容會留在最終 image 中。builder 層的編譯工具和中間檔案在建置完就廢棄，大幅縮小 image，同時減少攻擊面。

💡 查 OOM 紀錄：dmesg + exit code 137

當系統記憶體不足時，Linux OOM Killer 會挑選 oom_score 最高的行程終止以釋放記憶體。sudo dmesg -T | grep -i oom 查看核心 OOM 記錄（含被殺的 process name、oom_score、記憶體佔用）。exit code 137（= 128 + 9 SIGKILL）表示行程被 OOM 殺死。在 K8s 中，Pod 的 memory limits 總和超過節點實體 RAM 時 OOM 會連鎖殺 Pod。kubectl describe pod 的 Last State: OOMKilled 是 K8s cgroup 層級的 OOM。

# 系統層級 OOM 記錄（核心緩衝區）
sudo dmesg -T | grep -i oom

# 查看行程 exit code 是否為 OOM
# 在 K8s 中
kubectl describe pod  | grep -A 10 "Last State"

# 看 Pod 重啟原因
kubectl get pods -o wide | grep -E "CrashLoop|OOM"

# 監控記憶體壓力
free -h
kubectl top nodes

💭 exit code 137（SIGKILL）是 OOM 的典型徵兆。系統層 OOM（dmesg）和 K8s cgroup OOM（describe pod OOMKilled）是不同層級的機制：前者發生的話任意行程都可能被殺，後者只影響該 Pod 容器。

💡 Git stash 暫存管理：切換分支前的好幫手

當你正在工作區改動檔案但還沒 commit，卻需要切換分支或拉取更新時，git stash 可以暫存所有改動（含 staged 和 unstaged），還原一個乾淨的工作區。git stash -u 也會暫存 untracked files。git stash pop 還原最近一次暫存並從 stack 移除；git stash list 看所有暫存（LIFO，最後存的先出來）。stash 本質是 commit-like 物件存在 .git/refs/stash，可跨 branch 套用但可能產生衝突。

# 暫存目前改動（含 staged）
git stash

# 暫存含 untracked files
git stash -u

# 查看所有暫存
git stash list

# 還原最近一次暫存並移除
git stash pop

# 還原指定暫存但不移除
git stash apply stash@{1}

# 清除所有暫存
git stash clear

💭 stash 是一個 stack（LIFO），每次 stash 都在 .git/refs/stash 建立一個 commit。stash pop = apply + drop。跨 branch 套用 stash 可能衝突，需要手動解決。適合短時間暫存（幾小時到一天），長期暫存建議開 WIP branch。

💡 Cloudflare DNS 管理：Proxy vs DNS only 模式

Cloudflare DNS 有兩種模式：Proxy mode（橙色雲朵，也稱 proxied）流量經過 CDN 邊緣節點、隱藏 origin IP、提供免費 SSL/TLS 終止、DDoS 防護；DNS only（灰色雲朵）直接解析到 origin IP、無 CDN 加速或防護。用 dig +short example.com 查看：回傳 Cloudflare IP 表示 Proxy mode，回傳真實主機 IP 表示 DNS only。Cloudflare API 可程式化管理 DNS records，適合自動化。

# 確認 DNS 記錄模式（dig）
dig +short example.com
# Cloudflare IP 範圍 => Proxy mode
# 真實主機 IP => DNS only

# Cloudflare API 新增 DNS record（需 API Token）
curl -X POST "https://api.cloudflare.com/client/v4/zones//dns_records" \
  -H "Authorization: Bearer " \
  -H "Content-Type: application/json" \
  --data '{
    "type": "A",
    "name": "app",
    "content": "1.2.3.4",
    "ttl": 120,
    "proxied": true
  }'

💭 Proxy mode 透過 Cloudflare IP 轉發 True-Client-IP header 給 origin server，同時提供免費 TLS 終止。但 WebSocket 和 gRPC 在 Proxy mode 下可能不穩定（Cloudflare 不支援 HTTP/2 到 origin 的 gRPC）。DNS only 適合低延遲、不經過 CDN 的內部服務。

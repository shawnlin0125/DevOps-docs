💡 kp1 · kubectl top 資源診斷：即時用量 vs Scheduler 視角 kubectl,資源監控,K8s

kubectl top nodes 與 kubectl top pods -A 查看即時 CPU/RAM 用量；kubectl describe node | grep -A 8 Allocated 查看 request/limit 佔比（Scheduler 視角）。兩者差異：top 是實際消耗，describe Allocated 是排程保證量。

kubectl top nodes
kubectl top pods -A
kubectl describe node | grep -A 8 Allocated

💭 原理：即時用量 vs 排程用量是兩個不同維度——OOM 時看即時，Unschedulable 時看排程佔比。

💡 kp2 · Docker 多階段建置：Builder → Runtime 瘦身法 Docker,Image,多階段建置

多階段建置（Multi-stage build）讓 builder stage 裝編譯工具，runtime stage 只複製 artifacts。Go 可 FROM scratch 產生～10MB 的靜態 binary；Node.js 用 standalone output 也可大幅縮小。

FROM golang:alpine AS builder
WORKDIR /app
COPY . .
RUN go build -o myapp .
FROM alpine:latest
COPY --from=builder /app/myapp /myapp
CMD ["/myapp"]
# 查看 image 大小
docker images | grep

💭 原理：多階段建置的精髓是 runtime 環境只保留必要內容，拋棄編譯階段的重量級工具鏈。

💡 kp3 · Linux 資源監控：uptime / free / df 三指令 Linux,監控,系統維運

uptime 看 load average（超過核心數表示排隊）；free -h 看 available（不是 free——Linux 用閒置 RAM 做 cache）；df -h / 看磁碟使用率。三部曲涵蓋 CPU、RAM、Disk。

uptime
free -h
df -h /

💭 原理：load average > CPU 核心數表示 CPU 排程阻塞；available 是真正可用的 RAM（free + cache/buffer 中可回收的部分）。

💡 kp4 · Git 復原操作：reset / restore / reflog 三種情境 Git,復原,版本控制

git reset --soft HEAD~1（退回 commit 但保留 staged 檔案）；git restore （丟棄工作區改動，相當於 checkout）；git reflog（看所有 HEAD 移動記錄，可救回誤刪的 commit）。

# 退回 commit 但保留變更
git reset --soft HEAD~1
# 丟棄工作區改動
git restore 
# 救回誤刪的 commit
git reflog
git reset --hard HEAD@{n}

💭 原理：reflog 是 Git 的局部安全網——只要 commit 曾經被 HEAD 指向過，reflog 就有記錄，reset 和 rebase 誤操作都救得回來。

💡 kp5 · Helm 常用操作：生命週期管理四指令 Helm,K8s,套件管理

helm list -A 看所有 release；helm history -n 看版本歷史；helm rollback 退回指定版本；helm get values -n 看目前生效的 values。

helm list -A
helm history  -n 
helm rollback   -n 
helm get values  -n

💭 原理：helm history + rollback 是 K8s 應用的時間機器——部署出問題時秒級回退，不用重新部署整個 YAML。

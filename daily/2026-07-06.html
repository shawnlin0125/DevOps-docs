💡 kp1 · kubectl exec 進 Pod 內排查：env、nc、resolv.conf 三招 kubectl,exec,debug,pod

當 Pod 正在運行但行為異常（連不上資料庫、環境變數不對、DNS 解析失敗），用 kubectl exec -it <pod> -n <ns> -- sh 進到容器內互動排查。三個常用內部指令：env | grep -i 確認環境變數是否正確注入；nc -zv <svc> <port> 測試 TCP 連線（不須額外安裝 curl/wget）；cat /etc/resolv.conf 確認 DNS 設定是否指向正確的 CoreDNS ClusterIP。

# 進容器內排查（若有 /bin/bash 可改 -- bash）
kubectl exec -it <pod> -n <namespace> -- sh

# 確認環境變數
env | grep -i DB_HOST

# 測試服務連線（nc = netcat，大部分容器都有）
nc -zv my-service 5432

# 確認 DNS 設定（k8s 預設 /etc/resolv.conf 指向 svc.cluster.local）
cat /etc/resolv.conf

💭 原理：kubectl exec 是「門診室」——讓你不重啟 Pod 就能進去翻日誌、測連線、看設定，是 K8s 除錯的核心手法。

💡 kp2 · Docker 多階段建置縮小 Image Docker,Image,多階段建置,瘦身

多階段建置（Multi-stage build）讓 Dockerfile 有多個 FROM 階段——builder stage 裝完整編譯工具鏈做建置，runtime stage 只複製最終 artifacts。Go 可直接 FROM scratch 產生約 10MB 的靜態 binary（含 ca-certificates 用 alpine 補充）；Node.js 用 node:alpine 並把 standalone build output 複製過去。查看 image 大小用 docker images | grep <name> 或 docker image history <name> 看每一層的大小。

# Go 多階段建置範例
FROM golang:alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o myapp .

FROM alpine:latest
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/myapp /myapp
CMD ["/myapp"]

# 查看 image 大小
docker images | grep myapp
docker image history myapp

💭 原理：每個 FROM 是獨立的鏡像階段——builder 層建置完就被丟棄，runtime layer 只保留最終必要檔案，image 從數百 MB 降到數十 MB。

💡 kp3 · OOM Killer 診斷：dmesg + exit code 137 判別法 OOM,dmesg,exit code,SIGKILL,memory,Linux

當系統或 K8s Pod 被 OOM Killer 終止時，用 sudo dmesg -T | grep -i oom 查看核心 OOM 記錄，包含被終止的 process 名稱、PID、oom_score 以及當時記憶體使用量。Exit code 137（128 + 9 = SIGKILL）表示 process 被 OOM Killer 終止。兩層 OOM 的區別：kubectl describe pod 中 Last State: OOMKilled 是 cgroup 層級 OOM（由 K8s memory limits 觸發），而 dmesg 的 OOM 是節點層級（實體記憶體不足）。K8s 中若所有 Pod 的 memory limits 總和超過實體 RAM，OOM Killer 會連鎖殺 Pod。

# 看核心 OOM 記錄（-T 轉成人類可讀時間）
sudo dmesg -T | grep -i oom

# K8s 中看 Pod 是否被 OOM 殺死
kubectl describe pod <name>
# 看 Last State → OOMKilled

# Exit code 137 = SIGKILL
echo $?
# 137

💭 原理：OOM Killer 會挑 oom_score 最高的 process 終止（通常是 RSS 記憶體佔用最大者），exit code 128+signal=137 表示被 SIGKILL 強制終止。

💡 kp4 · GitHub PR 流程：gh CLI 完整操作 GitHub,gh,PR,merge,squash,CLI

用 gh CLI 在 terminal 內完成 PR 全流程：git checkout -b feature/xxx → commit → git push -u origin feature/xxx → gh pr create --title "..." --body "..." → 等 review → 合併（gh pr merge --squash --delete-branch 或 gh pr merge -m）。其他實用指令：gh pr list -A @me 看我開的 PR，gh pr diff 看變更內容，gh pr checkout <number> 切到 review branch，gh pr review --approve 批准。

# 完整 PR 流程
git checkout -b feature/new-thing
git add . && git commit -m "feat: new thing"
git push -u origin feature/new-thing
gh pr create --title "feat: new thing" --body "Implement new thing"

# 合併 PR（--squash 整理成一筆 commit）
gh pr merge --squash --delete-branch

# PR 列表與切換
gh pr list -A @me
gh pr checkout 42
gh pr diff

💭 原理：gh CLI 封裝 GitHub REST/GraphQL API，省去開瀏覽器切頁面的時間——PR 全流程在 terminal 完成，適合自動化程度高的工作流。

💡 kp5 · Cloudflare DNS 管理：Proxy Mode vs DNS Only Cloudflare,DNS,Proxy,CDN,TLS,API

Cloudflare DNS Record 有兩種模式：Proxy mode（橙色雲朵）——流量經過 Cloudflare 全球 CDN 網路，隱藏 origin IP 地址，提供免費 TLS 終止（Universal SSL）、DDoS 防護和快取加速；DNS only（灰色雲朵）——直接解析到 origin IP，無 CDN 保護。用 dig +short example.com 檢查模式：回傳 Cloudflare IP（任何 Cloudflare 邊緣節點 IP）表示 Proxy mode；回傳真實伺服器 IP 表示 DNS only。可透過 Cloudflare API 程式化管理 DNS records，適合基礎設施即程式碼的自動化部署。

# 查 DNS 看是否用 Cloudflare Proxy
dig +short example.com
# 回傳 Cloudflare IP → Proxy mode
# 回傳真實 IP → DNS only

# Cloudflare API 查所有 DNS Records
curl -s -X GET "https://api.cloudflare.com/client/v4/zones/{zone_id}/dns_records"   -H "Authorization: Bearer {token}"   -H "Content-Type: application/json" | jq

# 檢查 TLS 憑證狀態
curl -sI https://example.com | grep -i cf-ray

💭 原理：Proxy mode 本質是反向代理——Cloudflare 邊緣節點代理 TLS 終止後，透過自有線路轉發到 origin server（需確保 origin 防火牆允許 Cloudflare IP 範圍），從而隱藏真實伺服器位置。

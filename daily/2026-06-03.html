💡 kubectl 診斷 Pod 啟動失敗的完整流程

四步驟診斷流程：kubectl get pods 看狀態欄位 → kubectl describe pod 看 Events 與 Conditions → kubectl logs 看應用程式輸出 → kubectl get events --sort-by=.lastTimestamp 看叢集事件。從 Status/Events 可判斷是 ImagePullBackOff（鏡像無法拉取）、CrashLoopBackOff（Container 不斷重啟）、OOMKilled（記憶體超額）、還是 Pending（資源不足/PVC 未就緒）。

# 1. 列出所有 Pod 及狀態
kubectl get pods -A

# 2. 查看特定 Pod 的詳細事件與 Condition
kubectl describe pod <pod> -n <ns>

# 3. 看 application log
kubectl logs <pod> -n <ns> --tail=50
kubectl logs <pod> -n <ns> --previous  # CrashLoop 時看上一次的 log

# 4. 看叢集層級事件
kubectl get events --sort-by='.lastTimestamp' -n <ns>

💭 原理：describe 的 Events 區段記錄了 kubelet 的決策過程（拉鏡像→建立 Container→啟動→失敗→重啟循環），是除錯的第一站。

💡 k3s containerd 鏡像管理完整流程

k3s 使用 containerd 而非 Docker daemon，鏡像需手動匯入到 containerd 的 k8s.io namespace。完整流程：docker build（或 docker pull）→ docker save → sudo ctr -n k8s.io images import → kubectl set image 觸發更新。注意 imagePullPolicy: Never 時 digest 會被快取，必須用唯一 timestamp tag 強制更新。

# === 完整部署 Pipeline ===
TAG="stock-analysis:v$(date +%s)"

# 1. 建置新映像
sudo docker build --no-cache -t $TAG .

# 2. 匯出並匯入至 k3s containerd
sudo docker save $TAG | sudo ctr -n k8s.io images import -

# 3. 檢查是否成功匯入
sudo ctr -n k8s.io images ls | grep stock-analysis

# 4. 更新 Deployment 使用新 tag
sudo kubectl -n stock-analysis set image deploy/stock-analysis stock-analysis=$TAG

# 5. 驗證新 Pod 是否使用新映像
sudo kubectl get pods -n stock-analysis -o jsonpath='{.items[0].status.containerStatuses[0].imageID}'

💭 原理：k3s 不需 Docker registry；containerd 的 k8s.io namespace 是 k3s 專用，crictl 預設連不到。相同 tag 重新匯入不會更新 digest，這是很多人踩過的坑。

💡 查 OOM 紀錄

Linux OOM Killer 會在系統記憶體不足時終止 process。用 dmesg -T | grep -i oom 查詢被終止的 process 名稱、oom_score、以及觸發條件。在 K8s 環境中，Pod 的 memory limits 總和超過節點實體 RAM 時，OOM 會連鎖殺 Pod。

# 查 OOM 紀錄（需 root）
sudo dmesg -T | grep -i oom

# 只看最近的 OOM kill
sudo dmesg -T | grep -i "killed process"

# 即時監控記憶體用量
free -h                    # 看 available（不是 free）
cat /proc/meminfo | grep -E "(MemTotal|MemAvailable|MemFree)"

# Pod 層級查詢記憶體限制
kubectl describe pod <pod> -n <ns> | grep -A 2 Limits

💭 原理：OOM Killer 選 oom_score 最高的 process 終止（通常是最吃 RAM 的）。Linux 用閒置 RAM 做 page cache，所以 free 的數字低不代表記憶體不足，要看 available。

💡 Git 暫存管理：stash

當工作目錄有未 commit 的改動、需要切換 branch 時，用 git stash 暫存目前修改。回來後用 git stash pop 還原。stash 是 LIFO 堆疊，可用 git stash list 查看所有暫存，用 git stash apply stash@{n} 恢復特定暫存而不移除。

# 暫存目前改動（包含 staged 和 unstaged）
git stash

# 暫存並包含 untracked files
git stash -u

# 查看所有暫存清單
git stash list

# 還原最近一次暫存（同時從 list 移除）
git stash pop

# 恢復特定暫存但不移除
git stash apply stash@{1}

# 清除所有暫存
git stash clear

💭 原理：stash 本質是產生兩個臨時 commit（index 和 working tree），儲存在 .git/refs/stash 的 reflog 中。LIFO 順序確保最近暫存的先恢復。

💡 網路排查指令：curl、dig、ss、nc

四個排查指令各有用途：curl -v 看完整 HTTP request/response header（含 SSL/TLS handshake）；dig +short 快速查 DNS 解析結果；ss -tlnp 看 listening port 及佔用的 process；nc -zv 測特定 port 是否可連線（三向交握確認）。

# HTTP 診斷（看完整 header + 回應碼）
curl -v https://example.com
curl -s -o /dev/null -w '%{http_code}' https://example.com  # 只看狀態碼

# DNS 查詢
dig +short example.com
nslookup example.com

# 看本機 listening port
sudo ss -tlnp

# 測遠端 port 連線
nc -zv example.com 443
nc -zv 10.0.0.1 6443

💭 原理：dig 直接問 DNS 伺服器（跳過系統 cache），ss 讀取 /proc/net/tcp 等核心資料結構，nc -z 只做 TCP 三向交握後中斷連線（不傳資料）。

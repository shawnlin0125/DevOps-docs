💡 kubectl 診斷 Pod 啟動失敗的完整流程

Pod 卡在 Pending / CrashLoopBackOff / ImagePullBackOff 時，按順序執行四個 kubectl 指令就能找到根因。從 Status/Events 欄位判斷是 ImagePull 問題（ImagePullBackOff）、CrashLoop（應用錯誤，看 logs --previous）、OOMKilled（記憶體不足，Events 會有 OOMKilled）還是 Pending（資源不夠，Events 顯示 Insufficient cpu/memory）。

# 1. 看整體狀態
kubectl get pods -A

# 2. 看詳細事件（最關鍵，顯示所有 Error/Warning）
kubectl describe pod <pod> -n <ns>

# 3. 看應用日誌（CrashLoop 時加 -p 看 crash 前 log）
kubectl logs <pod> -n <ns> --previous

# 4. 看叢集層級事件（排序後更好讀）
kubectl get events -n <ns> --sort-by='.lastTimestamp'

💭 K8s 的故障排查遵循由淺入深原則：get pods 給宏觀、describe pod 給微觀（Events 欄位是精華）、logs 給應用層、events 給叢集層。跳過任一層都可能漏掉關鍵線索。

💡 Docker 多階段建置縮小 Image

多階段建置（Multi-stage build）讓你用一個 Dockerfile 同時包含 build 階段和 runtime 階段。Build 階段裝所有編譯工具（Go compiler / npm / gcc），runtime 階段只複製編譯好的 artifacts，大幅縮小最終 image。Go 可以 FROM scratch（靜態 binary 不需要 libc），Node.js 用 standalone output 或 alpine 基底。

# 多階段 Dockerfile 範例（Go）
FROM golang:1.22 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o myapp .

# Runtime stage
FROM alpine:3.19
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/myapp /usr/local/bin/
CMD ["myapp"]

# 查看 image 大小
docker images | grep myapp

💭 每個 FROM 都是一個獨立階段，只有最後一個 FROM 的內容會進最終 image。COPY --from=builder 可以跨階段複製檔案，build 階段的工具和中間檔案都不會殘留。

💡 查 OOM 紀錄：dmesg OOM Killer 診斷

當 Linux 系統記憶體不足時，OOM Killer 會挑選一個 oom_score 最高的行程殺掉釋放記憶體。用 dmesg 可以查看 OOM 事件記錄，確認哪個 process 被殺、吃了多少 RAM。在 K8s 環境中，Pod 的 memory limits 總和超過節點實體 RAM 時，OOM 會連鎖殺 Pod，這是常見的資源規劃失誤。

# 查 OOM 紀錄（-T 顯示人類可讀時間）
sudo dmesg -T | grep -i oom

# 更詳細的輸出（含 process name、RSS 用量）
sudo dmesg -T | grep -i "killed process"

# 即時監控記憶體壓力
journalctl -k | grep -i oom

💭 OOM Killer 不是隨機殺 process，而是根據 oom_score（綜合 RSS、swap、root 權限等計算）選分數最高的下手。K8s Pod 因為 cgroup 隔離，通常只看自己的 container 內行程，但節點層級 OOM 仍會影響所有 Pod。

💡 Git stash 暫存管理

當你在 branch A 開發到一半，需要緊急切到 branch B 修 bug 時，可以用 git stash 暫存目前工作區的改動（包含 staged 和 unstaged），讓工作目錄回到 clean 狀態。處理完 branch B 再回到 branch A 用 git stash pop 還原改動。Stash 是 LIFO（Last In First Out）的堆疊結構。

# 暫存目前改動（含 untracked 的話加 -u）
git stash
git stash push -m "WIP: feature X partial"

# 查看所有暫存
git stash list

# 還原最新暫存（並從 stash list 移除）
git stash pop

# 還原指定暫存（不移除，需手動 drop）
git stash apply stash@{2}

# 移除指定暫存
git stash drop stash@{2}

💭 stash 本質上是特殊類型的 commit，存在 refs/stash 上。stash@0 永遠是最新的暫存。用 stash push -m 加訊息可以幫助記憶每個暫存的內容，避免 pop 錯個。

💡 網路排查四指令：curl、dig、ss、nc

網路問題排查的四把瑞士刀：curl -v 看 HTTP 層的完整 request/response header（含 TLS handshake、redirect）、dig +short 快速查 DNS 解析結果（確認 domain 指向正確 IP）、ss -tlnp 看所有 TCP listening port（取代 netstat）、nc -zv 測試特定 port 是否可連線（比 telnet 輕量）。

# HTTP 除錯（看完整連線過程）
curl -v https://example.com

# DNS 查詢（+short 只顯示 IP）
dig +short example.com

# 看 listening port（t=TCP, l=listening, n=numeric, p=process）
ss -tlnp

# 測試 port 通不通（z=zero-I/O scan, v=verbose）
nc -zv 192.168.1.1 443

💭 這四指令對應 OSI 四層：dig（DNS/應用層）、curl（HTTP/應用層）、nc（傳輸層）、ss（傳輸層+系統層）。由上而下排查：先確認 DNS 對不對，再確認服務有無 listen，最後測連線通不通。

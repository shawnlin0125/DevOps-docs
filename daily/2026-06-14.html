💡 kubectl 診斷 Pod 啟動失敗的完整流程

kubectl get pods 看狀態欄位 → kubectl describe pod 看 Events/Conditions → kubectl logs 看容器輸出 → kubectl get events 看集群事件。從 Status 能快速判斷：ImagePullBackOff（鏡像問題）、CrashLoopBackOff（程式崩潰）、OOMKilled（記憶體不足）、Pending（資源不夠排程）。

kubectl get pods -n <ns>
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> --tail=50
kubectl get events -n <ns> --sort-by='.lastTimestamp'

💭 原理：K8s 的 Pod lifecycle 分為 Pending→Running→Succeeded/Failed。describe 的 Conditions 列出 scheduler/network/volume readiness，Events 列出 kubelet/pull/health check 的完整時間線。logs 僅在容器啟動成功後才有內容（CrashLoop 用 --previous 看上次 crash 的日誌）。

💡 Docker 多階段建置縮小 Image

Dockerfile 中用多個 FROM 區分 build stage 和 runtime stage。build stage 安裝所有建置工具（gcc、npm、go mod），runtime stage 只複製建置好的 artifacts。Go 可 FROM scratch（靜態 binary ~15MB），Node.js 用 standalone output。用 docker images | grep 查看各層大小。

# Go multi-stage example
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o app .

FROM scratch
COPY --from=builder /app/app /
ENTRYPOINT ["/app"]

💭 原理：Docker image 由唯讀 layers 疊加而成，每層增加 image 大小。多階段建置利用兩個 FROM 建立不同的 image，只有最終 stage 的 layers 被保留。build stage 的 layers 在 --from 複製後就捨棄，不會計入最終 image。

💡 Linux 資源監控三指令：uptime / free / df

uptime 看 load average（1/5/15 分鐘的 CPU 排隊數）→ load > 核心數表示 CPU 瓶頸。free -h 的 available 欄位才是真實可用記憶體（free 低不代表不夠，因為 Linux 拿閒置 RAM 做 disk cache）。df -h / 看磁碟使用率，通常設 80% 告警、90% 緊急。

uptime
# load average: 2.50, 1.80, 1.20  (4 cores → >4 is overloading)
free -h
#              total  used  free  shared  buff/cache  available
# Mem:        7.6Gi  2.1Gi 1.2Gi  120Mi    4.3Gi      5.1Gi
df -h /
# Filesystem  Size  Used  Avail  Use%  Mounted on
# /dev/vda1    78G   52G    23G   70%  /

💭 原理：Linux kernel 的記憶體管理預設把未使用的 RAM 用來做 page cache（buff/cache），加速檔案 I/O。available 是 kernel 估算的可回收記憶體（cache + free + 可 swap 的部分）。df 看到的是 filesystem 層級，不包含 inode 耗盡（df -i 查）。

💡 GitHub PR 流程：gh CLI

完整 PR 流程：git checkout -b feature/xxx → commit → git push -u origin feature/xxx → gh pr create --title "... " --body "..." → 等 review → gh pr merge --squash（或 --rebase）→ git checkout main && git pull。gh pr view 可 terminal 內看 PR 內容，gh pr checkout 可快速切到他人 PR。

git checkout -b feature/my-feature
git add . && git commit -m "feat: add my feature"
git push -u origin feature/my-feature
gh pr create --title "feat: add my feature" --body "Closes #123"
# CI runs...
gh pr merge --squash
git checkout main && git pull

💭 原理：gh CLI 透過 GitHub REST/GraphQL API 操作。gh pr create 推送 head branch 到 GitHub，自動設定 base = main（目前 branch 的 base）。--squash 將 feature branch 的所有 commits 壓成一個 commit 合併到 base branch，保持 main 歷史整潔。

💡 Helm 常用操作：生命週期管理

helm list -A 列出所有 release、helm history 看版本歷史、helm rollback 退回舊版、helm get values -n 查看目前生效的 values、helm template --debug 預覽渲染結果。rollback 基於 revision 機制可快速恢復到任何歷史版本。

helm list -A
helm history my-release -n default
helm rollback my-release 2 -n default
helm get values my-release -n default --all
helm template my-app ./chart -f values/prod.yaml --debug
helm diff upgrade my-app ./chart -f values/prod.yaml

💭 原理：Helm 每個 upgrade/install 產生一個 revision，K8s manifest 的 annotation 記錄了對應的 revision number。rollback 本質是 helm upgrade --revision N，不是 undo 而是重新應用舊版本的 manifest。--wait 確保 rollout 就緒後才回傳成功。

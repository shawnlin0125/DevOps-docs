💡 kubectl 進 Pod 內排查：exec + 常用內部指令

kubectl exec -it <pod> -n <ns> -- sh 讓你進入容器內部互動式排查，不需要 ssh 或直接存取 node。進入 Pod 後常用指令：env | grep -i 確認環境變數（檢查 Secret 或 ConfigMap 是否成功掛載）、nc -zv <svc> <port> 測試 Pod 能否連到其他 Service（比 ping 更可靠，因為 K8s 網路層不同）、cat /etc/resolv.conf 確認 DNS 設定（看是否使用 kube-dns / CoreDNS）。

# === 進入 Pod 互動式 shell ===
kubectl exec -it <pod> -n <ns> -- sh          # 大部分容器用 sh
kubectl exec -it <pod> -n <ns> -- bash        # 若有 bash 則更友善

# === 常用的 inside-Pod 診斷指令 ===
env | grep -i PASSWORD                         # 確認環境變數（Secret 掛載）
env | grep -i DATABASE                         # 檢查資料庫連線變數
nc -zv redis-service 6379                      # 測試 TCP 連線（Redis）
nc -zv postgres-service 5432                   # 測試 TCP 連線（PostgreSQL）
cat /etc/resolv.conf                           # 確認 DNS 伺服器
cat /etc/hosts                                 # 確認 hosts 對應
ps aux                                         # 看容器內有哪些 process
df -h /                                        # 看容器內磁碟空間（ephemeral storage）

# === 非互動式（單一指令）===
kubectl exec <pod> -n <ns> -- env             # 直接看所有環境變數
kubectl exec <pod> -n <ns> -- cat /etc/resolv.conf

💭 原理：kubectl exec 透過 K8s API Server 向 kubelet 發起請求，kubelet 再透過 container runtime（containerd/CRI-O）執行指定指令。注意容器內通常沒有 systemd、network tools 等，所以 nc（netcat）和 env 是最輕量也最可能有的工具。

💡 k3s containerd 鏡像管理完整流程

k3s 使用 containerd 而非 Docker daemon 來管理容器。部署自建鏡像的 SOP：docker build 產生 image → docker save 將 image 匯出為 tar → k3s ctr images import 匯入到 containerd → kubectl apply 或 kubectl set image 更新 deployment。由於 imagePullPolicy: Never 會快取舊 digest，因此**必須使用唯一 tag**（如 timestamp）來確保使用新鏡像。

# === 完整部署流程 ===
# 1. Build image（強制 clean rebuild）
rm -rf out .next
npx next build
docker build --no-cache -t my-app:v$(date +%s) .

# 2. 匯入 k3s containerd
docker save my-app:v1234567890 | sudo k3s ctr images import -

# 3. 更新 deployment
kubectl -n my-ns set image deploy/my-app my-app=my-app:v1234567890

# === 驗證 ===
sudo k3s ctr images ls | grep my-app           # 確認 image 存在於 containerd
kubectl get pods -o jsonpath='{.items[0].status.containerStatuses[0].imageID}'

# === 注意：k3s 的 containerd namespace 是 k8s.io ===
sudo ctr -n k8s.io images ls | grep my-app     # 明確指定 namespace
sudo ctr -n k8s.io images rm my-app:v1234567890  # 刪除舊 image

💭 原理：k3s 內建 containerd，預設使用 k8s.io namespace 區隔 K8s 鏡像與系統鏡像。docker save 匯出的是 OCI tar 格式，ctr images import 將其解包存入 containerd 的 content store。同 tag 重複 import 不會覆蓋 digest，所以 timestamp tag 是必要 workaround。

💡 Linux 資源監控三指令：uptime、free、df

伺服器資源診斷的第一步是看三個數字：uptime 顯示 load average（1/5/15 分鐘的平均排隊長度），若超過 CPU 核心數表示 CPU 瓶頸；free -h 看記憶體用量，**重點看 available 欄位**不是 free（Linux 拿閒置 RAM 做 cache 所以 free 看起來很低）；df -h / 看根目錄磁碟使用率，超過 80% 通常就需要清理。

# === 系統負載 ===
uptime                                    # 結果範例：load average: 2.50, 1.80, 1.20
nproc                                     # 看 CPU 核心數（判斷 load 是否超標）
top -bn1 | grep "CPU"                     # 看 CPU 使用率細項（us/sy/id/wa）

# === 記憶體用量 ===
free -h                                   # 看 available（不是 free！）
cat /proc/meminfo | grep MemAvailable     # 原始數值（KB）
vmstat 1 3                                # 看 swapping（si/so 欄位）

# === 磁碟用量 ===
df -h /                                   # 根目錄使用率
df -h /var/lib/docker                     # Docker 資料目錄（常爆滿）
du -sh /var/log/                          # log 總大小
du -sh /var/log/* | sort -rh | head -10   # 看哪些 log 最大

# === 診斷流程 ===
# load 高但 CPU idle 也高 → I/O wait（iowait 高 → 磁碟瓶頸）
# available RAM 接近 0 → OOM 風險
# Diskspace > 85% → 清理 log 或擴充 PV

💭 原理：load average 是 Linux 核心的 task 排隊統計——包含 running + uninterruptible sleep（後者即 I/O wait）。這就是為什麼 load 高但 CPU idle 也高時，通常是磁碟 I/O 瓶頸。free 的 available 是核心對「可分配的記憶體」的估算，包含 page cache + slab reclaimable。

💡 Git 復原操作：reset、restore、reflog

Git 提供了幾種不同程度的復原操作：git reset --soft HEAD~1 退回上一個 commit 但保留所有變更在 staging area（可用來重新 commit）；git restore <file> 丟棄工作區的未暫存改動（等於 checkout file 的新版）；git restore --staged <file> 將檔案移出 staging area 但不改內容。如果 commit 被誤刪了，git reflog 可以查看所有 HEAD 移動記錄並救回。

# === commit 復原 ===
git reset --soft HEAD~1                   # 退回 commit，保留 staged（重新 commit）
git reset --mixed HEAD~1                  # 退回 commit，保留工作區（unstaged）
git reset --hard HEAD~1                   # ⚠️ 退回 commit，丟棄所有改動（不可回復？可 reflog）

# === 工作區復原 ===
git restore <file>                         # 丟棄 uncommitted 改動
git restore --staged <file>               # 取消 git add，檔案內容不變
git checkout -- <file>                    # 舊式做法（功能同 git restore）

# === 救回誤刪的 commit ===
git reflog                                # 看所有 HEAD 移動記錄
git reset --hard HEAD@{2}                 # 回到 reflog 中的某個位置
git checkout <commit-hash> -b rescue-branch  # 在誤刪的 commit 開 branch

# === 實用情境 ===
# 情境 1：commit 了但訊息打錯 → git reset --soft HEAD~1 → git commit -m "正確訊息"
# 情境 2：git add 了不該加的檔案 → git restore --staged <file>
# 情境 3：git reset --hard 後悔了 → git reflog → git reset --hard @{1}

💭 原理：Git 的 commit 一旦被建立其實不會立刻消失（會被 GC 回收）。git reset 只是移動 HEAD 指標和 branch 指針，原 commit 仍存在 object database 中約 30 天（除非 git gc --prune）。reflog 是 Git 的本地操作日誌，記錄了 HEAD 的每次變更，是「後悔藥」的基礎。

💡 Helm 常用操作：list、history、rollback、get values

Helm 是 K8s 的套件管理工具，管理 K8s 應用的部署生命週期。helm list -A 列出所有 namespace 的 release；helm history <release> -n <ns> 查看某個 release 的版本歷史（每次 upgrade 就是一個新版本）；helm rollback <release> <rev> -n <ns> 快速退回指定版本（例如新版本 crash 時秒退）；helm get values <release> -n <ns> 看當前 release 使用的 values，--all 包含 chart 預設值。

# === Release 生命週期 ===
helm list -A                              # 列出所有 release（跨 namespace）
helm list -n <ns>                          # 列出指定 namespace
helm status <release> -n <ns>             # 看 release 狀態（deployed/failed）

# === 版本管理 ===
helm history <release> -n <ns>            # 看版本歷史（REVISION 編號）
helm rollback <release> 2 -n <ns>         # 退回第 2 版
helm rollback <release> 2 --wait -n <ns>  # 等 rollback 完成後才回傳

# === 除錯與檢視 ===
helm get values <release> -n <ns>         # 看使用者設定的 values
helm get values <release> -n <ns> --all   # 看所有 values（含 chart 內建預設）
helm get manifest <release> -n <ns>       # 看實際部署的 K8s YAML

# === 升級與 diff ===
helm upgrade <release> ./chart -f values/prod.yaml -n <ns>
helm diff upgrade <release> ./chart -f values/prod.yaml -n <ns>  # 先看 diff（需 helm-diff plugin）

# === 解除安裝 ===
helm uninstall <release> -n <ns>          # 刪除 release（含所有 K8s 資源）

💭 原理：Helm 將 chart template 與 values 合併渲染為最終 K8s manifest，然後透過 kubectl apply 部署。每次 helm upgrade 會建立一個新 revision（儲存在 K8s Secret 中），所以 rollback 只是重新應用舊 revision 的 manifest。

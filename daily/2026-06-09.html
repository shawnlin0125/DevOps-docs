💡 kubectl 看資源使用：top + describe node Allocated

三個指令對應不同監控視角：kubectl top nodes 看各節點即時 CPU/Memory 用量、kubectl top pods -A 看每個 Pod 的即時資源消耗、kubectl describe node <node> | grep -A 8 Allocated 看 scheduler 視角的 request/limit 佔比。即時用量高不一定代表資源不夠——scheduler 只看 request 總和來決定能否排程 Pod。

# 節點即時資源用量
kubectl top nodes

# 所有 Pod 即時資源用量
kubectl top pods -A

# 節點資源分配率（Scheduler 視角）
kubectl describe node <node-name> | grep -A 8 "Allocated resources"

💭 top 是即時用量（current usage），describe node Allocated 顯示 Pod request/limit 加總（scheduler 排程參考），兩者可能差異很大——應用可能 request 了 2GB 但實際只用 200MB。

💡 kubectl exec 進 Pod 內排查

用 kubectl exec -it <pod> -n <ns> -- sh 進入容器內部進行診斷。常用 inside-pod 指令：env | grep -i 確認環境變數是否正確傳入、nc -zv <svc> <port> 測試連線到其他 Service 的 port 是否通順、cat /etc/resolv.conf 確認 DNS 設定與 nameserver。

# 進入 Pod 容器
kubectl exec -it <pod> -n <namespace> -- sh

# 檢查環境變數（如 DATABASE_URL、API_KEY）
env | grep -i DB

# 測試連線到其他 Service
nc -zv <service-name> 5432

# 確認 Pod 內 DNS 設定
cat /etc/resolv.conf

💭 容器內診斷可以避開集群網路抽象層，直接驗證容器實例是否能正確解析服務名稱、讀取設定、連接到後端。nc -zv 非侵入式測試連線，是 container 內診斷的第一把刀。

💡 systemd 服務管理：三指令診斷流程

Linux 服務管理三步驟：systemctl list-units --state=failed 快速找出所有異常服務（不必一個個手查）；journalctl -u <service> -n 50 --no-pager 看該服務最近 50 行 log（-u 指定 unit，-n 指定行數）；systemctl daemon-reload 修改 .service unit file 後重新載入。

# 列出所有失敗的服務
systemctl list-units --state=failed

# 查看特定服務最近 log
journalctl -u my-app.service -n 50 --no-pager

# 修改 unit file 後重新載入
sudo systemctl daemon-reload
sudo systemctl restart my-app.service

💭 systemctl list-units 是 DevOps 的「健康儀表板」，幾秒內掃完全部服務。journalctl 的 -u 過濾比 grep 更精準且不浪費 CPU。daemon-reload 一定要在改完 unit file 後執行，否則 systemd 仍用舊設定。

💡 Git 復原操作三兄弟：reset、restore、reflog

三個指令覆蓋不同復原場景：git reset --soft HEAD~1 退回上一個 commit 但保留檔案變更在 staged 狀態（安全撤回 commit）；git restore <file> 丟棄工作區的未提交改動（回到 HEAD 版本）；git reflog 看所有 HEAD 移動記錄——不小心 hard reset 或刪錯 branch 時可找回遺失的 commit。

# 退回上一個 commit，變更保留在 staging
git reset --soft HEAD~1

# 丟棄單一檔案的工作區改動
git restore myfile.go

# 查看所有 HEAD 移動記錄（救回誤刪 commit）
git reflog
# 找到 SHA 後：git checkout <sha> 或 git cherry-pick <sha>

💭 git reset --soft 是最安全的「後悔藥」，不丟檔案只撤回 commit；git restore 取代了老式的 git checkout -- file；reflog 是 Git 的最後防線——只要曾在本機 commit 過，reflog 就有記錄（有效期預設 90 天）。

💡 Helm 常用操作：部署生命週期管理

Helm 是 K8s 套件管理器，常用維運指令：helm list -A 列出所有 namespace 的 release（已部署的 chart 實例）；helm history <release> -n <ns> 查看版本演進記錄；helm rollback <release> <rev> -n <ns> 回退到指定版本；helm get values <release> -n <ns> 查看目前生效的 values 設定（比翻 values.yaml 快）。

# 查看所有已部署的 release
helm list -A

# 查看特定 release 的版本歷史
helm history my-app -n production

# 回退到上一版（或指定 revision）
helm rollback my-app -n production
helm rollback my-app 3 -n production

# 查看目前使用的 values 設定
helm get values my-app -n production

💭 Helm 的 revision 從 1 開始遞增，每次 upgrade 或 rollback 都產生新 revision。rollback 本質是建立一個指向舊 revision 的「新」revision——所以 rollback 後 revision 數繼續增加，不會減少。回退後可用 helm history 確認目前生效的 revision。

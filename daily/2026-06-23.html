💡 kubectl exec 進 Pod 內排查

用 kubectl exec -it <pod> -n <ns> -- sh 進入容器互動排查。進到 Pod 內部後常用三招診斷：env | grep -i 確認環境變數是否正確注入（ConfigMap/Secret 生效與否）、nc -zv <svc> <port> 測試 Pod 能否連到其他 Service（網路策略和 DNS 解析問題）、cat /etc/resolv.conf 確認容器內 DNS 設定（search domain 和 nameserver 是否正確）。-- 之後的參數是要在容器內執行的指令。若要複製檔案進出，用 kubectl cp。

# 進入容器互動 shell（用 sh，很多最小鏡像無 bash）
kubectl exec -it <pod-name> -n <ns> -- sh

# 容器內常用診斷
env | grep -i DB_HOST          # 確認環境變數
nc -zv myservice.default 5432  # 測試 TCP 連線
cat /etc/resolv.conf            # 檢查 DNS 設定
wget -qO- http://service:8080/health  # HTTP 健康檢查

# 複製檔案
kubectl cp <pod>:<path> ./local <ns>  # 從 Pod 複製出來
kubectl cp ./local <pod>:<path> <ns>  # 複製進 Pod

# 直接執行單一指令不回互動
kubectl exec <pod> -n <ns> -- ls /app

💭 原理：kubectl exec 透過 kube-apiserver 代理到 kubelet 的 runtime exec API，本質是給容器內 PID 1 行程所屬 Namespace 中的一個新行程。容器內能看到的進程和網路 namespace 與主容器相同。-- 是 kubectl 參數終止標記，後面的都是容器內指令。

💡 Linux 資源監控三指令：uptime / free / df

系統資源快速診斷三指令：uptime 顯示 load average（1/5/15 分鐘的平均行程排隊數），對比 CPU 核心數來判斷是否超載；free -h 看記憶體使用，重點看 available 欄位（不是 free），available 包含可回收的 cache/buffer；df -h / 看磁碟使用率。三者的共同原則是：Linux 拿閒置 RAM 做 page cache 很正常，free 低不代表記憶體不夠，available 低才是真的壓力大。

# 1. CPU 負載：load average 對比核心數
uptime
# 08:30:00 up 30 days, 2:15,  load average: 2.50, 1.80, 1.20
# → 如果 4 核心，load 2.5 OK；如果 2 核心，load 2.5 = 排隊中

nproc  # 看有幾顆 CPU

# 2. 記憶體：看 available 不是 free
free -h
#               total  used  free  shared  buff/cache  available
# Mem:          31Gi   12Gi  2Gi   1Gi     17Gi        18Gi
# → free=2Gi 但 available=18Gi，很多 RAM 被 cache 佔用但可回收

# 3. 磁碟：使用率 + inode
df -h /       # 看磁碟使用率
df -i /       # 看 inode 使用率（inode 滿了也無法寫入）
du -sh /var/log  # 看目錄大小

💭 原理：Linux kernel 盡量用閒置記憶體做 disk cache 提升 I/O 效能（page cache + dentry cache + buffer cache）。available 是 kernel 估算的「在不觸發 swap 的前提下可分配給新程式的記憶體量」，比 free 更準確。load average > CPU 核心數表示有行程在等待 CPU 時間片。

💡 Git 復原操作：reset / restore / reflog

三種常見的 Git 後悔藥：git reset --soft HEAD~1 退回最近一次 commit 但保留所有變更在 staging area，適合「commit 內容不對要重做」的情境；git restore <file> 丟棄工作區的未暫存改動，回到上一次 commit 的狀態（相當於 checkout -- 的現代替代）；git reflog 紀錄所有 HEAD 移動的歷史（含 reset、rebase、amendment 等操作），是救回誤刪 commit 的最後防線。reflog 預設保留 90 天。

# 1. 退回最近一次 commit（保留變更在 staging）
git reset --soft HEAD~1
# → HEAD 退到前一個 commit，工作區和 staging 保持不變
# 可用來「commit 錯東西要重新整理」

# 2. 退回並保留在工作區（未 staged）
git reset --mixed HEAD~1  # 預設模式

# 3. 丟棄工作區的變更
git restore <file>          # 丟棄某個檔案
git restore .                # 丟棄所有檔案

# 4. 反轉某個 commit（建立新的反向 commit）
git revert <commit-hash>   # 安全地復原已推送的 commit

# 5. 救回誤刪的 commit
git reflog
# 找 commit-hash 後：git checkout <hash>
# 或 git cherry-pick <hash> 撿回來

💭 原理：reset 移動 HEAD 和 branch 指標，--soft 只移指標不碰 index/working tree，--mixed 移指標 + 重置 index，--hard 移指標 + 重置 index + 重置 working tree。reflog 是 Git 本地的 HEAD 移動日誌（存在 .git/logs/HEAD），不被 push/pull 傳輸，是你的專屬救援工具。

💡 Git 暫存管理：stash 技巧

切 branch 前工作區有未 commit 的變更時，用 git stash 暫存所有追蹤檔案的改動，還原乾淨的工作區。常用指令：git stash 暫存（只暫存 tracked files，加 -u 才包含 untracked files）、git stash pop 還原最近一次暫存並從 stash list 中移除、git stash list 看所有暫存項目、git stash apply stash@{2} 套用特定暫存但不移除項目。stash list 是 LIFO（後進先出），最新 stash 在最上面。

# 暫存目前所有改動（不含 untracked）
git stash
git stash push -m "WIP: feature X in progress"

# 暫存包含 untracked files
git stash -u

# 查看暫存列表
git stash list
# stash@{0}: On feature/x: WIP: feature X
# stash@{1}: On main: WIP: fix bug Y

# 還原最近暫存並從 list 移除
git stash pop

# 套用特定暫存但不移除
git stash apply stash@{2}

# 刪除特定暫存（不用套用）
git stash drop stash@{1}

# 清空所有暫存
git stash clear

💭 原理：git stash 本質上建立兩個特殊的 commit-like 物件（一個記錄 staged 變更的 index commit，一個記錄 working tree 變更的 WIP commit），儲存在 .git/refs/stash 中，形成一個 stash stack。因為是 commit-like 物件，所以跨 branch 套用 stash 時可能發生衝突（需手動解決）。

💡 Helm 常用操作：生命週期管理

Helm 是 Kubernetes 的套件管理器，核心操作圍繞 release 生命週期。用 helm list -A 列出所有已部署的 release（含 deploy/revision/status）；helm history <release> -n <ns> 看某個 release 的版本歷史（每次 helm upgrade 都會產生一個新 revision）；helm rollback <release> <rev> -n <ns> 退回到指定版本，適合升級失敗時快速回退；helm get values <release> -n <ns> 看目前 release 實際生效的 values。--reuse-values 參數會重用上次部署的 values（但不跟最新的 chart 預設值 merge，可能有意料外的行為）。

# 列出所有 release（含 namespace、版本、狀態）
helm list -A

# 查看特定 release 的版本歷史
helm history my-release -n my-namespace
# REVISION  STATUS      CHART          APP VERSION  DESCRIPTION
# 1         deployed    my-app-1.0.0   1.0.0        Install complete
# 2         superseded  my-app-1.1.0   1.1.0        Upgrade complete
# 3         failed      my-app-1.1.0   1.1.0        Upgrade failed ← 當前版本

# 退回指定版本（最常見的復原操作）
helm rollback my-release 1 -n my-namespace

# 查看 release 目前實際使用的 values
helm get values my-release -n my-namespace

# 升級（注意 values 管理）
helm upgrade my-release ./chart -n my-namespace -f values/prod.yaml

# 除錯：看最終渲染的 YAML（不實際部署）
helm template my-release ./chart -f values/prod.yaml --debug

💭 原理：每個 helm upgrade/install 都會在目標 namespace 中建立一個 Secret（類型為 helm.sh/release.v1），儲存 release metadata、manifest 和 values。helm rollback 本質上是將前一個版本的 values + manifest 重新 apply 到集群。helm list -A 實質上是在所有 namespace 中查詢這些 Secret。

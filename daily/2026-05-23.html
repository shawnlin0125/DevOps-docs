💡 kubectl 診斷 Pod 啟動失敗完整流程 — describe → logs → events 三步驟

Pod 起不來時的三步驟診斷：kubectl get pods 看 Status 欄位（Running/Pending/CrashLoopBackOff/ImagePullBackOff）、kubectl describe pod 看 Events（最下面，通常直接寫原因）、kubectl logs 看容器輸出。從 Status + Events 可快速判斷是 ImagePull、CrashLoop、OOMKilled 還是 Pending（資源不夠）。

# 第一步：看 Pod 狀態（STATUS 欄位是關鍵）
kubectl get pods -n production

# 第二步：看 Events（describe 最下面幾行通常就是原因）
kubectl describe pod my-app-xxx -n production | tail -20

# 第三步：看容器 log（CrashLoop 時加 --previous 看上次崩潰的 log）
kubectl logs my-app-xxx -n production
kubectl logs my-app-xxx -n production --previous

# 看全叢集最近 Events（有時 Pod 被 evicted 要去 events 找）
kubectl get events -A --sort-by='.lastTimestamp' | tail -20

💭 原理：kubectl describe pod 讀的是 Pod object 的 Status.Conditions 和 Events 列表（存在 etcd 中），Events 由 kubelet 在 Pod 生命週期變動時寫入。logs 讀的是容器 stdout/stderr，CrashLoop 時容器已死，需 --previous 才能看到上次的 log（kubelet 會保留最後一個 terminated container 的 log）。

💡 Git 復原操作 — reset --soft、git restore、git reflog 救回誤刪 commit

三種常見復原場景：git reset --soft HEAD~1 退回上次 commit 但保留 staged 內容（改 commit message 用）、git restore <file> 丟棄工作區改動、git reflog 看所有 HEAD 移動記錄（可救回誤刪的 commit，只要知道 hash 就能 checkout 回來）。

# 退回上次 commit，保留所有改動在 staged（改 message 或補檔用）
git reset --soft HEAD~1

# 丟棄某檔的工作區改動（還原到上次 commit 的版本）
git restore path/to/file

# 丟棄所有工作區改動
git restore .

# 查看 HEAD 所有移動記錄（救命指令！）
git reflog
# 輸出範例：
# abc1234 HEAD@{0}: commit: add feature X
# def5678 HEAD@{1}: commit: fix bug Y    ← 誤刪的 commit 也在這

# 救回誤刪的 commit（從 reflog 找到 hash 後）
git checkout def5678    # 或 git reset --hard def5678

# 取消 staged（把 staged 檔案移回 working）
git restore --staged path/to/file

💭 原理：Git 的 reflog 記錄了 HEAD 的每一次移動（commit、reset、checkout、merge），即使 commit 被 reset 掉、branch 被刪除、甚至做了 garbage collection，只要 reflog 還在（預設保留 90 天）就能找回來。reset --soft 只移動 HEAD 指標不動 index 和 working tree，所以改動完整保留。

💡 Helm 常用操作 — list / history / rollback / get values

Helm 日常運維四大指令：helm list -A 看所有 release 和狀態、helm history <release> -n <ns> 看部署版本歷史、helm rollback <release> <rev> -n <ns> 退回指定版本（緊急回滾用）、helm get values <release> -n <ns> 看目前生效的 values（確認覆蓋結果）。

# 看所有 namespace 的 release
helm list -A

# 看某 release 的部署歷史（STATUS 欄位看哪版 deployed/failed）
helm history my-app -n production

# 回滾到第 3 版（緊急時比手動修 YAML 快）
helm rollback my-app 3 -n production

# 查看目前生效的 values（確認 --set 或 values 檔有被正確合併）
helm get values my-app -n production

# 查看完整 manifest（含所有 template 渲染後的結果）
helm get manifest my-app -n production

💭 原理：Helm 把每次 install/upgrade 存成一個 Release Secret（或 ConfigMap，取決於 Helm 版本），內含 rendered manifest 和 values。rollback 就是取前一個 release secret 的內容重新部署。history 列出所有 release secret 的版本號、狀態、更新時間。

💡 網路排查四指令 — curl -v / dig / ss / nc

Linux 網路排查工具箱：curl -v http://host 看完整 HTTP request/response header（TLS handshake、redirect 都看得到）、dig +short domain 做 DNS 查詢（比 nslookup 資訊更完整）、ss -tlnp 看所有 listening TCP port 和對應 process（取代舊 netstat）、nc -zv host port 測試 port 通不通（純 TCP connect，不發 HTTP）。

# 看完整 HTTP 互動（header、TLS、redirect 全程）
curl -v https://example.com

# DNS 查詢（+short 只顯示結果，不加參數看完整 NS/SOA 等）
dig +short example.com
dig example.com

# 看誰在監聽哪些 port（-t tcp, -l listening, -n numeric, -p process）
ss -tlnp
# 輸出：LISTEN  0  128  *:8080  *:*  users:(("nginx",pid=1234,fd=6))

# 測 port 通不通（-z 不發資料, -v 顯示結果）
nc -zv example.com 443
# 成功：Connection to example.com 443 port [tcp/https] succeeded!
# 失敗：nc: connect to example.com port 443 (tcp) failed: Connection refused

# 看網路介面和 IP
ip addr show  # 取代 ifconfig

💭 原理：ss 直接讀 /proc/net/tcp 等 kernel socket table（netlink socket），比 netstat 快（尤其是大量連線時）。nc -z 只做 TCP 三次握手（SYN → SYN-ACK → RST），不對應用層發任何資料，適合純連通性測試。dig 直接發 DNS query 到 resolver（不走 nsswitch/hosts 快取）。

💡 systemd 服務管理 — failed units、journalctl、daemon-reload

systemd 服務日常管理：systemctl list-units --state=failed 快速找出掛掉的服務、journalctl -u <service> -n 50 --no-pager 看服務最近 log（-n 控制行數、--no-pager 避免進入互動模式）、systemctl daemon-reload 在改完 unit file 後重載設定（不做會導致改動不生效）。

# 找出所有掛掉的服務
systemctl list-units --state=failed

# 看某服務最近 50 行 log
journalctl -u nginx -n 50 --no-pager

# 即時追蹤 log（類似 tail -f）
journalctl -u nginx -f

# 看特定時間範圍的 log
journalctl -u nginx --since "2026-05-23 02:00" --until "2026-05-23 03:00"

# 改完 unit file 後必須重載
sudo systemctl daemon-reload

# 重啟服務並確認狀態
sudo systemctl restart nginx && systemctl status nginx

# 開機自動啟動
sudo systemctl enable nginx

💭 原理：systemd 把 unit file 讀進記憶體後會快取，改完 /etc/systemd/system/xxx.service 後記憶體中的版本不會自動更新 — daemon-reload 強制重新解析所有 unit file。journalctl 讀的是 systemd-journald 的二進位 log（/var/log/journal/），比傳統 syslog 多了結構化欄位（_PID、_UID、UNIT 等），可以用 --output=json-pretty 看完整 metadata。

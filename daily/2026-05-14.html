1. Plugin-Hub 架構簡化：從 Pool 到統一代理

對 plugin-hub 進行了一次重大架構簡化——移除「Pool」概念（proxy-high / proxy-normal），改為統一的單一 Deployment 代理模型。核心思想：當一個 plugin 被啟用，它應該在所有代理實例上都可用，無需手動指派到特定部署。

1.1 變更前後的架構對比

維度舊架構 (Pool)新架構 (Unified)
代理 Deployment2 個（proxy-high + proxy-normal）1 個（ticket-proxy）
Plugin 指派手動選擇部署池（dashboard dropdown）啟用即全局生效（無指派）
ConfigMap3 個（assignments, proxy-high-plugins, proxy-normal-plugins）1 個（proxy-plugins）
反向代理路由依 pool 多路分流單一 proxy → ticket-proxy 服務
觀念模型容量分池、手動指派總機模式（switchboard），啟用即上線

1.2 程式碼變更

handler.go 重寫：

  • 移除 AssignmentStore、Proxies map、pool-based 路由邏輯（刪除 ~268 行）
  • 新增 /api/load-plugins 端點：回傳以逗號分隔的已啟用 vendor ID 清單（供 proxy pod 經由 ConfigMap 讀取）
  • ProxyToVendor 改為檢查 registry 的 enabled 狀態，而非查詢 assignment map
  • 反向代理簡化：所有 /api/v1/{vendor}/* 請求統一路由到 ticket-proxy 服務
// 新邏輯：檢查 enabled，而非 assignment
func (s *Server) ProxyToVendor(w http.ResponseWriter, r *http.Request) {
    vendorID := chi.URLParam(r, "vendor")
    if !s.Registry.IsEnabled(vendorID) {
        http.Error(w, "vendor not enabled", 404)
        return
    }
    // 單一反向代理到 ticket-proxy
    s.proxy.ServeHTTP(w, r)
}

新增 EnabledVendors() 方法（registry.go）：

func (r *Registry) EnabledVendors() []string {
    var ids []string
    for _, p := range r.plugins {
        if p.Enabled {
            ids = append(ids, p.ID)
        }
    }
    return ids
}

Dashboard 簡化：移除部署選擇下拉選單，改為顯示 LOAD_PLUGINS = ticketmaster 資訊列。

1.3 K8s 清單變更

  • 刪除 deploy-proxy-high.yaml、deploy-proxy-normal.yaml
  • 新建 deploy-proxy.yaml：單一 Deployment (2 replicas)、單一 ConfigMap (proxy-plugins)、單一 Service
  • 更新 deploy-admin.yaml：移除 PROXY_SVC_PROXY_HIGH/NORMAL 環境變數和 hub-assignments ConfigMap 掛載
💡 架構思維：當所有代理實例功能相同時，不需要「池」的概念。Hub 只做兩件事：(1) 管理 plugin 的啟用/停用狀態，(2) 作為反向代理總機將請求路由到下游。這讓部署模型從「N 種部署 × 手動指派」簡化為「1 種部署 × 自動加載」。

2. Cron Job 除錯：DevOps Daily Learning Doc 排程修正

發現並修復了一個關鍵 bug：每日 03:00 執行的「DevOps Daily Learning Doc」cron job 始終回傳 [SILENT]，導致從未實際產生學習頁面。

2.1 問題根因

Cron job 在凌晨 3:00 執行時，prompt 指示搜尋「今天的」對話。但在 03:00 還沒有當天的任何對話，導致永遠找不到內容，直接輸出 [SILENT] 並跳過。

🐛 Bug：排程任務的時間語意錯誤——在一天的開始搜尋「今天」的內容是不可能的。必須搜尋「昨天」的內容。

2.2 修正內容

  1. Prompt 修正：將「搜尋今天的對話」改為「搜尋昨天（執行日期減一天）的對話」
  2. Delivery 目標變更：從 local（無通知）改為 telegram:-1003966564424:652（#schedule topic），確保完成通知送達
# Cron job 設定（修正後）
Job ID: 8b8efe7cf28e
Name: DevOps Daily Learning Doc
Schedule: 0 3 * * *
Deliver: telegram:-1003966564424:652  (原為 local)
Prompt: 搜尋昨天（執行日期減一天）的對話...

2.3 Delivery 通知問題

修正後手動觸發測試，cron job 成功執行（last_status: ok，last_delivery_error: null），但使用者未收到即時完成通知。這是一個已知的 delivery pipeline 問題——cron 完成後的訊息未即時推送。目前尚未解決，等待觀察下一次 03:00 自動執行。

💡 Cron Job 設計原則：(1) 時間敏感任務必須考慮執行時間點的上下文——凌晨任務應查詢「前一天」資料；(2) Delivery target 應設為使用者會查看的頻道，而非 local（無通知）；(3) 排程任務的 prompt 中明確寫入日期計算邏輯（而非依賴 LLM 推斷），避免語意歧異。

5. DevOps 學習筆記系統的自我迭代

這一天的工作正好展示了自動化系統的自我修復能力：用 cron job 發現 cron job 的問題，修正後產生昨天的學習頁面。

5.1 發現問題

使用者手動檢查時發現 5/14 凌晨的排程沒有產生 5/13 的學習頁面。cron job 回傳 [SILENT]。

5.2 診斷與修正（同一天內完成）

  1. 查詢 cron job 執行記錄 → 確認執行了但回傳 SILENT
  2. 分析 prompt → 發現「搜尋今天」的語意錯誤
  3. 修正 prompt → 改為「搜尋昨天（執行日期減一天）」
  4. 手動觸發測試 → 成功產生 2026-05-13.html（25KB，5 大主題）
  5. 更新 index.html → 插入新 day-card
  6. Git commit + push → 部署到 K3s
💡 元學習：自動化系統的 bug 往往在邊界條件下才暴露——這裡是「凌晨 3 點沒有當天對話」這個邊界。設計排程任務時，必須考慮執行時間點的上下文，並對所有邊界條件做防禦性設計。

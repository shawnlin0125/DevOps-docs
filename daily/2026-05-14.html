🖥️ 對話一：Plugin-Hub K8s 代理架構簡化

07:49 AM · 統一代理模型，移除池化路由，單一 ticket-proxy Deployment

💡 K8s ConfigMap 驅動的 Plugin 載入機制

Plugin-Hub 使用 ConfigMap proxy-plugins 的 LOAD_PLUGINS 環境變數來控制 ticket-proxy 載入哪些 vendor plugin。Hub Admin 的 /api/load-plugins 端點回傳逗號分隔的已啟用 vendor ID 列表，運維人員據此更新 ConfigMap 並重啟 proxy pods。

# /api/load-plugins 回傳格式（純文字，逗號分隔）
ticketmaster,line,shopee

# proxy-plugins ConfigMap 結構
apiVersion: v1
kind: ConfigMap
metadata:
  name: proxy-plugins
  namespace: plugin-hub
data:
  LOAD_PLUGINS: "ticketmaster,line,shopee"

💭 原理：ConfigMap 是 K8s 中的宣告式設定載體。Proxy pod 啟動時讀取 LOAD_PLUGINS 環境變數，動態載入對應的 Go plugin 模組。這將「哪些 plugin 啟用」的狀態從程式碼中分離到 ConfigMap，無需重新 build image。

💡 Docker 鏡像導入 k3s containerd 的工作流

k3s 使用 containerd 而非 Docker 作為容器執行時。本地構建的 Docker 鏡像需要先 docker save 匯出為 tar，再透過 k3s ctr images import 匯入 containerd。

# 完整工作流
sudo docker build -t plugin-hub:go-latest .
sudo docker save plugin-hub:go-latest -o /tmp/plugin-hub.tar
sudo k3s ctr images import /tmp/plugin-hub.tar

# 確認鏡像已匯入
sudo k3s ctr images ls | grep plugin-hub

# 重啟 deployment 使用新鏡像（需搭配 imagePullPolicy: Never）
sudo kubectl -n plugin-hub rollout restart deployment hub-admin

💭 原理：containerd 有自己的鏡像儲存和命名空間，與 Docker 的 /var/lib/docker 完全獨立。imagePullPolicy: Never 告訴 kubelet 不要從 registry 拉取，直接使用本地 containerd 中的鏡像 — 適合單節點開發/測試環境。

💡 單一代理架構 vs 池化路由 — 架構簡化取捨

舊架構有 proxy-high 和 proxy-normal 兩個 Deployment，vendor 透過 AssignmentStore（YAML 後端）分配到不同池。新架構移除池概念，所有已啟用 vendor 載入到單一 ticket-proxy Deployment 的所有 pod。

簡化內容：刪除 hub-assignments ConfigMap、移除 Assignment API（GET/POST /api/assignments）、dashboard 移除部署下拉選單、handler.go 重構為單一上游。

💭 原理：當所有 vendor plugin 的總資源需求在單一 pod 可承受範圍內，池化路由帶來的複雜度（多 Deployment 管理、分配邏輯、ConfigMap 同步）超過其價值。簡化後的操作模型：Enable vendor → 更新 ConfigMap → 重啟 proxy → 所有實例生效。

💡 Go Reverse Proxy Handler 重構：從多上游到單上游

handler.go 的 ProxyToVendor 函數被重構：移除 AssignmentStore 查詢和池選擇邏輯，改為直接檢查 registry 中 vendor 是否啟用 → 反向代理到單一 ticket-proxy Service。

// 重構後的核心邏輯（偽代碼）
func (h *Handler) ProxyToVendor(w http.ResponseWriter, r *http.Request) {
    vendorID := chi.URLParam(r, "vendorID")
    if !h.registry.IsEnabled(vendorID) {
        http.Error(w, "vendor not enabled", 404)
        return
    }
    // 單一上游，不再查 AssignmentStore
    h.reverseProxy(w, r, "ticket-proxy.plugin-hub.svc.cluster.local:8000")
}

💭 原理：反向代理的精髓是透明轉發。當後端只有一個 Service 時，不需要路由表 — 直接寫死目標位址即可。這比維護 YAML-backed 分配表更可靠（無狀態、無同步問題）。

🔧 對話二：基礎設施總覽 & Cron Job 修正

09:53 AM · 排程 bug 修正、6 個服務總覽、ArgoCD 密碼查詢

💡 Cron Job 排程：搜尋「今天」vs「昨天」的陷阱

「DevOps Daily Learning Doc」排程在凌晨 3:00 執行時，prompt 指示搜尋「今天」的對話 — 但凌晨 3 點還沒有任何對話，永遠回傳 [SILENT]。修正為搜尋「昨天」（執行日期減一天）。

# 正確的日期計算（Python）
from datetime import datetime, timedelta
yesterday = (datetime.now() - timedelta(days=1)).strftime("%Y-%m-%d")

💭 原理：排程的執行時間和資料的時間窗口必須對齊。凌晨排程的「今天」是資料真空期 — 這不是排程失敗，而是邏輯錯誤。任何凌晨產生日報/摘要的排程都要處理這個時間差。

💡 kubectl 從 K8s Secret 讀取密碼

ArgoCD 初始密碼儲存在 K8s Secret argocd-initial-admin-secret 中，以 base64 編碼。使用 kubectl get secret -o jsonpath 可直接解碼取出。

# 讀取 ArgoCD admin 密碼
kubectl -n argocd get secret argocd-initial-admin-secret   -o jsonpath="{.data.password}" | base64 -d

# ArgoCD 登入資訊
# URL: https://argocd.shawnlin.online
# 帳號: admin

💭 原理：K8s Secret 的 .data 欄位是 base64 編碼（不是加密）。jsonpath 可以直接提取特定欄位，搭配 base64 -d 解碼。注意：任何人能執行 kubectl 就能讀取 Secret — 生產環境需搭配 RBAC 限制。

💡 單節點 k3s 的 6 個公開服務總覽

透過 kubectl get ingress -A 和 kubectl get svc -A 盤點所有對外服務。所有服務共用一台 2 vCPU / 7.5G RAM 的單節點 k3s，經 Cloudflare 代理。

# 查詢所有 Ingress
sudo kubectl get ingress -A

# 服務列表
# shawnlin.online          → korean-learning (prod)
# korean-staging.shawnlin.online → korean-staging
# argocd.shawnlin.online   → argocd (v3.4.2)
# devops.shawnlin.online   → devops-docs
# grafana.shawnlin.online  → monitoring
# hub.shawnlin.online      → plugin-hub

💭 原理：定期盤點對外暴露的服務是 SRE 基本動作。Ingress 資源是對外流量的入口 — 清點 Ingress 就等於清點攻擊面。Cloudflare 橙色雲（proxied）模式隱藏了真實來源 IP，提供免費的 DDoS 防護和 CDN。

# Topic 對照表

# #korean   → thread 2
# #infra    → thread 4

💭 原理：Telegram Forum Topic 本質上是同一群組內的訊息分流機制。每個 topic 有自己的 thread_id，bot 發送訊息時帶上 message_thread_id 參數即可路由到指定主題。這讓不同類型的通知（警報、部署、排程結果）各自有獨立的討論空間。

⏰ 對話三：排程架構討論 & Plugin 排程設計

09:54 AM · Cron job 檢視、APScheduler 選擇、delivery 通知問題

💡 Plugin 排程架構：APScheduler vs Celery/Kafka 的選擇

Plugin-Hub 平台本身不處理排程，每個 vendor plugin 內部自行管理 APScheduler 實例，透過 start()/stop() 生命週期 hook 控制。Celery 和 Kafka 被評估為「太重」— 需要額外的 message broker（Redis/RabbitMQ），在單節點 k3s 上增加不必要的資源消耗。

# APScheduler 整合模式（Python plugin 範例）
from apscheduler.schedulers.background import BackgroundScheduler

class TicketMasterPlugin:
    def start(self):
        self.scheduler = BackgroundScheduler()
        self.scheduler.add_job(self.check_tickets, 'interval', minutes=5)
        self.scheduler.start()

    def stop(self):
        self.scheduler.shutdown()

💭 原理：APScheduler 是 in-process 排程器（~0 額外 RAM），排程狀態隨 plugin 生命週期。Celery 需要獨立的 broker（Redis）和 worker 程序，Kafka 更重。在資源有限的單節點環境，in-process 排程是最務實的選擇。取捨：in-process 排程不支援跨實例協調（只有一個 pod 沒差）。

💡 Cron Job 的 deliver 欄位：local vs Telegram topic

Hermes cron job 的 deliver 欄位決定了執行結果的傳送方式。local 表示結果只存在 cron_output 目錄（無通知），telegram:chat_id:thread_id 則將結果送到指定的 Telegram 主題。

# 三種 deliver 模式
# "deliver": "local"                             → 僅存檔，無通知
# "deliver": "telegram:-1003966564424:4"         → 送到 #infra 主題
# "deliver": "telegram:-1003966564424:652"       → 送到 #schedule 主題

# 現有排程 deliver 設定
# Uptime Watchdog (e7258a5033a4):    origin (每 2 分鐘)
# Alert Checker (fe448223c4db):      telegram:...#4 (每 5 分鐘)
# DevOps Daily Doc (8b8efe7cf28e):   telegram:...#652 (每日 03:00)

💭 原理：不同排程有不同的通知需求。高優先級警報應送到專用 alert 主題（即時推送），低優先級日報送到 schedule 主題（不干擾日常討論）。local 模式適合純副作用排程（如備份），不需要人為介入。

💡 手動觸發 Cron Job 進行測試

修改排程 prompt 後，可以手動觸發 cron job 來驗證修正是否生效，而不需要等到下一個排程時間。Hermes 支援即時觸發排程。

# 觸發後驗證產出
ls -la /home/ubuntu/projects/devops-docs/daily/2026-05-13.html
# 確認檔案大小 > 0（非空）

# 檢查 git log 確認 commit

💭 原理：Cron job 的 prompt 是程式碼，修改後需要測試。手動觸發是 smoke test — 不保證所有邊界情況正確，但能快速確認核心邏輯（日期計算、搜尋、輸出）是否正常。這也是 CI/CD 思維：變更後立即驗證，不等排程自動執行。

🏗️ 對話四：K8s 基礎設施概念 & 資源評估框架

11:12 AM · OSI 模型、kubelet 機制、Pod 分佈、資源評估三線框架

💡 OSI L1-L7 在 K8s 中的對應：從 CNI 到 Ingress

OSI 七層模型簡化為 TCP/IP 四層後，可以清楚對應 K8s 中的網路元件：L2/L3（網路層）= CNI overlay（Flannel/Calico），L3 = Pod IP，L4（傳輸層）= Service（ClusterIP/NodePort，kube-proxy 處理 IP+Port 負載平衡），L7（應用層）= Ingress（host/path 路由，HTTP 層面）。

關鍵區分：L4 負載平衡只看 IP+Port（kube-proxy 用 iptables/IPVS 規則），L7 負載平衡看 HTTP 內容（Ingress controller 解析 Host header 和 URL path 來路由）。

💭 原理：理解網路分層可以幫助除錯。Pod 之間不通 → 檢查 CNI（L2/L3）；Service 不通 → 檢查 kube-proxy（L4）；Ingress 路徑不對 → 檢查 Ingress rule（L7）。分層觀念讓除錯可以逐層排查。

💡 kubelet 的 Pull 模型：不是 SSH 推播，而是主動拉取

K8s 的 Control Plane 不會 SSH 到 Node 下指令。kubelet 持續 watch API Server，主動發現自己被分配到的 Pod，然後呼叫 containerd 執行。整個控制鏈：kubectl → API Server (HTTPS) → etcd 寫入狀態 → Scheduler 選定 Node → kubelet 觀察到變更 → containerd 執行容器。

# 三層控制模型
# 1. Control Plane → Node：kubelet pull（watch API Server）
# 2. Controller → Resources：Reconciliation Loop（比較期望 vs 實際）
# 3. User → K8s：kubectl / REST API

# k3s 特殊之處：所有元件打包為單一二進位檔
# etcd 被 SQLite 取代（可選切換到 PostgreSQL: --datastore-endpoint）

💭 原理：Pull 模型是 K8s 可擴展性的關鍵 — API Server 不需要知道所有 Node 的位址或狀態，kubelet 自己來報到和拉任務。這與傳統 SSH 推播模式（Ansible、Capistrano）根本不同：Node 多了可以自己重新連接，Control Plane 不需要維護 Node 連線池。

💡 K8s 宣告式 vs Docker Compose 命令式

Docker Compose 是命令式（imperative）— 你告訴系統「做什麼」（啟動容器、停止容器）。K8s 是宣告式（declarative）— 你宣告「期望狀態」（3 個 replica、用這個 image），Controller 不斷比對實際狀態並修正差異（Reconciliation Loop）。

Pod 是拋棄式的：Pod 死掉後，新 Pod 有新名稱和新 IP，Service 自動更新 endpoints。Deployment Controller 持續比較 current state vs desired state，發現差異就修正。

💭 原理：宣告式模型的核心是 Reconciliation Loop — 不是一次性指令，而是持續監控。這意味著即使手動刪除一個 Pod，Controller 會立刻建立新的來補足 replica 數量。Docker Compose 如果容器掛了，你需要重跑 docker-compose up。

💡 資源評估三線框架（保守/警戒/危險）

針對 2 vCPU / 7.5G RAM / 79G SSD 的單節點 k3s，建立三線資源評估標準：

資源🟢 保守線 (Safe)🟡 警戒線 (Warning)🔴 危險線 (Critical)
CPU (load/cores)< 0.70.7–2.0> 2.0
RAM (實際使用)< 60%60%–80%> 80%
Disk (使用率)< 60%60%–80%> 80%
RAM (K8s limits)< 70%70%–90%> 90%

資源耗盡順序：RAM 最先掛（OOM Kill）→ Disk 滿 → CPU 瓶頸 → Network（最少見）。目前伺服器狀態：CPU load 0.20/2 cores (~10%)，RAM 56%（available 3.9G），Disk 43% — 全部在保守線內。

💭 原理：RAM 是單節點的第一瓶頸。CPU 可以超量分配（throttle），但 RAM 超量會觸發 OOM Killer 殺程序。K8s limits 總和 87% 接近實際 RAM，表示所有 Pod 同時達到 limit 時會觸發 OOM — 需要監控的是 limits 總和 vs 實體 RAM，不是 requests。

💡 free -h 要看 available 不是 free

Linux 會把閒置 RAM 用作磁碟快取（disk cache），所以 free -h 的 free 欄位通常很小。available 欄位才是真正可分配給新程序的記憶體（含可回收的快取）。

$ free -h
               total   used   free   shared   buff/cache   available
Mem:           7.5Gi   4.1Gi  210Mi   250Mi      3.4Gi        3.9Gi
Swap:          1.9Gi   214Mi  1.7Gi
# ↑ free 只有 210M，但 available 有 3.9G — 系統其實很充裕

💭 原理：Linux 的記憶體管理哲學是「閒置 RAM 是浪費」，所以會積極使用未分配的 RAM 作為 page cache。當程序需要更多記憶體時，kernel 可以立即丟棄乾淨的 cache page 來騰出空間。available = free + 可回收的 cache/buffer。

💡 K8s 資源超額分配（Overcommit）的風險

K8s 允許 CPU limits 總和超過實體核心數（本伺服器 6550m / 2000m = 436% overcommit）。CPU overcommit 相對安全（kernel 用 CFS 公平排程），但記憶體 limits overcommit 很危險 — 一旦所有 Pod 同時觸及 limit，OOM Killer 會殺程序，可能造成級聯故障。

# 當前 K8s 資源分配
# CPU  Requests: 1135m (75%)  Limits: 6550m (436% overcommit)
# Mem  Requests: 2224Mi (33%) Limits: 5732Mi (87%)
# ↑ Mem limits 87% 接近實體 RAM，headroom 僅 13%

# 檢查 OOM 事件
sudo dmesg -T | grep -i oom

# 檢查 K8s 資源分配
sudo kubectl describe nodes | grep -A 8 "Allocated"

💭 原理：CPU 是 compressible resource（可壓縮）— 用滿了只會變慢，不會 crash。記憶體是 incompressible resource（不可壓縮）— 用滿了 kernel 必須殺程序。記憶體 overcommit 必須謹慎：理想的 limits 總和應 < 實體 RAM 的 80%（保留 kernel/buffer 空間）。

💡 單節點 k3s 加入 Worker Node 的方法

從單節點 k3s 擴充到多節點，只需在新的 Worker Node 上執行一行指令。Master 的 token 可從 /var/lib/rancher/k3s/server/token 取得。

# 在 Master 節點取得 token
sudo cat /var/lib/rancher/k3s/server/token

# 在新的 Worker Node 執行（Ubuntu/Debian）
curl -sfL https://get.k3s.io | K3S_URL=https://43.167.10.119:6443   K3S_TOKEN=<master-token> sh -

# 驗證節點加入
sudo kubectl get nodes
# NAME               STATUS   ROLES                  AGE
# vm-1-243-ubuntu    Ready    control-plane,master   30d
# new-worker-node    Ready    <none>                 1m

💭 原理：k3s 的設計目標是極簡安裝。Worker node 只需要知道 Master 的 API Server URL 和 token 即可加入叢集。加入後，kube-scheduler 自動開始將 Pod 分配到新節點（根據資源和親和性規則）。擴充瓶頸從「單機資源不足」轉移到「網路延遲和 CNI 跨節點通訊」。

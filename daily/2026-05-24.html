🐱 stock-analysis-v2 K3s 部署實戰

💡 Docker socket 權限錯誤 → sudo docker 解決

在 Ubuntu 上執行 docker build 時遇到 permission denied 錯誤，原因是 Docker daemon socket (/var/run/docker.sock) 預設只有 root 和 docker 群組成員可以存取。若使用者不在 docker 群組中，所有 docker 指令都需要加 sudo。

# 錯誤示範
docker build -t myapp .

# 正確做法（未加入 docker 群組時）
sudo docker build -t myapp .
sudo docker save myapp:latest | sudo k3s ctr images import -

💭 原理：Docker daemon 以 root 權限執行，socket 權限為 srw-rw----，非 docker 群組成員無法寫入。長期解法是 sudo usermod -aG docker $USER 後重新登入。

💡 k3s containerd 鏡像匯入（免 registry）

k3s 內建使用 containerd 而非 Docker daemon 作為容器執行環境。使用 docker build 產生的 image 必須透過 k3s ctr images import 手動匯入 k3s 的 containerd image store，才能被 Pod 使用。

# 完整流程：build → export → import
sudo docker build -t myapp:latest .
sudo docker save myapp:latest | sudo k3s ctr images import -

# 確認 image 已匯入
sudo k3s ctr images ls | grep myapp

💭 原理：k3s 用 containerd 取代 Docker，兩者 image store 完全獨立。docker save 把 image 轉成 tar stream，pipe 給 k3s ctr images import 寫入 containerd。

💡 imagePullPolicy: Never 在 k3s 的意義

在 Deployment spec 中設定 imagePullPolicy: Never，告訴 kubelet 不要嘗試從 registry 拉取 image，直接使用本地 containerd 中已有的 image。這是 k3s 單節點開發部署的常見模式。

# deployment.yaml 關鍵片段
spec:
  containers:
  - name: myapp
    image: myapp:latest
    imagePullPolicy: Never  # 不從 registry pull，用本地 image

💭 原理：預設 imagePullPolicy 是 Always（latest tag）或 IfNotPresent。設為 Never 後 kubelet 只查本地 containerd image store，找不到就直接報錯，適合沒有 registry 的單機 k3s 環境。

💡 Next.js static export + nginx:alpine Dockerfile

Next.js 應用程式若不需要 SSR，可以設定 output: "export" 將整個網站匯出為靜態 HTML/CSS/JS，再用 nginx:alpine 提供服務，大幅縮小 image 體積並降低運行時資源消耗。

# next.config.ts
const nextConfig = {
  output: "export",
};

# Dockerfile
FROM nginx:alpine
COPY out/ /usr/share/nginx/html/
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

💭 原理：Next.js 靜態匯出把每個 page 預渲染成 .html，不需要 Node.js runtime。nginx:alpine image 僅 ~10MB，遠小於 node:alpine 的 ~120MB。

💡 kubectl rollout restart + status 完整流程

更新 Deployment 後，使用 rollout restart 觸發滾動重啟（建立新 Pod → 等待 ready → 終止舊 Pod），再用 rollout status 等待整個流程完成後才做驗證，確保部署零停機。

# 觸發滾動更新
kubectl rollout restart deployment/stock-analysis -n stock-analysis

# 等待 rollout 完成（會顯示進度）
kubectl rollout status deployment/stock-analysis -n stock-analysis

# 最後驗證
curl -s -o /dev/null -w '%{http_code}' https://stock.shawnlin.online/

💭 原理：rollout restart 會為 Deployment 新增一個 annotation 觸發 ReplicaSet 更新，新的 ReplicaSet 逐步建立 Pod，ready 後才刪除舊 Pod，確保服務不中斷。

💡 K8s Resource Limits 設定策略（靜態網站）

為 nginx 靜態網站設定 resource limits：memory 128Mi、CPU 200m。對於只提供靜態檔案的服務，這些值足夠且有餘裕，避免單一服務占用過多節點資源。

# deployment.yaml 中的 resources 設定
resources:
  limits:
    memory: "128Mi"
    cpu: "200m"
  requests:
    memory: "64Mi"
    cpu: "100m"

💭 原理：limits 是上限（超過會被 throttle/OOM），requests 是排程保證。靜態 nginx 通常只用 ~10-20Mi RAM 和極少 CPU，設 128Mi/200m 留足緩衝又不過度浪費。

💡 K8s liveness / readiness probes 配置

為 nginx container 設定 HTTP GET 型態的 liveness 和 readiness probe，指向 port 80 的 / 路徑。K8s 透過定期 HTTP 請求判斷容器是否存活及是否準備好接收流量。

# deployment.yaml probes
livenessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 3
  periodSeconds: 5

💭 原理：liveness probe 失敗 → kubelet 重啟容器（修復 crash）；readiness probe 失敗 → 暫時從 Service endpoints 移除（不送流量），但不重啟。兩種 probe 各司其職。

💡 nginx ingress host-based 路由

使用 nginx ingress controller 根據 HTTP Host header 將流量路由到不同 Service，實現單一 LoadBalancer IP 服務多個網域。

# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: stock-analysis
  namespace: stock-analysis
spec:
  ingressClassName: nginx
  rules:
  - host: stock.shawnlin.online
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: stock-analysis
            port:
              number: 80

💭 原理：nginx ingress controller 根據 rules 中的 host 欄位比對請求的 Host header，轉發到對應 backend Service。一個 ingress controller 可以管理數十個 domain。

💡 curl 部署 smoke test 驗證

部署完成後，用一行 curl 指令快速驗證服務是否正常回應 HTTP 200。比起開瀏覽器手動檢查，curl smoke test 可自動化且可串接在 CI/CD 流程中。

# 回傳 HTTP status code 並丟棄 body
curl -s -o /dev/null -w '%{http_code}' https://stock.shawnlin.online/

# 加上 retry（服務可能需要幾秒才 ready）
curl -s -o /dev/null -w '%{http_code}' --retry 3 --retry-delay 2 https://example.com/

💭 原理：-s silent 模式、-o /dev/null 丟棄 body、-w 輸出自訂格式。只回傳 status code 讓腳本可以直接判斷部署是否成功（200=OK）。

💡 K8s namespace 專案隔離

為每個專案建立獨立 namespace（如 stock-analysis），將 Deployment、Service、Ingress 等資源放在同一個 namespace 下，避免不同專案的資源名稱衝突，也方便後續設定 ResourceQuota。

# namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: stock-analysis

# 建立 namespace
kubectl apply -f k8s/namespace.yaml
kubectl get namespaces

💭 原理：namespace 是 K8s 的邏輯隔離機制，同一 namespace 內的資源名稱必須唯一，不同 namespace 可以重名。等同於在一個 cluster 內切出多個「虛擬 cluster」。

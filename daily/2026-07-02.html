💡 kubectl top 資源診斷：即時用量 vs Scheduler 視角

kubectl top nodes 看節點即時 CPU/Memory 用量；kubectl top pods -A 看每個 Pod 即時用量。kubectl describe node | grep -A 8 Allocated 看 request/limit 佔比（scheduler 視角，用於容量規劃）。top 是即時實際用量（以 cgroup 為基礎），describe node Allocated 是 scheduler 看到的已分配資源佔比。兩者對比可分辨是「真的撐不住」還是「申請太多卻沒用到」。

# 節點即時用量
kubectl top nodes

# 各 Pod 即時用量
kubectl top pods -A

# Scheduler 視角：已分配資源佔比
kubectl describe node  | grep -A 8 'Allocated resources'

# 常用排序：看最吃資源的 Pod
kubectl top pods -A --sort-by=cpu | tail -10
kubectl top pods -A --sort-by=memory | tail -10

💭 原理：kubectl top 讀取 cgroup 的即時統計資料（cpuacct.usage、memory.usage_in_bytes），顯示 Pod 真實消耗。describe node Allocated 顯示的是 request/limit 總和，是 scheduler 決定能不能排 Pod 的依據。如果 top 低但 Allocated 高，表示 request 申請過多但實際沒用到。

💡 Docker 多階段建置縮小 Image：builder → runtime 瘦身法

Dockerfile 用多個 FROM 實現多階段建置：第一個 FROM（builder）裝所有建置工具和依賴做編譯，第二個 FROM（runtime）只複製編譯好的 artifacts，不帶建置工具。Go 可用 FROM scratch（static binary 零依賴），Node.js 用 standalone output。docker images 比較大小，可從 1GB+ 降到 100MB 以下。

# Dockerfile 範例（Go）
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o server .

FROM scratch
COPY --from=builder /app/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]

# 查看各層大小
docker history my-app:latest
docker images | grep my-app

💭 原理：Dockerfile 每個 RUN/COPY 指令產生一個唯讀層（layer），多階段把 builder 階段的層全部丟棄，只保留最後一個 FROM 建立的層。FROM scratch 空的映像檔完全不含 OS layer，適合靜態編譯語言，但需要注意 ca-certificates 和時區資料可能需要手動加入（用 FROM alpine 替代）。

💡 Linux 資源監控三指令：uptime、free、df

uptime 看 load average：三個數字分別是 1/5/15 分鐘平均。load average > 核心數表示 process 在等 CPU 時間。free -h 看記憶體：重點是 available（真正可用的記憶體，包含可回收的 cache/buffer），不是 free 欄位。df -h / 看磁碟使用率，df -i / 看 inode 使用率（大量小檔案可能 inode 先滿）。

# CPU 負載：load average vs CPU 核心數
uptime
# load average: 4.5, 3.2, 2.1  →  若 4 核心 CPU 表示目前有排隊
nproc   # 看 CPU 核心數

# 記憶體：看 available 才是真可用
free -h
#               total  used  free  shared  buff/cache  available
# Mem:          7.6G   2.1G  1.2G  120M    4.3G        5.0G
#                                      ↑ available 才是真可用 (包含可回收的 cache)

# 磁碟：使用率和 inode
df -h /
df -i /

💭 原理：Linux 充分利用閒置 RAM 做 disk cache（page cache + dentry cache），所以 free 欄位通常很低但系統並不缺記憶體。available 是 kernel 估算的「在不觸發 swap 的前提下可分配給新 process 的記憶體量」，是真正的可用值。load average > 核心數意味著 CPU 有排隊，但不一定是瓶頸——可能是 I/O wait 讓 process 卡在 D 狀態。

💡 Git 復原操作：reset、restore、reflog 三種情境

git reset --soft HEAD~1 退回上一次 commit 但保留 working directory 和 staging area 的改動（可重新 commit）。git restore 丟棄工作區的未暫存改動（取代舊版 git checkout -- ）。git reflog 看所有 HEAD 移動記錄，可用來找回誤刪的 commit（git reset --hard ORIG_HEAD 或 git cherry-pick 救回特定 commit）。

# 情境 1：commit 錯了但想保留改動重新 commit
git reset --soft HEAD~1

# 情境 2：丟棄工作區的修改（沒 staged 過的）
git restore 
# 或恢復整個目錄
git restore .

# 情境 3：救回誤刪的 commit（還沒被 GC）
git reflog
# 找到要救的 commit SHA
git cherry-pick 
# 或直接 reset 到那個位置
git reset --hard HEAD@{2}

# 取消 staging
git restore --staged

💭 原理：Git 是 DAG（有向無環圖）結構，commit 永遠不會消失，只是從分支（可達路徑）脫落。reflog 是本機操作日誌記錄 HEAD 指向的歷史，記錄所有分支切換、commit、reset 等操作。只要沒有被 git gc 清除（預設 90 天），commit 物件仍存在 .git/objects 中，可透過 reflog 的 SHA 找回。

💡 Helm 常用操作：list、history、rollback、get values

helm list -A 看所有 namespace 的 release（已部署應用）。helm history -n 看某個 release 所有 revision 的變更記錄。helm rollback -n 退回指定版本（適合快速回退）。helm get values -n 看目前 release 的實際 values（用於確認部署參數）。--history-max 控制保留的 revision 數量避免 etcd 膨脹。

# 查看所有 release
helm list -A

# 查看特定 release 的版本歷史
helm history my-app -n production

# 退回上一版（最常見的 rollback）
helm rollback my-app -n production

# 退回指定 revision
helm rollback my-app 3 -n production

# 查看目前已部署的 values
helm get values my-app -n production

# 控制 revision 數量（安裝時設定）
helm install my-app ./chart --history-max 5

# 除錯：渲染 YAML 看最終結果
helm template my-app ./chart -f values/production.yaml --debug

💭 原理：Helm 的 release 是 K8s 資源集合的快照。每次 helm upgrade 建立一個新 revision（包含當時的 manifests）。rollback 不是真的回到過去，而是部署前一個 revision 的 manifests 作為新 revision。--history-max 控制 revision 數量是因為每個 revision 的 secrets 都存於 etcd，長期累積會佔用大量 etcd 儲存空間。

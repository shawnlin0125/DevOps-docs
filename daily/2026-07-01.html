💡 kubectl 診斷 Pod 啟動失敗的四步驟流程

Pod 啟動失敗時依序使用：kubectl get pods → describe pod → logs → get events。從 Status/Events 欄位判斷是 ImagePullBackOff（鏡像問題）、CrashLoopBackOff（容器啟動後不斷重啟）、OOMKilled（超過記憶體限制）還是 Pending（資源不足無法排程）。describe 的 Events 段落記錄 kubelet 對 Pod 的每一個操作與錯誤，是最快定位問題的入口。

# 步驟 1: 查看 Pod 狀態
kubectl get pods -n 
# 步驟 2: 看詳細事件
kubectl describe pod  -n 
# 步驟 3: 看容器日誌
kubectl logs  -n 
# 步驟 4: 看所有事件
kubectl get events -n  --sort-by='.lastTimestamp'

💭 原理：kubelet 對 Pod 的每個操作都會寫入 Events，describe pod 的 Events 欄位就是最快定位問題的入口。logs 只能看到容器 stdout/stderr，適合 CrashLoopBackOff 時看最後的錯誤訊息。

💡 k3s containerd 鏡像管理完整流程

k3s 使用 containerd 而非 Docker daemon，離線或本地部署需要經由 docker save / k3s ctr import 流程：先在開發機 docker build，然後 docker save 成 tar，再傳到 k3s 節點用 sudo k3s ctr images import 匯入。部署時須設 imagePullPolicy: Never 避免 kubelet 嘗試從遠端 registry 拉取。用 sudo k3s ctr images ls 確認鏡像已匯入。

# 開發機：建置匯出
docker build -t my-app:latest .
docker save my-app:latest > my-app.tar
# k3s 節點：匯入
sudo k3s ctr images import my-app.tar
# 確認匯入
sudo k3s ctr images ls | grep my-app
# Deployment 需設 imagePullPolicy: Never
kubectl apply -f deploy.yaml
kubectl rollout restart deployment/my-app

💭 原理：k3s 的 containerd 有自己的 image store（namespace k8s.io），與 Docker daemon 分離。k3s ctr import 自動處理 namespace，但本地沒有 registry 機制，所以必須用 imagePullPolicy: Never 跳過遠端拉取。

💡 查 OOM 紀錄：dmesg + exit code 137

當 Pod 或 process 被 OOM Killer 終止時，用 sudo dmesg -T | grep -i oom 查看核心 OOM 記錄（含被殺的 process、oom_score、記憶體使用量）。exit code 137（128 + 9 SIGKILL）表示 process 被 OOM Killer 殺死。K8s 中 kubectl describe pod 的 Last State: OOMKilled 是 cgroup 層級 OOM。注意：節點 memory limits 總和超過實體 RAM 時 OOM 會連鎖殺 Pod。

# 查核心 OOM 紀錄
sudo dmesg -T | grep -i oom | tail -20
# 看 process exit code（137 = OOM）
kubectl describe pod  | grep -A 10 'Last State'
# 檢查節點記憶體壓力
free -h
kubectl describe node | grep -A 5 'Allocated resources'

💭 原理：OOM Killer 由核心記憶體管理子系統觸發，挑選 oom_score 最高的 process（通常是吃最多 RAM 的）終止以釋放記憶體。K8s 的 cgroup 層級 OOM 發生在 Pod 超過 memory limits 時只殺該 Pod 的 container，而節點層級 OOM 會殺任意 process。

💡 Git stash 暫存管理：切換分支前的好幫手

當你在分支 A 工作進行到一半，需要切到分支 B 處理事情時，git stash 暫存所有未 commit 的改動，還原乾淨工作區。git stash -u 含 untracked 檔案。回來後 git stash pop 還原最近暫存並從列表中移除。git stash list 看所有暫存（LIFO 堆疊）。stash 本質是 commit-like 物件存於 .git/refs/stash，可跨 branch 套用但可能衝突。

# 暫存目前改動
# 切到緊急分支 FIX_TAG 拉最新修正
git stash -u        # 暫存含 untracked
git checkout FIX_TAG
git pull
git checkout -
git stash pop      # 還原並移除 # 回來後還原改動
# 查看暫存列表
git stash list
git stash show -p stash@{0}

💭 原理：stash 本質上產生一個 commit-like 物件指向 working tree 的狀態，存在 .git/refs/stash 參考的 reflog 中。stash stack 是 LIFO，最近暫存放在 stash@{0}。因為是 commit-like 物件，可以跨分支套用，但如果套用到的分支有衝突仍需要手動解決。

💡 Cloudflare DNS 管理：Proxy vs DNS only 模式

Cloudflare DNS 有兩種模式：Proxy mode（橙色雲朵）流量經過 Cloudflare CDN，隱藏 origin IP 並提供免費 TLS；DNS only（灰色雲朵）直接解析到 origin IP，無 CDN 保護。用 dig +short domain.com 檢查：回傳 Cloudflare IP 表示 Proxy mode，回傳真實伺服器 IP 表示 DNS only。Cloudflare API 可程式化管理 DNS records 適合自動化部署。

# 檢查 DNS 解析模式
dig +short example.com
# 若回傳 Cloudflare IP（如 104.x.x.x / 172.x.x.x）→ Proxy mode
# 若回傳真實 IP → DNS only

# Cloudflare API 管理 DNS（需 API Token）
curl -X GET "https://api.cloudflare.com/client/v4/zones//dns_records" \
  -H "Authorization: Bearer " \
  -H "Content-Type: application/json"

# 新增 A record（Proxy mode）
curl -X POST "https://api.cloudflare.com/client/v4/zones//dns_records" \
  -H "Authorization: Bearer " \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"www","content":"1.2.3.4","proxied":true}'

💭 原理：Proxy mode 下 Cloudflare 的 Anycast 網路會終止 TLS 連線，建立 CDN 到 origin 的專線（保證加密）。DNS only 純粹是 DNS 解析，請求直接到達 origin 伺服器。選擇 Proxy mode 可獲得免費 TLS + DDoS 防護，但 SSL 終止在 Cloudflare 端，origin 需信任 Cloudflare 的來源 IP 範圍。

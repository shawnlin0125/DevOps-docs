💡 kubectl 診斷 Pod 啟動失敗的完整流程

當 Pod 無法啟動時，依序執行四步驟診斷：(1) kubectl get pods -A 看 Status 欄快速判斷（CrashLoopBackOff、ImagePullBackOff、Pending、OOMKilled）；(2) kubectl describe pod <pod> -n <ns> 看 Events 欄和 Conditions 找到真正錯誤；(3) kubectl logs <pod> -n <ns> 看容器 stdout/stderr；(4) kubectl get events -n <ns> 看 cluster 層級事件（如 Node 資源不足）。

# 步驟 1：看所有 Pod 狀態
kubectl get pods -A

# 步驟 2：詳細描述（Events 欄是關鍵）
kubectl describe pod <pod> -n <ns>

# 步驟 3：看容器日誌
kubectl logs <pod> -n <ns>
kubectl logs --previous <pod> -n <ns>  # 看上一次 restart 前的 log

# 步驟 4：看 cluster 事件
kubectl get events -n <ns> --sort-by='.lastTimestamp'

# 常見 Status 判讀：
# ImagePullBackOff → 鏡像不存在或拉取失敗
# CrashLoopBackOff → 容器啟動後一直 crash
# Pending → 資源不夠或 PVC 未 bound
# OOMKilled → memory limits 不足

💭 原理：kubectl describe 從 kube-apiserver 撈取 Pod 完整 spec + status + events，Events 是 kubelet/kube-scheduler 寫入的可觀察性記錄。CrashLoopBackOff 表示 container 啟動後立即退出（exit code ≠ 0），kubelet 回傳 restartCount ++，exponential backoff 延遲重啟。Pending 最常見原因是 Pod 排程不上去（資源不足）或 PersistentVolumeClaim 還沒 bound。

💡 k3s containerd 鏡像管理：build → save → import → deploy

k3s 不使用 Docker daemon，而是內建 containerd。部署自建鏡像的完整流程：先在 Docker 環境 build 鏡像，docker save 成 tar 檔，再透過 k3s ctr images import 匯入 containerd 的 image store，最後 kubectl apply + imagePullPolicy: Never 讓 k3s 使用本地鏡像而不去 registry 拉取。

# 1. Docker build（在開發機或本機）
docker build -t myapp:latest .

# 2. Docker save 成 tar
docker save myapp:latest -o myapp.tar

# 3. k3s 節點上匯入 containerd
sudo k3s ctr images import myapp.tar

# 4. 確認已匯入
sudo k3s ctr images ls | grep myapp

# 5. Deployment 設定 imagePullPolicy: Never
# spec.template.spec.containers[0].imagePullPolicy: Never

# 6. 部署
kubectl apply -f deployment.yaml
kubectl rollout restart deploy/myapp

# 注意：每次 rebuild 後要重新 save + import + restart

💭 原理：k3s containerd 的 image namespace 預設是 k8s.io，k3s ctr images import 自動匯入到正確的 namespace。imagePullPolicy: Never 讓 kubelet 跳過 registry pull 步驟，直接用 containerd 本地 image store 的鏡像。若用 :latest tag 不更新，建議用 timestamp tag（如 myapp:20260710-1200）確保每次強制使用新版。

💡 systemd 服務管理：systemctl + journalctl

systemd 是 Linux 的 init 系統，管理所有服務（unit）。常用 systemctl 指令：systemctl status <service> 看服務狀態、systemctl list-units --state=failed 列出所有失敗的服務、systemctl daemon-reload 重載 unit file 變更。journalctl -u <service> -n 50 --no-pager 看特定服務的最近 log。systemctl enable/disable 控制開機自啟。

# 查看服務狀態
systemctl status k3s

# 列出所有失敗的服務
systemctl list-units --state=failed

# 看特定服務最近日誌
journalctl -u k3s -n 50 --no-pager

# 看即時日誌（類似 tail -f）
journalctl -u k3s -f

# 重載 unit file（修改 .service 檔後執行）
systemctl daemon-reload

# 重啟服務
systemctl restart k3s

# 開機自啟管理
systemctl enable k3s
systemctl disable k3s

# 隱藏 service 副檔名也可以
systemctl status k3s.service  # 等同 systemctl status k3s

💭 原理：systemd unit 放在 /etc/systemd/system/（自訂）或 /lib/systemd/system/（套件安裝），副檔名為 .service、.timer、.socket 等。systemctl daemon-reload 會重新掃描 unit 目錄並載入變更。journalctl 讀取 /var/log/journal/ 的二進位 journal 檔案，支援 --since/--until 時間範圍過濾。

💡 Git stash 暫存管理

當你在 branch 上改了檔案但還沒 commit，卻需要換 branch 或處理其他事時，git stash 可以暫時儲存目前的工作目錄改動。預設只暫存 tracked 檔案，git stash -u 或 --include-untracked 連新增檔案也暫存。git stash list 看所有暫存，git stash pop 恢復最新暫存並刪除它，git stash apply 恢復但不刪除（給多次 apply 用）。

# 暫存目前改動（含 untracked）
git stash -u

# 看所有暫存
git stash list
# stash@{0}: WIP on main: a1b2c3d feat: xxx
# stash@{1}: WIP on feature: e5f6g7h fix: yyy

# 恢復最近暫存並刪除
git stash pop

# 恢復指定暫存但不刪除
git stash apply stash@{1}

# 刪除指定暫存
git stash drop stash@{1}

# 全部清空
git stash clear

# 暫存時加訊息方便辨識
git stash push -u -m "WIP: refactoring auth module"

💭 原理：Git stash 本質上產生一個 merge commit（或兩個 parent commit：staged + working tree 的 HEAD），存放在 .git/refs/stash refs 中。stash list 是 LIFO 結構（stack），每次 stash push 都推到最上面，stash pop 取出最新（stash@{0}）並自動 drop。

💡 網路排查四指令：curl · dig · ss · nc

四個指令分別對應 OSI 模型不同層級：curl -v http://domain（應用層，看 HTTP request/response 和 SSL 握手）、dig +short domain（DNS 層，查域名解析）、ss -tlnp（傳輸層，看 listening TCP port 及所屬 process）、nc -zv host port（傳輸層，測試 TCP 連線是否通）。

# curl：完整 HTTP 請求（含 header + SSL 握手資訊）
curl -v https://example.com
curl -I https://example.com  # 只看 response headers

# dig：DNS 查詢
dig +short example.com           # A record
dig +short mx example.com        # MX record
dig example.com CNAME            # CNAME record

# ss：看 listening port（取代 netstat）
ss -tlnp  # TCP listening + process
ss -ulnp  # UDP listening

# nc：測試 TCP 連線
nc -zv example.com 443           # 測 HTTPS 通不通
nc -zv 10.0.0.1 3306             # 測內部 MySQL 連線

# 常見應用：確認服務是否在 listening
ss -tlnp | grep 8080

💭 原理：curl -v 走完整 TCP + TLS 握手，輸出 SSL certificate 資訊和 HTTP response status line，是排查 HTTPS 連線問題的首選。dig +short 跳過 dig 詳細輸出直接給解析結果。ss 直接讀取 kernel socket 資訊（/proc/net/tcp），比 netstat 更快更完整（支援 cgroup、socket inode）。nc -zv 只發 SYN 等 ACK（三次握手第一步），成功即退出，不建立完整連線。

💡 kubectl exec Pod 內排查：env、nc、resolv.conf 三招

kubectl exec -it <pod> -n <ns> -- sh 進容器後，env | grep -i 確認環境變數是否正確傳入；nc -zv <svc> <port> 測試容器能否連到其他服務（2 秒快速驗證）；cat /etc/resolv.conf 確認 DNS 設定（搭配 CoreDNS 的 cluster domain）。這三招覆蓋 80% 的容器內診斷需求：配置、連線、DNS。

# 進入容器
kubectl exec -it  -n  -- sh

# 檢查環境變數
env | grep -i DB_HOST

# 測試服務連線
nc -zv myservice 8080

# 確認 DNS 設定
cat /etc/resolv.conf

💭 原理：kubectl exec 透過 K8s API server 建立到 container runtime 的連線，本質是 attach（非 ssh）。容器內用 nc -z（zero I/O）測試 TCP 連線只檢查 port 是否 listening，不回傳資料。

💡 Docker 多階段建置縮小 Image：builder → runtime 瘦身法

Dockerfile 用多個 FROM 語句，builder 階段裝所有建置工具（gcc、npm、pip install），runtime 階段只複製編譯後的 artifacts。Go 可用 FROM scratch（static binary 零依賴），Node.js 用 standalone output 搭配 FROM node:alpine。docker images | grep <name> 比較建置前後大小（可從 1GB+ 降到 100MB 以下）。

# Go 多階段建置範例
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o app

FROM scratch
COPY --from=builder /app/app /app
CMD ["/app"]

💭 原理：Docker image 由唯讀層堆疊，多階段只是不同 Dockerfile 的命名階段。--from=builder 只複製指定階段的檔案，不保留 builder 的 base image 層。每個 FROM 啟動一個新階段，前一階段的中間層全部捨棄。

💡 Linux 資源監控三指令：uptime、free、df

uptime 看 load average（1/5/15 分鐘），數值超過 CPU 核心數表示正在排隊（例如 4 核心 load=8 表示平均有 4 個 process 在等 CPU）。free -h 看記憶體，重點看 available 不是 free（Linux 拿閒置 RAM 做 page cache，free 低不等於不夠）。df -h / 看磁碟使用率，監控閾值通常 80% 告警、90% 緊急。

# CPU 排隊狀況（load > 核心數 = 在等 CPU）
uptime

# 記憶體（看 available 才是真實可用）
free -h

# 磁碟使用率
df -h /

💭 原理：load average = CPU 佇列長度 + 正在執行 + I/O blocked 的 process 數。available = free + page cache + slab reclaimable，是核心估算的「可立即回收給應用程式的記憶體」。

💡 GitHub PR 流程：gh CLI 完整操作

完整 PR 流程：git checkout -b feature/xxx → 改程式 → git add/commit → git push -u origin feature/xxx → gh pr create --title "..." --body "..." → 等 review → gh pr merge --squash --delete-branch。實用工具：gh pr list 看進行中的 PR、gh pr diff 看改動、gh pr checkout <num> 切到他人 PR。合併策略：squash（單一 commit 進 main）、merge（保留 branch commits）、rebase（線性歷史）。

# 完整 PR 流程
git checkout -b feature/my-feature
# ... 改程式碼 ...
git add . && git commit -m "feat: add my feature"
git push -u origin feature/my-feature
gh pr create --title "feat: 新增功能" --body "做了什麼、為什麼"

# Review 後合併
gh pr merge --squash --delete-branch

# 查看進行中的 PR
gh pr list

💭 原理：gh pr create 基於你 push 的分支（不是 HEAD），會自動偵測 remote。--squash 將 PR 所有 commits 壓成一個，main 線性乾淨；--delete-branch 合併後自動刪遠端分支，避免堆積。

💡 Helm 常用操作：list、history、rollback、get values

helm list -A 看所有 namespace 的 release；helm history <release> -n <ns> 看版本歷史（每次 upgrade 生成一個 revision）；helm rollback <release> <rev> -n <ns> 退回指定版本（快速救回失誤升級）；helm get values <release> -n <ns> 看目前生效的 values（確認哪些 --set 已套用）。--history-max 設定保留多少 revision 避免 etcd 膨脹。

# 查看所有 release
helm list -A

# 查看版本歷史
helm history myapp -n production

# 退回版本 2
helm rollback myapp 2 -n production

# 看目前生效的 values
helm get values myapp -n production

💭 原理：Helm upgrade 不是原地更新，而是建立新 revision（新版 K8s manifest），rollback 就是 apply 舊 revision 的 manifest。Revision 是累積的，revision 越多 etcd 中 storage 越肥。helm get values 讀的是 Helm 記憶體中的 values（不是 K8s resource 的欄位）。

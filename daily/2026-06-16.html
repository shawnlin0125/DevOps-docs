💡 kubectl 診斷 Pod 啟動失敗的完整流程

kubectl get pods 看狀態列 → kubectl describe pod <name> 看 Events/Conditions 欄位（Last State / Reason）→ kubectl logs <name> 看容器輸出 → kubectl get events --sort-by='.lastTimestamp' 看集群事件時間線。從 Status 欄位快速判讀：ImagePullBackOff 表示鏡像問題、CrashLoopBackOff 是程式崩潰後反覆重啟、OOMKilled 是記憶體不足被殺、Pending 是資源不足沒排上節點。logs --previous 可以看 crash 前最後一輪的 stdout/stderr，對 CrashLoopBackOff 特別有用。

# Step 1: 看狀態
kubectl get pods -n <namespace>

# Step 2: 看事件與 Conditions
kubectl describe pod <pod-name> -n <namespace>

# Step 3: 看容器日誌（CrashLoop 用 --previous）
kubectl logs <pod-name> -n <namespace> --previous

# Step 4: 看集群事件
kubectl get events --sort-by='.lastTimestamp' -n <namespace>

💭 原理：Pod 啟動失敗時，K8s 控制面版會記錄事件和 Container Status，describe 的 Conditions 欄位結合 events 形成完整時間線。logs --previous 保留 crash 前最後一次輸出的緩衝區，不會因重啟而丟失。

💡 Docker 多階段建置縮小 Image

Dockerfile 用多個 FROM 指令分離 build 和 runtime stage。build stage 安裝所有編譯工具（gcc、npm、pip）產生 artifacts，runtime stage 只從 builder 複製最終產物（binary、靜態檔案）。Go 應用可 FROM scratch（~15MB static binary）、Node.js 用 standalone output 脫離 node_modules 減少大小。docker images 或 docker image history 查看最終 image 各層大小，build stage 的 layers 在 COPY 後被捨棄不計入。

# Go 多階段建置範例
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server

FROM scratch
COPY --from=builder /app/server /server
CMD ["/server"]

# 查看 image 大小
docker images | grep myapp
docker image history myapp:latest  # 看每層大小

💭 原理：Docker image 由唯讀層疊加，builder 的層不會出現在最終 image 中——COPY --from=builder 只在 runtime stage 新建一層包含所需 artifacts，捨棄 deps 層，達到最小化攻擊面和加速傳輸的效果。

💡 查 OOM 紀錄：dmesg + exit code 137

系統級 OOM Killer 紀錄用 sudo dmesg -T | grep -i oom 查看，會顯示被殺的 process 名稱、pid 和當時記憶體用量。K8s 環境中 Pod 因超出 memory limits 被 kill 會顯示 OOMKilled 狀態（exit code 137 = 128 + SIGKILL 9）。如果多個 Pod memory limits 總和超過節點實體 RAM，OOM Killer 會連鎖殺 Pod。kubectl describe pod <name> | grep -A 2 Limits 查看 Pod 的 memory limits。

# 查系統 OOM 紀錄（-T 顯示人類時間）
sudo dmesg -T | grep -i oom | tail -5

# 看 Pod 是否 OOM Killed
kubectl describe pod <pod-name> | grep -E "(State|Reason|Exit)"

# 看 Pod resources（requests/limits）
kubectl describe pod <pod-name> | grep -A 2 Limits

# 看節點可用記憶體
kubectl describe node <node> | grep -A 5 "Allocated resources"

💭 原理：Linux OOM Killer 是核心記憶體不足時的最後防線，它計算每個 process 的 oom_score（主要看 RSS 用量），挑分數最高的砍。exit code 137 = 128 + 9（SIGKILL），在 K8s 中表示容器被主動殺掉而非正常退出。Pod resources limits 總和超出節點容量是常見原因。

💡 GitHub PR 流程：gh CLI

完整 PR 流程：git checkout -b feature/xxx 開分支 → 開發 commit → git push -u origin feature/xxx 推上遠端 → gh pr create --title "..." --body "..." 開 PR → 等 review 和 CI 通過 → gh pr merge --squash 合併進 main/develop → git checkout main && git pull 同步本地。gh pr view 看 PR 詳情，gh pr checkout <number> 切到他人 PR review。--squash 將 feature branch 的多個 commit 壓成一個，保持主線歷史整潔。

# 開分支 + 開發
git checkout -b feature/add-logging
# ... 開發、commit ...

# 推上遠端 + 開 PR
git push -u origin feature/add-logging
gh pr create --title "[Feat] 新增 logging 功能" --body "實作內容說明"

# Review 過後合併
gh pr merge --squash --delete-branch

# 同步主線
git checkout main && git pull

# 看他人 PR
gh pr list
gh pr checkout 42  # 切到 PR #42

💭 原理：gh CLI 封裝 GitHub REST API，pr create 等同於呼叫 POST /repos/owner/repo/pulls。--squash merge 在 GitHub 上建立一個 squash commit 到 base branch，feature branch 的細碎 commits 不汙染主線歷史。push -u 設定 upstream tracking 讓後續 git push/pull 自動使用正確遠端分支。

💡 Cloudflare DNS 管理：Proxy vs DNS only

Cloudflare DNS record 有兩種模式：Proxy mode（橙色雲朵）流量經 Cloudflare 代理，隱藏 origin IP、提供免費 TLS 終止、DDoS 防護與 CDN 快取，但會增加一跳延遲。DNS only（灰色雲朵）只解析 DNS 到 origin IP，無保護但延遲最低。透過 Cloudflare API 可自動化管理：curl -X POST https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records 搭配 Bearer token。proxied: true 啟用 Proxy，proxied: false 為 DNS only。

# 用 API 新增 DNS record（Proxy mode）
curl -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"www","content":"203.0.113.10","ttl":120,"proxied":true}'

# 用 API 列出所有 DNS records
curl -s "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $CF_API_TOKEN" | jq '.result[] | {name, type, content, proxied}'

# 測試 proxy 是否生效（看 IP 是否為 Cloudflare 節點）
dig +short www.example.com

💭 原理：Proxy mode 讓 Cloudflare 的 Anycast 邊緣節點作為反向代理接收請求，origin server 只和 Cloudflare IP 通信。DNS only 則直接回傳 origin IP，瀏覽器直接連線，適合不需要安全/快取功能的內部服務或 API endpoint。

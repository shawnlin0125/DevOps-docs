💡 Docker 多階段建置縮小 Image

Docker 多階段建置（multi-stage build）讓你在一個 Dockerfile 中使用多個 FROM 指令：build stage 安裝所有建置依賴（編譯器、npm 套件等），runtime stage 只複製編譯後的 artifacts，大幅縮小最終 image。Go 語言可以 FROM scratch（static binary，連 base OS 都不需要），Node.js 可以用 standalone output。查看 image 大小用 docker images 或 docker image history。

# === Go 範例（FROM scratch） ===
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server

FROM scratch
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]

# === Next.js 範例 ===
FROM node:20 AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
EXPOSE 3000
CMD ["node", "server.js"]

# 查看 image 大小
docker images | grep <name>
docker image history <image>  # 看每層的大小

💭 原理：Docker image 由唯讀層疊加而成，每層都會永久佔用空間。多階段建置讓最終 image 只包含 runtime 層，build 階段的工具鏈（go compiler、node_modules、npm cache）全部捨棄。

💡 systemd 服務管理：systemctl + journalctl

systemd 是現代 Linux 的 init 系統。常用維運流程：systemctl list-units --state=failed 快速找出所有失敗的服務；journalctl -u <service> -n 50 --no-pager 看最近服務的 log；修改 /etc/systemd/system/<service>.service 後，執行 systemctl daemon-reload 重載設定。用 systemctl status <service> 確認服務是否正在執行。

# === 服務狀態診斷 ===
systemctl list-units --state=failed        # 列出所有失敗的服務
systemctl status <service>                  # 看單一服務狀態（含最近 log）
systemctl is-active <service>               # 只看是否 active（回傳字串）

# === 日誌診斷 ===
journalctl -u <service> -n 50 --no-pager   # 看最近 50 行 log
journalctl -u <service> --since "1 hour ago"  # 看過去 1 小時
journalctl -u <service> -f                  # 即時追蹤 log（類似 tail -f）

# === 服務操作 ===
sudo systemctl restart <service>            # 重啟服務
sudo systemctl daemon-reload                # 修改 unit file 後重載
sudo systemctl enable <service>             # 設定開機啟動
sudo systemctl disable <service>            # 取消開機啟動

💭 原理：journalctl 讀取 systemd-journald 的二進位日誌（位於 /var/log/journal/），支援結構化過濾（-u、--since、_PID= 等），比傳統 syslog 功能更強且無需 log rotate。

💡 GitHub PR 流程：gh CLI

標準 PR 流程：從 main 開 feature branch → 提交程式碼 → push 到 origin → 用 gh pr create 開 PR → 等 review 與 CI 通過 → merge。用 gh pr view 看 PR 內容、gh pr status 看所有 PR 狀態。merge 後回到 main branch 同步。

# === 完整 PR 流程 ===
# 1. 開 feature branch
git checkout main
git pull origin main
git checkout -b feature/xxx

# 2. 開發、commit、push
git add .
git commit -m "feat: add xxx"
git push -u origin feature/xxx

# 3. 開 PR
gh pr create --title "feat: add xxx" --body "實作 xxx 功能，請 review" --assignee @me

# 4. review 與 CI 通過後 merge
gh pr merge --squash --auto  # squash merge + 啟用 auto-merge

# 5. 同步 main
git checkout main && git pull

# === 查看 PR 狀態 ===
gh pr status              # 列出所有 PR（含需 review 的）
gh pr view <pr-number>    # 看特定 PR 內容
gh pr list --state open   # 列出所有 open PR

💭 原理：gh CLI 透過 GitHub REST API 與 GraphQL API 操作 PR，支援 token 認證（gh auth status）。--squash 將多個 commit 壓成一個，保持 main 的歷史乾淨。

💡 Helm values 分層覆蓋原則

Helm 的 values 有多層覆蓋順序：values.yaml（chart 內建的預設值）← values/production.yaml（環境特定覆蓋）← --set key=value（CLI 執行時覆蓋）。後面的層級 merge 覆蓋前面的同名 key。用 helm get values 查看 release 當前的實際 values。--set 很方便但容易打錯字，建議 CI/CD 中使用明確的 values 檔案。

# === Helm values 層級 ===
# 第一層：values.yaml（chart 內建預設）
#   replicaCount: 1
#   image.tag: latest

# 第二層：values/production.yaml（環境覆蓋）
#   replicaCount: 3
#   image.tag: v1.2.3

# 第三層：--set（最高優先，執行時指定）
helm upgrade my-app ./chart --values values/production.yaml \
  --set image.tag=v1.2.4 --set ingress.enabled=true

# === 查看目前已部署的 values ===
helm get values my-app -n <ns>          # 看使用者覆蓋的 values
helm get values my-app -n <ns> --all    # 看所有 values（含 chart 預設）

# === diff 檢查變更 ===
helm diff upgrade my-app ./chart --values values/production.yaml  # 需安裝 helm-diff plugin

💭 原理：Helm 使用 Go template 渲染 YAML，多層 values 透過 helm.sh/helm/v3/pkg/cli/values 的 MergeValues 合併。相同層級遇到 key 衝突時，後寫入者覆蓋前者。map 是深度合併，scalar 直接取代。

💡 Cloudflare DNS 管理：Proxy vs DNS only

Cloudflare DNS 有兩種模式：Proxy mode（橘雲）隱藏 origin IP，所有流量經過 Cloudflare 邊緣節點，提供免費 TLS、DDoS 防護、CDN 快取；DNS only（灰雲）單純解析 IP，流量直接連到 origin server。用 Cloudflare API 可以程式化管理 DNS records，適合自動化部署。

# === DNS 模式切換 ===
# 橘雲（Proxy）：隱藏 origin IP，走 Cloudflare CDN
# dig 會回傳 Cloudflare 邊緣 IP（104.x.x.x 等）
dig +short example.com

# 灰雲（DNS only）：直接解析到 origin IP
# 可在 Cloudflare Dashboard 切換，或透過 API

# === Cloudflare API 管理 DNS ===
# 取得 Zone ID（從 Dashboard 或 API）
ZONE_ID="your-zone-id"
API_TOKEN="your-api-token"

# 查詢 DNS records
curl -s -H "Authorization: Bearer $API_TOKEN" \
  "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records?type=A"

# 新增 A record（proxied=true=橘雲, false=灰雲）
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"www","content":"1.2.3.4","ttl":120,"proxied":true}'

💭 原理：橘雲模式下，Cloudflare 反代所有 HTTP(S) 流量，用戶看到的是 Cloudflare IP，origin 只接收 Cloudflare 的連線。這層 proxy 實現了 TLS termination、WAF 過濾、快取加速。DNS only 適合 SSH、API 等非 HTTP 服務。

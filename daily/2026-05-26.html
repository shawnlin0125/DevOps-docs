🐱 伺服器端全市場掃描系統部署（stock-analysis）

💡 hostPath Volume 動態檔案服務：無需重建容器即可更新內容

k3s hostPath volume 讓 Nginx 直接讀取 host 目錄中的檔案。掃描腳本寫入 host 路徑 /home/ubuntu/stock-analysis-data/ 後，Nginx 透過 volume mount 即刻提供最新 scan-results.json，無需 rebuild image 或 restart container。適合頻繁更新的靜態資料。

# k3s deployment.yaml 中的 volume 設定
volumes:
  - name: scan-data
    hostPath:
      path: /home/ubuntu/stock-analysis-data
      type: DirectoryOrCreate
volumeMounts:
  - name: scan-data
    mountPath: /usr/share/nginx/html/data

# 腳本直接寫入 host 路徑，Nginx 即刻提供新內容
python3 scan-all-stocks-v3.py  # 輸出 → /home/ubuntu/stock-analysis-data/scan-results.json
# 前端立即讀取：https://stock.shawnlin.online/data/scan-results.json

💭 原理：hostPath volume 不是複製，而是直接 mount host 目錄到容器內。所以 host 上的任何檔案變更，容器內立即可見。比 ConfigMap 適合大型或頻繁更新的檔案（ConfigMap 有 1MB 限制且更新需要 rollout），也比 rebuild image 快。

💡 API Rate Limit 實戰偵測與資料來源遷移策略

FinMind 免費 API 在發出 ~200-300 次請求後回傳 HTTP 403，回應 header 含 retry-after: 1239（約 20 分鐘），隨後 IP 完全被封鎖。yfinance 備案同樣被 rate-limit。最終遷移至 TWSE OpenAPI 解決：無 rate limit、不需 API token、官方資料更可靠。

# FinMind rate limit 被觸發時的典型回應
# HTTP 403 Forbidden
# retry-after: 1239  ← 需等 20 分鐘
# 約 183/1089 支股票後中斷

# 遷移策略：尋找官方、免認證、無 rate limit 的替代 API
# ✅ TWSE OpenAPI: openapi.twse.com.tw
# ✅ 無需 API key、無 rate limit
# ✅ 官方資料，準確度最高

💭 原理：API rate limit 是服務端保護機制（通常是 IP-based 或 token-based）。免費 API 通常有嚴格的 rate limit。生產環境的資料 pipeline 應優先選擇官方 API 或無 rate limit 的來源，避免在排程任務中觸發封鎖。

💡 TWSE STOCK_DAY_ALL：一次 API 呼叫撈全市場當日行情

TWSE OpenAPI 的 STOCK_DAY_ALL endpoint 單次呼叫回傳全部 ~1,361 檔上市股票的當日 OHLCV（開高低收量）。無需 auth token、無 rate limit。將原需 1000+ 次個別查詢的架構縮減為 1 次批量查詢 + 針對篩選標的補歷史資料。

# 一次呼叫取得全市場當日數據
curl "https://openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL"
# 回應: [{Code:"0050", Name:"元大台灣50", TradeVolume:"...", ...}, ...共 1361 筆]

# 篩選候選標的：股價 ≤ 150、成交量 ≥ 5000
# 878 檔進入第二階段：個別查詢歷史資料
curl "https://www.twse.com.tw/exchangeReport/STOCK_DAY?response=json&stockNo=2330&date=20260501"

# 每檔約需 4 次 API call（4 個月歷史），0.25s 間隔
# 總耗時約 45-50 分鐘（無 rate limit 阻斷）

💭 原理：批次 API（一次回傳全部）vs 逐筆 API（每筆一個 request）的效能差距是指數級的。STOCK_DAY_ALL 讓網路往返從 O(n) 降為 O(1)，這是 API 架構選擇的重大 DevOps 決策——直接影響執行時間和穩定性。

💡 長時間執行腳本的進度監控與中繼儲存設計

執行 45+ 分鐘的掃描腳本（878 檔股票），將進度寫入 /tmp/scan-status.json 並每 50 筆中繼儲存結果到輸出檔。解決 stdout 緩衝問題（pipe 模式下不即時 flush），同時提供 crash recovery 的 checkpoint 機制。

# 進度檔案格式
# /tmp/scan-status.json
# {"scanned": 120, "total": 878, "passing": 2, "eta_seconds": 2700}

# 查看即時進度
cat /tmp/scan-status.json | python3 -m json.tool

# 中繼儲存（每 50 筆寫一次）
# 確保崩潰後最多損失 50 筆進度
if scanned_count % 50 == 0:
    with open(output_path, 'w') as f:
        json.dump(results, f, ensure_ascii=False)
    with open('/tmp/scan-status.json', 'w') as f:
        json.dump(status, f)

💭 原理：stdout 是 line-buffered（TTY）或 fully-buffered（pipe/file），導致進度訊息在程式結束前看不到。寫入獨立檔案解決緩衝問題，同時提供可程式化讀取的狀態接口。中繼儲存則是 crash recovery 的基礎——損失上限 = checkpoint 間隔。

💡 CronJob 與底層腳本的耦合管理

當 CronJob 執行的腳本從 v1 升級到 v3 時，CronJob 的 command 欄位也必須同步更新（腳本路徑從 scan-all-stocks.py 變為 scan-all-stocks-v3.py）。解決方案：用固定路徑 symlink 指向最新版本，CronJob 永遠指向 symlink 不動。

# ❌ 耦合：CronJob 直接引用版本號
# CronJob command: ["python3", "/home/ubuntu/scripts/scan-all-stocks-v3.py"]
# 每次升級都要改 CronJob manifest → kubectl apply

# ✅ 解耦：用 symlink 抽象版本
ln -sfn /home/ubuntu/scripts/scan-all-stocks-v3.py /usr/local/bin/daily-scan
# CronJob command: ["python3", "/usr/local/bin/daily-scan"]
# 升級只要更新 symlink，CronJob 不變

💭 原理：這是經典的「介面隔離」模式——CronJob 不應知道腳本的版本號，只應知道「我要執行 daily-scan」。symlink 就是這個抽象層，把變動隔離在 CronJob 之外。

💡 k3s hostPath type: DirectoryOrCreate 的防呆機制

hostPath volume 的 type 設為 DirectoryOrCreate 時，若 host 目錄不存在，kubelet 會自動建立（權限 0755、owner root）。比 type: Directory 更安全——後者目錄不存在時 Pod 直接 CrashLoopBackOff。

# deployment.yaml — hostPath volume 定義
spec:
  volumes:
    - name: scan-data
      hostPath:
        path: /home/ubuntu/stock-analysis-data
        type: DirectoryOrCreate  # ← 關鍵：目錄不存在時自動建立

# type 對照表：
# DirectoryOrCreate  → 目錄不存在就建立（最常用）
# Directory           → 目錄必須已存在，否則 Pod 啟動失敗
# FileOrCreate        → 檔案不存在就建立
# File                → 檔案必須已存在
# ""  (空字串)        → 不做任何檢查（最不安全）

💭 原理：kubelet 在掛載 hostPath 前會檢查路徑是否存在。DirectoryOrCreate 讓 kubelet 執行 mkdir -p，避免「先手動建目錄再 deploy」的手動步驟——對 first-deploy 或 CI/CD 自動化部署特別重要。

💡 Python stdout 緩衝問題：pipe 模式下的輸出延遲

Python 的 stdout 在非 TTY 環境（pipe 到 tee、背景執行、cron job）時會啟用區塊緩衝（block buffering），導致 print() 輸出延遲數分鐘甚至到程式結束才出現。掃描腳本因此無法即時看到進度。

# ❌ 問題：背景執行時 print() 不即時輸出
python3 scan.py &  # stdout 被緩衝，看不到進度

# ✅ 解法一：強制行緩衝
import sys
sys.stdout.reconfigure(line_buffering=True)

# ✅ 解法二：寫入檔案（更可靠，適合長時間任務）
with open('/tmp/progress.json', 'w') as f:
    json.dump({"scanned": n, "total": 878}, f)
    f.flush()  # 確保寫入磁碟

# ✅ 解法三：命令列參數
python3 -u scan.py  # -u = unbuffered stdout/stderr

💭 原理：C 標準庫的 stdio 緩衝策略：TTY → line-buffered（遇到 \n 就 flush），pipe/file → fully-buffered（滿 4KB/8KB 才 flush）。Python 繼承這個行為。非 TTY 環境（cron、systemd、pipe）下要主動處理緩衝。

💡 批次處理的中繼檔案崩潰恢復模式

處理 878 筆資料的長時間任務，每 50 筆寫入一次中繼結果到輸出檔案。若程式崩潰，可從上次 checkpoint 繼續而非重頭開始。關鍵設計：中繼檔案格式與最終輸出完全相同，重啟時讀取最後 checkpoint 的進度接續處理。

# 中繼儲存模式（每 N 筆 checkpoint）
CHECKPOINT_INTERVAL = 50

for i, stock in enumerate(stocks):
    result = analyze(stock)
    if result and result['passing']:
        results.append(result)

    # 每 50 筆寫一次 checkpoint
    if (i + 1) % CHECKPOINT_INTERVAL == 0:
        with open(output_path, 'w') as f:
            json.dump(results, f)
        # 進度也寫到狀態檔
        with open('/tmp/scan-status.json', 'w') as f:
            json.dump({"scanned": i+1, "total": len(stocks)}, f)

# 崩潰後重啟：從 output_path 讀取已完成數量，skip 已處理的
if os.path.exists(output_path):
    existing = json.load(open(output_path))
    start_index = len(existing)  # 從這裡繼續

💭 原理：這是「原子寫入 + checkpoint」模式。每次 checkpoint 覆蓋整個輸出檔（原子操作），崩潰時檔案狀態是上一次完整 checkpoint。損失上限 = checkpoint 間隔（此例 50 筆 ≈ 2.5 分鐘）。

💡 k3s 資源請求與限制的實戰權衡：靜態 Nginx 為例

靜態 Nginx 站點的最佳化配置：requests 設最低值讓排程容易通過（10m CPU/32Mi RAM），limits 設合理上限防止失控（200m CPU/128Mi RAM）。requests 影響排程決策（資源不夠 = Pending），limits 防止容器吃垮節點。

# deployment.yaml — 靜態 Nginx 的保守資源設定
resources:
  requests:
    cpu: 10m       # 排程最低保證：1% CPU core
    memory: 32Mi   # 排程最低保證：32MB RAM
  limits:
    cpu: 200m      # 最多可用 20% CPU core（burst 上限）
    memory: 128Mi  # 超過 128MB → OOMKilled

# Nginx Alpine 靜態站點的實測用量
# idle: ~2-4MB RAM, ~0 CPU
# under load: ~15-20MB RAM, ~50m CPU

💭 原理：requests 是 scheduler 用來決定 Pod 該放哪個節點的依據（bin-packing），limits 是 kubelet 用來 enforce 的硬上限。靜態站點 RAM 需求極低且穩定，128Mi limits 已綽綽有餘；CPU 設 200m 給 burst 空間但不會真的吃滿。

💡 容器健康檢查參數的設計思維：liveness vs readiness

livenessProbe（決定是否重啟容器）用較寬鬆參數避免誤殺：initialDelaySeconds: 5 等容器啟動，periodSeconds: 30 降低檢查頻率。readinessProbe（決定是否送流量）用較靈敏參數快速反應：initialDelaySeconds: 3，periodSeconds: 10。

# deployment.yaml — 健康檢查參數設計
livenessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 5   # 等容器啟動（Nginx 約 1-2s 就 ready）
  periodSeconds: 30        # 30s 檢查一次（誤殺成本高，不需太頻繁）
  failureThreshold: 3      # 連續 3 次失敗才重啟（共 90s）

readinessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 3   # 更快開始檢查（流量應該早點進來）
  periodSeconds: 10        # 10s 檢查一次（靈敏度高，快速摘流量）
  failureThreshold: 3      # 連續 3 次失敗才摘除（共 30s）

💭 原理：liveness 和 readiness 的職責不同。Liveness 的「誤判」成本是殺掉一個活著的容器（服務中斷），所以參數要寬鬆。Readiness 的「誤判」成本只是暫時不送流量（不會中斷現有連線），所以可以更靈敏。

💡 kubectl top 看資源使用：即時用量 vs Scheduler 視角

kubectl top nodes 看每個節點的即時 CPU/RAM 用量百分比；kubectl top pods -A 看所有 Pod 即時用量（顯示實際使用值）；kubectl describe node | grep -A 8 Allocated 看 scheduler 視角的資源分配佔比（基於 Pod 宣告的 request/limit）。三者差異：top 顯示的是實際用量（即時的），describe Allocated 顯示的是 request/limit 的百分比（scheduler 根據這個決定能否排程新 Pod）。如果 Allocated resources 接近 100%，表示節點已滿無法排程新 Pod，即使 top 顯示實際用量很低。

# 1. 節點即時資源用量
kubectl top nodes
# NAME       CPU(cores)  CPU%   MEM(bytes)  MEM%
# k3s-node   250m        12%    4Gi         25%

# 2. 所有 Pod 即時用量（相當於 Linux top for Pods）
kubectl top pods -A

# 3. Scheduler 視角的資源分配（看 Allocated resources 區段）
kubectl describe node k3s-node | grep -A 8 Allocated
# Allocated resources:
#   Resource        Requests     Limits
#   cpu             950m         1800m
#   memory          6Gi          12Gi
# → 如果 node RAM=16Gi，requests=6Gi=37%，limits=12Gi=75%

# 4. 用 jsonpath 精確取值
kubectl describe node k3s-node | grep -A 8 Allocated | grep memory
kubectl get node k3s-node -o json | jq '.status.allocatable'

💭 原理：kubectl top 透過 metrics-server 向 kubelet 的 Summary API 查詢即時 cgroup 用量（取自 cgroups cpuacct/memory），數據有約 15 秒延遲。describe node Allocated 讀的是 Pod spec 中宣告的 requests/limits 總和，是 scheduler 在調度時的決策依據。兩者視角不同：top 看「現在用多少」，Allocated 看「最多能吃多少」。

💡 Docker 多階段建置縮小 Image：builder → runtime 瘦身法

多階段建置（multi-stage build）讓 Dockerfile 可以有多個 FROM 指令，每個 FROM 是獨立建置階段。第一個 stage（builder）安裝所有編譯工具和依賴做建置，第二個 stage（runtime）只複製最終 artifacts。這樣 runtime image 不必包含編譯器/套件管理工具。Go static binary 可用 FROM scratch（最小的 image，只有 binary），Node.js 可用 FROM node:alpine 搭配 standalone output。用 docker images | grep <name> 查看 image 大小差異。

# === Go 多階段建置範例 ===
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server

FROM scratch  # 最小 runtime：只有 binary
COPY --from=builder /app/server /server
# scratch 沒有 shell、沒有 ca-certificates、沒有時區資料
# 如果需要 SSL 證書：COPY --from=builder /etc/ssl/certs /etc/ssl/certs
CMD ["/server"]

# === Node.js 多階段建置範例 ===
FROM node:20 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build  # Next.js standalone output

FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/public ./public
CMD ["node", "server.js"]

# 查看 image 大小
docker images | grep my-app
docker image history my-app  # 看每一層大小

💭 原理：Docker image 由 overlay filesystem 層疊而成，每個 RUN/COPY 指令生成一個唯讀層。多階段建置讓 builder 階段的所有層在建置完成後被丟棄，只有最終階段（FROM scratch/alpine）的層被保留。--from=builder 語法讓你可以從前一個 stage 複製檔案，不保留該 stage 的任何層。scratch 是空的 filesystem（無 shell、無 libc），只有 static binary 可執行。

💡 systemd 服務管理：systemctl + journalctl 健康檢查

systemd 是主流 Linux 發行版的 init 系統，服務透過 unit file 管理。常用維運操作：systemctl list-units --state=failed 快速查看所有失敗的服務（一鍵找出問題服務）；journalctl -u <service> -n 50 --no-pager 看某個服務最近 50 行 log；修改 unit file 後一定要 systemctl daemon-reload 重新載入配置；systemctl restart <service> 是原子操作（stop 後立刻 start），而 stop + start 之間有空窗期。

# 1. 快速找問題服務
systemctl list-units --state=failed
# UNIT               LOAD   ACTIVE SUB
# my-app.service     loaded failed failed

# 2. 看服務最近 log
journalctl -u my-app.service -n 50 --no-pager

# 3. 看即時 log（等同 tail -f）
journalctl -u my-app.service -f

# 4. 重新載入 unit file（改完 .service 後必做）
sudo systemctl daemon-reload
sudo systemctl restart my-app.service

# 5. 啟用 / 停用開機自啟
sudo systemctl enable my-app.service
sudo systemctl disable my-app.service

# 6. 檢查服務狀態
systemctl status my-app.service
# → 看 Active: active (running) / exited / failed
# → 看 Main PID 和記憶體使用量

💭 原理：systemctl restart 實作是先發 SIGTERM 給主進程，等待它退出後立即啟動新進程。stop+start 中間有空窗期（其他請求可能因此連線失敗）。RestartForceExitStatus= 可在 unit file 中設定某些 exit code 會自動觸發 restart（類似 keepalive）。journalctl 讀的是二進位 binary journal 日誌（存在 /var/log/journal/），比傳統 text log 更省空間且支援結構化查詢。

💡 Helm values 分層覆蓋與 --set 陷阱

Helm values 有三層覆蓋機制，愈後面的層級優先：values.yaml（chart 預設值）← values/production.yaml（環境特定覆蓋）← --set key=value（CLI 即時覆蓋）。Helm 的 merge 是深層合併（deep merge），巢狀 map 會遞迴合併而不是直接取代。常見陷阱：--set 參數 typo 不會報錯，只會新增一個不存在的 key，導致 values 不如預期生效。用 helm template --debug 可以先看最終渲染的 YAML 來除錯。

# values.yaml（chart 預設值）
# replicaCount: 1
# image:
#   tag: latest

# values/production.yaml（環境覆蓋）
# replicaCount: 3
# image:
#   tag: v1.2.3

# 部署：三層覆蓋依序套用
helm upgrade my-app ./chart -n production \
  -f values/production.yaml \
  --set image.tag=v1.2.4

# 查看目前 release 實際生效的 values
helm get values my-app -n production

# 除錯：看最終渲染的 YAML（不實際部署）
helm template my-app ./chart -f values/production.yaml --debug

# 小心 --set 類型陷阱
# --set metrics.enabled=true 設定為字串 "true"（非 boolean true）
# 正確：--set metrics.enabled=true （Helm 會自動推斷 boolean）
# 但 --set-string 可強制為字串

# 注意：--set 不會報 typo 錯誤
# --set replciaCount=3  // typo，不報錯但 key 無效

💭 原理：Helm 的三層 values 透過 go-template 的 template.FuncMap 來實現語法渲染，使用 Helm 內建的 merge/overwrite 邏輯。--set 的 key 用點路徑解析（如 service.type），如果 typo 不存在，Helm 不會報錯，只會新增一個無效的 key。Helm 的 deep merge 與 Kubernetes strategic merge patch 不同：Helm 會遞迴合併巢狀 map，而 strategic merge 可根據 type 決定取代或合併。

💡 網路排查四指令：curl / dig / ss / nc 對應 OSI 四層

網路問題診斷的四把瑞士刀，從底層到應用層依序排查：curl -v http://host 看完整 HTTP 流程（應用層，含 SSL 握手、request/response header、redirect 追蹤）；dig +short domain 快速 DNS 解析（跳過 /etc/hosts 直接查 DNS）；ss -tlnp 看 TCP listening port 與所屬 process（取代 netstat，速度更快、資訊更完整）；nc -zv host port 純測試 TCP port 通不通（z=zero I/O 只測試連線不送資料）。建議排查順序由下往上：ss（本地 listening）→ dig（DNS）→ curl（應用層）。

# 1. listening port + process（取代 netstat）
ss -tlnp
# State   Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process
# LISTEN  0      128     0.0.0.0:80          0.0.0.0:*          users:(("nginx",pid=1234))
# LISTEN  0      128     0.0.0.0:443         0.0.0.0:*          users:(("nginx",pid=1234))

# 2. DNS 解析（跳過本地 /etc/hosts）
dig +short example.com
# 93.184.216.34            ← 回傳 A record
#  dig 的 +short 只顯示 IP，忽略 CNAME/NSSEC 等細節

# 3. TCP 連線測試（純測 port 通不通）
nc -zv example.com 80
# Connection to example.com port 80 [tcp/http] succeeded!
# -z：不送資料只測試連線；-v：顯示詳細資訊

# 4. HTTP/HTTPS 完整檢查
curl -v https://example.com
# * TCP_NODELAY set
# * Connected to example.com (93.184.216.34) port 443 (#0)
# * ALPN: offering h2
# * SSL handshake completed
# > GET / HTTP/1.1
# > Host: example.com
# < HTTP/1.1 200 OK
# < Server: nginx

# 5. 簡化版：只看 HTTP status code
curl -s -o /dev/null -w "%{http_code}" https://example.com
# 200

💭 原理：ss 從 /proc/net/tcp 和 /proc/net/tcp6 直接讀取 kernel socket 狀態，比 netstat 快（netstat 讀 /proc 多個檔案還要解析）。dig 直接查 DNS server（讀 /etc/resolv.conf 的 nameserver），跳過 /etc/hosts 和 nscd cache。nc -z 建立 TCP 連線後立即關閉（只做三次握手），如果連線成功表示 port 通了。curl -v 能看到 SSL/TLS 握手各階段的細節，是診斷 HTTPS 問題的最佳工具。

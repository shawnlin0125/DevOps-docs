💡 kubectl 診斷 Pod 啟動失敗的完整流程

Pod 啟動失敗時，按順序執行四步驟排查：kubectl get pods → kubectl describe pod → kubectl logs → kubectl get events。從 Status/Events 欄位判斷是 ImagePull（鏡像拉取失敗）、CrashLoopBackOff（容器不斷重啟）、OOMKilled（記憶體不足）還是 Pending（資源不夠排程）。

# 1. 看 Pod 狀態
kubectl get pods -n 

# 2. 看詳細事件（含 Error Reason、最後狀態）
kubectl describe pod  -n 

# 3. 看容器 stdout/stderr
kubectl logs  -n 
kubectl logs --previous  -n   # 看前一個實例的 log

# 4. 看叢集層級事件（過濾特定 namespace）
kubectl get events -n  --sort-by='.lastTimestamp'

💭 原理：kubectl describe 的 Events 段落記錄了 kubelet 對 Pod 的每一個操作與錯誤原因，是最快定位問題的入口。CrashLoopBackOff 表示容器啟動後立即退出，需看 logs 或 describe 的 Last State 欄位確認 exit code。

💡 Docker 多階段建置縮小 Image

多階段建置（Multi-stage build）讓一個 Dockerfile 包含多個 FROM 區段。build stage 安裝所有建置依賴（編譯器、npm、go mod），runtime stage 只複製編譯後的 artifacts，大幅縮小最終映像。Go 可 FROM scratch（靜態二進位完全不需要基礎映像），Node.js 則用 standalone output 搭配 alpine。

# === Go 多階段建置範例 ===
# Build stage
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# Runtime stage — 從 scratch 開始
FROM scratch
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]

# 查看 image 大小
docker images | grep

💭 原理：Docker image 是分層（layer）的，每個 RUN/COPY 產生一層。多階段建置只在 builder 階段產生編譯層，runtime 階段只複製最終檔案，builder 層全部丟棄，所以最終 image 只包含 runtime 必要的檔案。

💡 查 OOM 紀錄：dmesg + exit code 137

OOM Killer 會在系統記憶體不足時終止吃最多 RAM 的行程。用 sudo dmesg -T | grep -i oom 查看核心 OOM Killer 紀錄（含被殺的 process name、pid、oom_score）。Pod 被 OOM 殺掉時 exit code 為 137（SIGKILL），描述 Pod 中 Events 會顯示 OOMKilled。

# 查看 OOM Killer 核心紀錄
sudo dmesg -T | grep -i oom

# 檢查最近被殺的行程
sudo dmesg -T | grep -i "killed process"

# 看 Pod 是否因 OOM 被殺（kubectl describe 的 Last State 欄位）
kubectl describe pod  -n  | grep -A 5 "Last State"

# K8s 中 memory limits 總和 > 實體 RAM 時 OOM 會連鎖殺 Pod

💭 原理：OOM Killer 在核心記憶體耗盡時觸發，選擇 oom_score 最高的行程終止（通常是 RSS 佔用最多的）。在 K8s 中，Pod 超過 memory limit 會被 cgroup OOM Killer 殺掉（OOMKilled），不是節點層級 OOM Killer。

💡 GitHub PR 流程：gh CLI

GitHub CLI（gh）可在終端機完成完整的 PR 生命週期管理：建立 branch → commit → push → 開 PR → review → merge。使用 gh pr create 開 PR，gh pr review --approve 審核，gh pr merge --squash 合併。流程結束後切回 main 並 pull 最新。

# 完整 PR 流程
git checkout -b feature/xxx
git add . && git commit -m "feat: ..."
git push -u origin feature/xxx

# 開 PR（推薦用 Web 填 body 或 --fill）
gh pr create --title "..." --body "..." --fill

# 審核與合併
gh pr review --approve
gh pr merge --squash --delete-branch

# 回到 main
git checkout main && git pull

# 實用工具命令
gh pr list -A "@me"          # 看我開的所有 PR
gh pr checkout       # 切到 PR 分支看 code
gh pr diff                    # 看 PR 的程式碼差異

💭 原理：gh 透過 GitHub REST/GraphQL API 操作 PR，--squash 將所有 commit 壓成一個之後合併到 base branch，保持歷史整潔。--delete-branch 在合併後自動刪除遠端分支。

💡 Cloudflare DNS 管理：Proxy vs DNS only

Cloudflare DNS 記錄有兩種模式：Proxy mode（橙色雲朵）讓流量經過 Cloudflare CDN/WAF，隱藏 origin IP 並提供免費 TLS；DNS only（灰色雲朵）直接解析記錄指向原始 IP。用 Cloudflare API 可程式化管理 DNS 記錄。查詢方式：dig +short example.com 若回傳 Cloudflare IP 則為 Proxy mode。

# 查詢 DNS 記錄（用 dig 判斷是否經過 Cloudflare）
dig +short example.com
# 若回傳 Cloudflare IP 區段 → Proxy mode
# 若回傳真實伺服器 IP → DNS only

# 用 Cloudflare API 管理 DNS 記錄（需 API Token）
curl -s -X GET "https://api.cloudflare.com/client/v4/zones//dns_records" \
  -H "Authorization: Bearer " \
  -H "Content-Type: application/json" | jq .

# 新增 A 記錄（DNS only）
curl -s -X POST "https://api.cloudflare.com/client/v4/zones//dns_records" \
  -H "Authorization: Bearer " \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"www","content":"1.2.3.4","ttl":120,"proxied":false}' | jq .

# Proxy mode（proxied: true）
curl -s -X POST "https://api.cloudflare.com/client/v4/zones//dns_records" \
  -H "Authorization: Bearer " \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"www","content":"1.2.3.4","ttl":1,"proxied":true}' | jq .

💭 原理：Proxy mode（橘雲）讓 Cloudflare Anycast IP 作為反向代理，origin server 只需要允許 Cloudflare IP 範圍的連線。DNS only（灰雲）直接暴露 origin IP，適合不希望流量經過 Cloudflare 的場景（如 API 服務、WebSocket）。

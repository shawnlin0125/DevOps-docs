💡 kubectl exec 進 Pod 內排查

用 kubectl exec -it <pod> -n <ns> -- sh 進入容器內部，取得 shell 後用 env | grep -i 確認環境變數是否有正確注入（如 Secret/ConfigMap 對應的 ENV）、用 nc -zv <svc> <port> 測試到其他 Service 的連線是否通暢、用 cat /etc/resolv.conf 確認 Pod 內的 DNS 設定是否指向正確的 CoreDNS Cluster IP。

# 進入容器互動 shell
kubectl exec -it my-pod-5f4d8f9c-k8v7n -n default -- sh

# 常用診斷指令
env | grep -i
nc -zv my-service 8080
cat /etc/resolv.conf
wget -qO- http://my-service:8080/health

💭 原理：exec 是透過 kube-apiserver 的 subresource API 向 kubelet 發起容器 attach/exec 請求。-- sh 啟動 shell process 在 container 的 namespace 中，所以看到的網路/DNS/環境變數和應用程式完全一致。

💡 Linux 資源監控三指令：uptime / free / df

uptime 的 load average（1/5/15 分鐘）超過 CPU 核心數時，表示有行程在排隊等待 CPU。一般負載在 0.7 × 核心數以下算正常。用 nproc 或 lscpu 查看核心數。

free -h 的 available 欄位才是真正可用的記憶體（包含可回收的 cache/buffer）。不要只看 free 欄位，Linux 會把閒置 RAM 拿去做 page cache，free 很低不代表記憶體不夠。

df -h / 看根分割區使用率，超過 80% 就要注意，超過 90% 屬於危險。也用 df -i / 檢查 inode 使用率，inode 用滿了即使還有空間也無法建立新檔案。

uptime
# 輸出範例：load average: 0.32, 0.45, 0.51

free -h
# 看 available 不是 free

df -h /
df -i /

💭 原理：load average 是 CPU 排程佇列中 running + uninterruptible sleep 行程的平均數；available = free + page cache + slab reclaimable；df -i 顯示的是 inode table 使用率，inode 在格式化時固定分配，小檔案過多會先耗盡 inode。

💡 Git 復原操作：reset / restore / reflog

git reset --soft HEAD~1 退回一個 commit 但保留 staging area 和工作區的改動。適合「commit 太快忘記加檔案」的情況──退回後補 add 再重新 commit。

git restore <file> 丟棄特定檔案的工作區改動，還原到 HEAD 版本。相當於舊版的 git checkout -- <file>。

git reflog 記錄所有 HEAD 移動歷史（含被 reset 掉的 commit），可以用 git reset --hard <sha> 救回誤刪的 commit。Reflog 是本地操作紀錄，只保留 90 天。

# 復原 commit 但保留改動內容
git reset --soft HEAD~1

# 丟棄工作區改動
git restore myfile.py

# 救回誤刪的 commit
git reflog
git reset --hard abc1234

💭 原理：--soft 只移動 HEAD 指標，不碰 index 和 working tree；--mixed（預設）移動 HEAD 並清空 index 但保留 working tree；--hard 移動 HEAD、清空 index 和 working tree（不可還原的改動）。reflog 是 .git/logs/HEAD 的文字記錄，每次 HEAD 變動就 append 一行。

💡 Helm values 分層覆蓋與 --set 陷阱

Helm values 有三層覆蓋順序（愈後面的層級優先）：values.yaml（chart 內建預設值）← values/production.yaml（環境特定覆蓋）← --set key=value（CLI 手動覆蓋）。後者會 merge 覆蓋前者的同名 key。

--set 覆蓋很方便但容易出錯：typo 沒人檢查、boolean/number 型態轉換可能非預期、list 覆蓋行為容易混淆。建議用 helm template --debug ... 先渲染 YAML 確認結果。

# 三層覆蓋範例
helm upgrade my-release ./chart \
  --values values/production.yaml \
  --set image.tag=v2.1.0 \
  --set resources.limits.memory=512Mi

# 除錯：先渲染看看
helm template my-release ./chart \
  --values values/production.yaml \
  --debug

💭 原理：Helm 的 merge 是深層合併（deep merge），巢狀 map 會遞迴合併而非覆蓋整個 map。--set 的值會先 parse 成 YAML 再 merge，因此 key 路徑中的點（.）可以穿透多層次結構。

💡 網路排查四指令：curl / dig / ss / nc

這四支指令涵蓋 OSI 四個層級的網路診斷：

1. curl -v http://host:port — 看完整 HTTP/HTTPS 流程。不僅測試連線，還能看到 SSL 握手細節、response header、錯誤訊息。加上 --connect-timeout 5 避免卡住。

2. dig +short domain — 快速 DNS 查詢。不加 +short 可以看到 DNS 回應的權威/遞迴路徑與 TTL。對比 Cloudflare Proxy（回傳 CDN IP）vs DNS only（回傳真實 IP）。

3. ss -tlnp — 列出所有 TCP listening port 與對應的 process。取代 netstat。四個參數：t( TCP)、l( listening)、n( 數字格式不反查 )、p( 顯示 process )。

4. nc -zv host port — 測試 TCP 連線是否通。z(zero I/O 不送資料)、v(verbose)。比 telnet 輕量，適合 script 中做 health check。

# HTTP/HTTPS 流程診斷
curl -v --connect-timeout 5 https://example.com

# DNS 查詢
dig +short example.com

# 看 listening port
ss -tlnp

# TCP 連線測試
nc -zv google.com 443

💭 原理：四支指令各自對應不同 OSI 層級──ss 看 L4（TCP）、nc 測 L4（TCP 連線）、dig 測 L7（DNS 是應用層）、curl 測 L7（HTTP/HTTPS 應用層）。由下往上排查：先確認 L4 通不通（ss/nc），再確認 DNS 解析（dig），最後測應用層（curl）。

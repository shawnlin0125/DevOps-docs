💡 kubectl 看資源使用：top / describe Allocated

當叢集出現資源壓力時，用三個指令從不同維度診斷。 kubectl top nodes 即時看每個節點的 CPU / Memory 實際用量；kubectl top pods -A 看所有 Pod 的即時資源消耗，快速找到吃最多的 Pod；kubectl describe node <node> | grep -A 8 Allocated 看 scheduler 視角的資源佔比（requests / limits 被排程時計算，不是即時用量）。三者缺一不可：top 告訴你「現在用多少」，describe Allocated 告訴你「K8s 認為這個節點被佔用了多少（不管實際上用不用）」，這差異就是 resource overcommit 的空間。

# 節點即時用量
kubectl top nodes
# NAME              CPU     MEMORY
# k3s-master        342m    3.5Gi
# k3s-worker1       1.2Gi   8.1Gi

# Pod 即時用量（找出吃資源大戶）
kubectl top pods -A
# NAMESPACE  NAME              CPU    MEMORY
# default    my-app-7d6f8      250m   1.2Gi
# kube-system traefik-xxx      120m   256Mi

# Scheduler 視角的資源佔比（requests/limits）
kubectl describe node k3s-worker1 | grep -A 8 Allocated
#   Namespace    Name              CPU Requests  CPU Limits  Memory Requests  Memory Limits
#   ──────────   ─────────────    ────────────   ──────────  ───────────────  ─────────────
#   default      my-app-7d6f8     250m (12%)     500m (25%)  1024Mi (12%)     2Gi (25%)
#   kube-system  traefik-xxx      100m (5%)      300m (15%)  128Mi (1%)       512Mi (6%)
#   Allocated resources:
#   CPU Requests: 350m (17%)   CPU Limits: 800m (40%)
#   Memory Requests: 1152Mi (13%)  Memory Limits: 2560Mi (31%)

💭 原理：kubectl top 從 Metrics Server 取得 cAdvisor 收集的即時資源使用數據；describe node 的 Allocated resources 則是 scheduler 根據 Pod spec 的 resources.requests 和 resources.limits 計算的「預訂量」— Pod 實際用得少但 request 已保留，這就是為何 requests 設太高會浪費資源、設太低會導致 overcommit 過度。

💡 Docker 多階段建置縮小 image

多階段建置（Multi-stage Build）是 Docker 最有效的 image 瘦身技巧：第一階段（build stage）包含完整 SDK / 編譯器 / 開發依賴來建置 artifacts；第二階段（runtime stage）只複製必要的 binary 或 artifacts，搭配極輕量的 base image。Go 語言特別適合 FROM scratch（static binary，最終 image 只有 binary 本身）；Node.js 可用 Alpine 搭配 standalone output。查看 image 大小用 docker images | grep <name>。

# === Go 多階段建置範例 ===
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server

FROM scratch
COPY --from=builder /app/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]
# → image 可能只有 10-15MB

# === Node.js 多階段建置範例 ===
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build    # 產生 standalone output

FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/public ./public
EXPOSE 3000
ENV NODE_ENV=production
CMD ["node", "server.js"]

# 查看 image 大小
docker images | grep my-app
# my-app    latest     abc1234    10 minutes ago   128MB
# （相比沒多階段：通常 1GB+）

💭 原理：Docker image 由多層（layer）組成，每個 RUN / COPY 指令產生一層。多階段建置讓最終 image 只包含 runtime stage 的 layer，builder stage 的所有 layer（Go SDK、npm cache、原始碼）在最終 image 中完全不存在。FROM scratch 是完全空的 base image，連 shell 都沒有，適合 static binary（Go / Rust）極致瘦身。

💡 systemd 服務管理：systemctl + journalctl

DevOps 日常維運中，systemd 是管理後台服務的核心工具。三個最常用的情境：systemctl list-units --state=failed 快速找出所有異常服務（比一個個檢查快很多）；journalctl -u <service> -n 50 --no-pager 查看特定服務最近 50 行 log（不加 -u 會看所有系統 log）；systemctl daemon-reload 在修改了 /etc/systemd/system/*.service 後必執行，否則 systemd 還是用舊的 unit file。結合 systemctl restart / enable / status 形成完整服務生命週期管理。

# 1. 快速找出所有失敗的服務
systemctl list-units --state=failed
# UNIT                    LOAD   ACTIVE SUB    DESCRIPTION
# vendor-scan.service     loaded failed failed Vendor Plugin Scanner

# 2. 看服務最近的 log
journalctl -u vendor-scan.service -n 50 --no-pager
# Jun 01 03:00:01 k3s-master vendor-scan.sh[1234]: ERROR: connection timeout
# Jun 01 03:00:02 k3s-master systemd[1]: vendor-scan.service: Main process exited, code=exited

# 3. 改完 .service 檔案後重載
sudo systemctl daemon-reload
sudo systemctl restart vendor-scan.service
sudo systemctl status vendor-scan.service

# 其他常用
sudo systemctl enable my-service    # 開機自動啟動
sudo systemctl disable my-service   # 取消開機啟動
sudo systemctl is-active my-service  # 檢查是否 running

💭 原理：systemd 是 Linux 的 init 系統（PID 1），管理所有服務的啟動、停止、監控、依賴關係。list-units 查詢 systemd 內部狀態機（loaded / active / failed）；journalctl 從 binary journal 檔案讀取結構化日誌（比純文字 log 多了 timestamp 索引、priority 過濾）；daemon-reload 強制 systemd 重新解析所有 unit file。journalctl 日誌預設保存在 /var/log/journal/，若磁碟空間不足會自動輪轉（rotate）。

💡 GitHub PR 流程：branch → commit → PR → merge

GitHub Pull Request 是 DevOps CI/CD 的工作流核心。標準流程：從 main branch 開出 feature branch → 開發 → commit → push → 開 PR（用 gh pr create）→ 等 CI 通過 → code review → merge。善用 gh CLI 直接在終端機操作 PR，不必開瀏覽器。merge 後切回 main branch 並 pull 最新 code。多人協作時，保持 PR 小而專注（single responsibility）能加速 review。

# === 完整 PR 流程 ===
# 1. 從最新的 main 開 branch
git checkout main
git pull origin main
git checkout -b feature/add-health-endpoint

# 2. 開發、commit、push
git add .
git commit -m "feat: add health check endpoint for k8s probes"
git push -u origin feature/add-health-endpoint

# 3. 開 PR（使用 gh CLI）
gh pr create \
  --title "feat: add health check endpoint" \
  --body "Adds /health and /ready endpoints for liveness/readiness probes" \
  --base main

# 4. 查看 PR 狀態
gh pr status
gh pr view --web    # 瀏覽器開啟

# 5. CI 通過 + review 後 merge（Squash and Merge）
gh pr merge feature/add-health-endpoint --squash --delete-branch

# 6. 回到 main 更新
git checkout main
git pull origin main

💭 原理：GitHub PR 本質是 request 要求 maintainer 將一個 branch 的 commits 合併到另一個 branch。gh CLI 透過 GitHub REST / GraphQL API 與 GitHub 互動，不需要瀏覽器。Squash merge 將 feature branch 上的多個 commits 壓成一個 commit 合併到 main，保持 git history 乾淨。--delete-branch 在 merge 後自動刪除遠端 branch，避免堆積。

💡 Cloudflare DNS 管理：Proxy Mode vs DNS Only

Cloudflare DNS 提供兩種模式控制流量路由，選擇會直接影響安全性和效能。Proxy mode（橘色雲朵）啟用 Cloudflare CDN 代理：所有流量經過 Cloudflare 邊緣節點，隱藏真實 Origin IP、提供免費 TLS / DDoS 防護 / WAF / 快取；DNS only（灰色雲朵）只做 DNS 解析，流量直接打到 Origin Server，Cloudflare 不代理。大部分生產服務建議用 Proxy mode，但以下情境需要 DNS only：SSH 連線（非 HTTP 流量無法代理）、Email SMTP / IMAP、TCP/UDP 非 Web 服務、以及 Websocket 有特殊限制時。

# 使用 Cloudflare API 管理 DNS 記錄
# API Token 需要 Zone:DNS:Edit 權限

# 建立 A record（Proxy mode，橘色雲）
curl -X POST "https://api.cloudflare.com/client/v4/zones/${ZONE_ID}/dns_records" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" \
  --data '{
    "type": "A",
    "name": "vendor-demo",
    "content": "43.167.10.119",
    "ttl": 120,
    "proxied": true
  }'

# 查詢 DNS 記錄
curl -s "https://api.cloudflare.com/client/v4/zones/${ZONE_ID}/dns_records?type=A&name=vendor-demo.shawnlin.online" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" | jq '.result[] | {name, content, proxied}'
# {
#   "name": "vendor-demo.shawnlin.online",
#   "content": "43.167.10.119",
#   "proxied": true
# }

# 切換模式（修改 proxied 欄位）
curl -X PATCH "https://api.cloudflare.com/client/v4/zones/${ZONE_ID}/dns_records/${RECORD_ID}" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" \
  --data '{"proxied": false}'

💭 原理：Proxy mode 時，Cloudflare 邊緣節點作為反向代理接收客戶端請求，同時與 Origin Server 建立獨立的 TCP+TLS 連線。客戶端看到的是 Cloudflare IP（104.16.0.0/12 等），Origin IP 對外不可見。DNS only 時，dig 查詢直接返回真實 IP，客戶端直連 Origin Server，Cloudflare 只做名稱解析。TLS 憑證在 Proxy mode 下由 Cloudflare 管理（Edge Certificate），支援自動 renew。

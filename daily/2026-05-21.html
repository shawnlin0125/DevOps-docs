💡 kubectl 進 Pod 內排查 — 環境變數、網路連線、DNS 診斷

當 Pod 看似 Running 但功能異常時，直接進 Pod 內部排查最快。用 kubectl exec -it <pod> -n <ns> -- sh 進入容器後，常用三個指令：env | grep -i 確認環境變數、nc -zv <svc> <port> 測網路連線、cat /etc/resolv.conf 確認 DNS 設定。

kubectl exec -it api-gateway-69b74d9878-qhpcl -n korean-staging -- sh
# 進 Pod 後
env | grep -i DATABASE
nc -zv user-service 3000
cat /etc/resolv.conf

💭 原理：kubectl exec 啟動容器內的 shell process（stdin/stdout 透傳），讓你直接在容器環境中驗證 — 環境變數來自 ConfigMap/Secret injection、DNS 來自 CoreDNS、網路受 NetworkPolicy 限制。

💡 k3s containerd 鏡像管理完整流程 — docker save → ctr import → kubectl apply

k3s 內建 containerd 而非 Docker daemon，本地鏡像需要用 docker save 匯出 tar，再用 k3s ctr images import 匯入 containerd image store。搭配 imagePullPolicy: Never 避免 k3s 嘗試從 registry 拉取。

docker build -t my-app:latest .
docker save my-app:latest -o my-app.tar
sudo k3s ctr images import my-app.tar
kubectl apply -f deploy.yaml
kubectl rollout restart deployment/my-app -n my-ns

💭 原理：k3s 用 containerd 作為容器 runtime，containerd 有自己的 image store（/var/lib/rancher/k3s/agent/containerd/），和 Docker 的 image store 完全獨立。ctr images import 就是橋接兩者的工具。

💡 查 OOM 紀錄 — dmesg + oom_score 機制

當 process 被 OOM Killer 殺掉，用 sudo dmesg -T | grep -i oom 查看 kernel log。OOM Killer 會挑 oom_score 最高的 process（通常是吃最多 RAM 的）。K8s 中 memory limits 總和超過 Node 實體 RAM 時，OOM 會連鎖殺 Pod。

sudo dmesg -T | grep -i oom | tail -20
# 看 process 的 oom_score
cat /proc/<PID>/oom_score
# 查哪個 Pod 被 OOMKilled
kubectl describe pod <pod> -n <ns> | grep -A 5 "OOMKilled"

💭 原理：Linux kernel 在記憶體耗盡時啟動 OOM Killer，根據 oom_score（綜合 RSS、swap、cgroup 限制等計算）選擇 victim。K8s 的 memory limit 轉化為 cgroup limit，超出則觸發 OOM，Pod 狀態變為 OOMKilled。

💡 GitHub PR 完整流程 — branch → push → gh pr create → merge → pull main

標準 GitHub PR 流程：從 main 開 feature branch → 修改 → commit → push → gh pr create 建立 PR → 等待 review → 通過後用 gh pr merge 合併 → 切回 main 並 pull 最新。

git checkout -b feature/add-login
# ... 修改檔案 ...
git add . && git commit -m "feat: add login page"
git push -u origin feature/add-login
gh pr create --title "Add login page" --body "Implements OAuth login flow"
# 等 review 通過後
gh pr merge --squash feature/add-login
git checkout main && git pull

💭 原理：PR 的核心是「code review gate」— 讓變更在被合併進 main 前經過審查。gh CLI 直接呼叫 GitHub REST API，省去開瀏覽器的步驟。--squash 合併會把所有 commit 壓成一個乾淨的 commit，適合功能分支。

💡 Cloudflare DNS 管理 — Proxy vs DNS only、API 自動化

Cloudflare DNS 有兩種模式：Proxy（orange cloud）隱藏 origin IP + 免費 TLS + DDoS 防護，但只支援 HTTP/HTTPS port；DNS only（gray cloud）直接解析到 server IP，適用於非 HTTP 服務（如 SSH、SMTP）。可用 Cloudflare API 自動化管理 DNS records。

# 建立 proxied CNAME（orange cloud）
curl -X POST "https://api.cloudflare.com/client/v4/zones/{ZONE_ID}/dns_records"   -H "Authorization: Bearer {API_TOKEN}"   -H "Content-Type: application/json"   -d '{"type":"CNAME","name":"app","content":"shawnlin.online","proxied":true}'

# 建立 DNS-only A record（gray cloud）
curl -X POST "https://api.cloudflare.com/client/v4/zones/{ZONE_ID}/dns_records"   -H "Authorization: Bearer {API_TOKEN}"   -H "Content-Type: application/json"   -d '{"type":"A","name":"direct","content":"43.167.10.119","proxied":false}'

💭 原理：Proxy 模式時，DNS 查詢返回 Cloudflare edge IP 而非你的 origin IP，請求經過 Cloudflare CDN 後再轉發到 origin。這等於多了一層反向代理，提供免費的 TLS termination 和 DDoS 防護。

📂 K3s 叢集疑難排解（6 個 issue）

💡 ErrImageNeverPull：imagePullPolicy + Docker Hub 路徑的致命組合

Helm --set 覆蓋 image 為 Docker Hub 路徑，但 k3s containerd 只有本地 :latest → pod 永遠起不來，且消耗 ResourceQuota

kubectl get pods -n korean-staging | grep ErrImage
kubectl describe pod <pod> -n korean-staging | grep -A5 Events
kubectl set image deployment/api-gateway api-gateway=api-gateway:latest -n korean-staging
helm upgrade korean-staging ./helm/korean-learning -f values/staging.yaml --set apiGateway.image=api-gateway:latest -n korean-staging

💭 imagePullPolicy: Never 是最嚴格的模式——kubelet 絕不 pull，只找本地 containerd。Helm 的 --set 覆蓋是 silent killer：不會報錯，只會讓 Pod 永遠 ImagePullBackOff

💡 ResourceQuota 耗盡：僵屍 ReplicaSet 偷偷吃 quota

8+ 個舊 ReplicaSet 消耗 CPU 2800m/3000m，新 rollout 全部 blocked。解法：kubectl delete replicaset 清理

kubectl get replicasets -n korean-staging
kubectl get quota -n korean-staging
kubectl delete replicaset <old-rs> -n korean-staging

💭 Deployment 每次 rollout 都留一個舊 ReplicaSet（預設保留 10 個）。如果舊 RS 的 Pod 卡在 ImagePullBackOff，quota 就被無效 Pod 佔據。清理後 quota 從 2800m 降到 2300m

💡 Grafana sidecar OOMKilled：32Mi → 128Mi 除錯過程

monitoring-quota 要求所有容器宣告 limits，但 Grafana Helm chart 的 sidecar 預設 resources: {}。先補 32Mi → OOMKilled → 調到 128Mi 才穩定

kubectl get events -n monitoring | grep OOMKilled
kubectl patch deployment monitoring-grafana -n monitoring --type='json' -p='[{"op":"replace","path":"/spec/template/spec/containers/1/resources","value":{"limits":{"memory":"128Mi"},"requests":{"memory":"16Mi"}}}]'

💭 k8s-sidecar 在掃描 ConfigMap 時會載入所有 dashboard JSON 到記憶體，32Mi 不夠。RM OOM 的 sidecar 會拖垮 Grafana 主容器（同一個 Pod）——導致 Prometheus alert 一直響

GrafanaOOMKilledResourceQuotamonitoring

💡 ReadWriteOnce PVC lock：單節點 k3s 必須 scale down 再 up

Grafana PVC 使用 ReadWriteOnce，rolling update 時新舊 Pod 同節點搶 PVC → init container chown Permission denied

kubectl scale deployment monitoring-grafana -n monitoring --replicas=0
# 等待 PVC released
kubectl scale deployment monitoring-grafana -n monitoring --replicas=1

💭 ReadWriteOnce 只允許一個 Node 上的 Pod 同時掛載。單節點 k3s 的 rolling update 嘗試新 Pod 在同節點啟動時，PVC 還被舊 Pod 鎖住，必須先 scale to 0 釋放

KubernetesPVCReadWriteOncedebuggingk3s

💡 ArgoCD ApplicationSet CRD：k3s annotation 262KB 限制

kubectl apply 裝 ApplicationSet CRD 時超過 k3s 的 262144 bytes annotation 限制；用 --server-side 繞過 client-side validation

kubectl apply -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/crds/applicationset-crd.yaml
# 失敗 → 改用 server-side apply
kubectl apply --server-side -f applicationset-crd.yaml

💭 k3s 把 Kubernetes resource 存在 SQLite，single-row 大小限制約 262KB。CRD 的 annotations（含 OpenAPI schema）容易超過。--server-side 跳過 client 端檢查，直接送 API Server

ArgoCDCRDk3sApplicationSet

💡 alert-checker.py exit code：alerts found ≠ error

alert-checker.py 發現 alert 時 sys.exit(1)，cron 系統判為 failure。改成 sys.exit(0)：找到 alert 是正常運作，不是錯誤

# alert-checker.py 修改
# Before: sys.exit(1)
# After:  sys.exit(0)  # alerts found is normal operation

💭 cron 系統根據 exit code 判斷成功/失敗。exit 1 會觸發 error handling（retry、log、通知）。找到 alert 是預期行為，不應該回報失敗

📂 ArgoCD GitOps 部署

💡 ArgoCD v3.4.2 在 k3s 部署

用官方 install.yaml 部署 ArgoCD 到 argocd namespace，7 個 pods 約 123Mi RAM + 11m CPU

kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d

💭 ArgoCD 是 GitOps 的核心：Git repo 是 single source of truth，ArgoCD 持續比對 cluster state vs git state，有差異就標示 OutOfSync

ArgoCDGitOpsk3s部署

💡 ArgoCD 308 redirect loop + Cloudflare TLS 修復

Cloudflare 做 TLS termination（HTTPS→HTTP），ArgoCD 強制 redirect HTTP→HTTPS 造成無限 redirect。解法：server.insecure=true

kubectl patch configmap argocd-cm -n argocd --patch '{"data":{"server.insecure":"true"}}'
kubectl patch configmap argocd-cmd-params-cm -n argocd --patch '{"data":{"server.insecure.enabled":"true"}}'
kubectl annotate ingress argocd -n argocd nginx.ingress.kubernetes.io/force-ssl-redirect-

💭 Cloudflare 做 TLS termination 後，到 origin 的流量是 HTTP。ArgoCD 看到 HTTP request 就 redirect 到 HTTPS（自己），但 Cloudflare 再轉成 HTTP...無限迴圈。server.insecure=true 告訴 ArgoCD：接受 HTTP request，不要 redirect

ArgoCDCloudflareTLSredirect loop

💡 ArgoCD Application 的 ignoreDifferences：保護現有 Secret

用 ignoreDifferences 排除 postgres-secret 和 jwt-secret，避免 ArgoCD 把 k3s 中的實際密碼覆寫成 Git 裡的 placeholder

# app-korean-learning.yaml
spec:
  ignoreDifferences:
  - group: ""
    kind: Secret
    name: postgres-secret
    jsonPointers:
    - /data

💭 Git 裡不該存明文密碼（即使 base64）。ArgoCD 如果不知道要忽略 Secret 的差異，會把 k3s 裡的正確密碼覆寫成 Git 裡的 template 值——生產災難

📂 Plugin-hub Go 重寫

💡 Python/FastAPI → Go 重寫：255MB → 134MB image

Plugin-hub 從 Python/FastAPI 重寫為 Go (net/http)，Docker image 縮小 47%，idle RAM ~50MB → <10MB，binary 只有 8.3MB

# Go build
CGO_ENABLED=0 go build -ldflags="-s -w" -o plugin-hub .
# Docker: 2-stage, final stage FROM scratch
# Result: 8.3MB binary, 7.86MB compressed

💭 Go static binary 不需要 runtime（不像 Python 需要 interpreter + pip packages）。FROM scratch 的 Docker image 只有 binary 本身，沒有 OS layer

GoPython重寫Docker效能

💡 Plugin 排程架構：APScheduler in-process vs Celery/Kafka

每個 vendor plugin 自己管理 APScheduler，不依賴 central message queue。Platform 只做 switchboard（routing + toggle），不做排程

💭 Central scheduler（Celery/Kafka）增加 infra 複雜度和耦合；in-process APScheduler 每個 plugin 自給自足，platform 完全不碰排程邏輯——clean separation of concerns

💡 Telegram Forum Topic 路由：thread_id 不連續

Telegram supergroup 的 forum topic ID 不是連續數字（1,2,4,7,8,652），不能猜，必須用 send_message list 查實際 ID

💭 Telegram 的 topic ID 是內部 ID，被刪除的 topic 的 ID 不會回收重用。652 這麼大表示之前有很多 topic 被建立又刪除

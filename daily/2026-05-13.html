  1. Cron job 搜尋昨天的 DevOps 對話
  2. LLM 分析對話、提取知識點
  3. 產生 daily/YYYY-MM-DD.html
  4. 更新 index.html 的 day-card 列表
  5. git add → git commit → git push

hostPath Volume 優化

原始設計將 HTML 內嵌於 Docker 映像，每天更新需要 rebuild image。改為使用 hostPath volume mount：

volumes:
  - name: docs-content
    hostPath:
      path: /home/ubuntu/projects/devops-docs
      type: Directory
volumeMounts:
  - name: docs-content
    mountPath: /usr/share/nginx/html
💡 關鍵學習：對頻繁更新的靜態內容，hostPath 直接掛載遠比每次 rebuild Docker 映像更高效。Cron job 只需要 git pull + 寫入檔案，nginx 就能立即服務最新內容。

2. Telegram 監控告警路由修正

發現 Prometheus Alert Checker 的告警訊息出現在 General topic，但應該去 #infra（基礎設施/監控專用 topic）。

根因：cron job 的 deliver: "origin" 設定將輸出送到「建立 cron job 時所在的 topic」。當初在 General (thread 1) 建立，所以 alert 一直送到那裡。

Telegram Topic 探索：

  1. 查 ~/.hermes/channel_directory.json — 只有 General (thread 1)
  2. 用 send_message 測試 thread 2~10，發現 2、4、7、8 存在
  3. 發送測試訊息請使用者辨識每個 thread 對應的 topic 名稱

最終 Topic 地圖：

Thread IDTopic 名稱用途
1General一般討論
2#korean韓文平台開發/部署
4#infra伺服器/k3s/安全/監控
7#gitopsArgoCD/Flux
8#research工具/架構/討論
💡 關鍵發現：Telegram topic 的 thread_id 不一定是連續的。刪除 topic 後重建可能跳號。不要假設 ID=2,3,4,5... 一定要逐個測試。

修正方式：使用 cronjob(action='update') 將 delivery target 改為 telegram:-1003966564424:4（#infra topic）。

3. K3s 叢集疑難排解馬拉松（6 個問題修復）

使用者要求檢查並修復 k3s 叢集上的所有問題，一次處理了 6 個不同層面的故障。

3.1 korean-staging：Rolling Update 卡住 (ErrImageNeverPull)

現象：api-gateway 和 user-service deployment 有新 pod 處於 ImagePullBackOff。

根因：imagePullPolicy: Never 搭配不存在於本地的映像標籤 shawnlin0125/*:af305049...。舊 pod 仍正常運行（服務未中斷），但新 pod 無法啟動。

修復：Deployment 自動 rollback，手動清理 orphan pods 和 8+ 個 stale ReplicaSet。

⚠️ 教訓：使用 imagePullPolicy: Never 的部署，必須確保映像已透過 k3s ctr images import 匯入到 containerd。Rollout 前務必驗證映像存在。

3.2 ResourceQuota 超限

現象：korean-staging-quota 的 CPU 使用率 2800m/3000m、Memory 1408Mi/1536Mi，新 pod（korean-learning、quiz-service、vocab-service）無法排程。

根因：Stale ReplicaSet 佔用 quota 配額。

修復：清理 stale RS 後，CPU 降至 2300m/3000m，Memory 降至 1152Mi/1536Mi。

3.3 Grafana Init Containers 缺少 Resource Limits

現象：Grafana deployment 無法創建 pod。monitoring-quota 要求所有容器宣告 limits/requests，但 Helm chart 的 sidecar 和 init container 使用 resources: {}。

修復：手動 patch deployment，為 grafana-sc-dashboard、grafana-sc-datasources（sidecar）和 init-chown-data（init container）加上 resource limits。

關鍵步驟：需要先 scale down 到 0 再 scale up 到 1，因為 ReadWriteOnce PVC 無法同時被兩個 pod 掛載（舊 pod 的 init container chown 在 Permission denied 時卡住）。

💡 Kubernetes 知識點：使用 ReadWriteOnce PVC 時，更新 Deployment（rolling update）會先啟動新 pod。如果新舊 pod 在同一個 node 上（單節點 k3s），第二個 pod 無法掛載已綁定的 PVC，導致 init container 失敗。解決方案：先 scale down 到 0，釋放 PVC，再 scale up。

3.4 ArgoCD ApplicationSet CRD 遺失

現象：argocd-applicationset-controller CrashLoopBackOff，錯誤 no matches for kind "ApplicationSet"。

根因：ArgoCD 安裝時 applicationsets.argoproj.io CRD 因為 k3s 的 annotation 大小限制（262KB）未能成功建立。

修復：手動 apply CRD manifest（需先 strip oversized annotations），然後刪除 crashing pod 觸發重啟。

💡 K3s 限制：k3s 對 Kubernetes 資源的 annotation 總大小有 262,144 位元組的限制（與 etcd 的預設值相關）。大型 CRD manifest 若 annotations 過多會失敗。解決方案：手動 strip 非必要的 metadata annotations。

3.5 Grafana Sidecar OOMKilled（32Mi → 128Mi）

現象：修復 #3 後，grafana-sc-dashboard 和 grafana-sc-datasources 持續 OOMKilled → CrashLoopBackOff。Prometheus 告警 PodCrashLooping 持續觸發。

根因：初次設定的 memory limit 32Mi 太小。k8s-sidecar 掃描 ConfigMap 時需要更多記憶體。

修復：將 sidecar memory limit 提升至 128Mi（requests 16Mi、CPU 5m request / 10m limit）。Pod 恢復 3/3 Running，restart count 歸零。

ContainerCPU RequestCPU LimitMem RequestMem Limit
grafana (main)50m200m128Mi256Mi
grafana-sc-dashboard5m10m16Mi128Mi
grafana-sc-datasources5m10m16Mi128Mi
init-chown-data10m50m16Mi32Mi
⚠️ 教訓：sidecar 容器的資源 limit 不能太保守。k8s-sidecar 在掃描 ConfigMap/Secret 時有明顯的記憶體峰值。建議至少 128Mi，生產環境可設 256Mi。

3.6 Alert Checker Exit Code 修正

問題：alert-checker.py 在發現告警時 exit code 為 1，導致 cron 系統標記為 "failed"。

修復：sys.exit(1) → sys.exit(0)。有告警時輸出內容到 stdout（exit 0），無告警時 silent。這樣 cron 不會誤報 failure。

4.2 308 Redirect Loop 問題解決

問題：透過 Cloudflare → ingress-nginx 存取 ArgoCD 時出現 308 無限 redirect。

根因：ArgoCD 預設強制 HTTPS redirect，但 TLS 已在 Cloudflare 層處理（Cloudflare ↔ 伺服器是 HTTP）。

三步修復：

  1. 設定 argocd-cm ConfigMap：server.insecure: "true"
  2. 設定 argocd-cmd-params-cm ConfigMap：server.insecure: "true"
  3. 移除 Ingress 的 nginx.ingress.kubernetes.io/force-ssl-redirect annotation
💡 架構知識：當 TLS 在反向代理層（Cloudflare）終止時，後端服務（ArgoCD）應關閉自身的 HTTPS 強制跳轉。這適用於所有有 Cloudflare orange cloud 的服務。

4.5 ignoreDifferences 保護 Secrets

syncPolicy:
  syncOptions:
    - RespectIgnoreDifferences=true
ignoreDifferences:
  - group: ""
    kind: Secret
    name: postgres-secret
    jsonPointers:
      - /data/password
      - /data/jwt-secret

這個設定確保 ArgoCD 不會覆寫已在叢集中手動設定的密碼。避免 Git repo 中的 placeholder 值覆蓋真實密碼。

⚠️ 注意：ignoreDifferences 保護的資源在 UI 上會永遠顯示 OutOfSync（因為實際值與 repo 不同）。這是預期行為，不是 bug。目前使用 Manual sync 策略，尚未啟用 auto-sync。

5. Plugin-hub Go 重寫：Python → Go 的資源優化之旅

將 plugin-hub 平台從 Python/FastAPI 重寫為 Go (net/http stdlib)，動機是「AI 負責寫程式碼，語言選擇應以部署效率為優先，而非開發者偏好」。

5.1 資源對比

指標Python/FastAPIGo (net/http)改善
Docker 映像大小255 MB134 MB-47%
執行檔大小N/A (interpreted)8.3 MB (binary)-
閒置記憶體~50 MB<10 MB-80%
💡 語言選擇思考：Go 勝過 Rust（AI 迭代速度不足）和 Python（資源使用過高）。因為 AI 負責程式碼生成，語言選擇應該優化部署足跡（image size、RAM、startup time）而非開發者生產力。這是 AI-assisted development 時代的新思維。

5.2 排程架構決策

Platform 不處理排程。Plugin-hub 只是一個「總機」（switchboard）：發現、路由、開關 plugin。

方案記憶體決策
Celery150-300 MB❌ 太重
Kafka1-2 GB❌ 太重
APScheduler (in-process)~0 MB extra✅ 採用

每個 vendor plugin 內部使用 APScheduler，透過 start()/stop() lifecycle hooks 管理排程。

🛠️ 涉及指令與工具

K3s / Kubernetes

  • kubectl get pods -A | grep -v Running — 快速找出所有異常 pod
  • kubectl describe pod <name> -n <ns> — 查看 pod 事件和錯誤原因
  • kubectl get replicasets -n <ns> — 列出 ReplicaSet（檢查 stale RS）
  • kubectl delete replicaset <name> -n <ns> — 清理 stale ReplicaSet
  • kubectl scale deployment <name> -n <ns> --replicas=0 — 釋放 PVC 鎖定
  • kubectl get quota -n <ns> — 檢查 ResourceQuota 使用率
  • kubectl patch deployment <name> -n <ns> --type='json' -p='[...]' — JSON patch 更新 deployment
  • kubectl apply -f <crd.yaml> — 手動安裝 CRD（k3s 需要 strip 大型 annotations）
  • k3s ctr images import <image.tar> — 將 Docker 映像匯入 k3s containerd
  • kubectl get --raw /apis/argoproj.io/v1alpha1 — 驗證 CRD 是否註冊

ArgoCD

  • argocd login argocd.shawnlin.online --username admin --password ... --insecure — CLI 登入
  • argocd repo add https://github.com/... --type git — 連接 Git 倉庫
  • kubectl edit cm argocd-cm -n argocd — 設定 server.insecure: "true"
  • kubectl edit cm argocd-cmd-params-cm -n argocd — 設定命令列參數
  • kubectl apply -f argocd/app-korean-learning.yaml — 建立 Application
  • argocd app sync korean-learning — 手動觸發同步

DevOps / 部署

  • gh (GitHub CLI) — snap install gh、gh auth login、gh repo create
  • git add / commit / push — 版本控制
  • docker build -t devops-docs:latest . — 建置映像
  • Cloudflare API — 建立 CNAME record（POST /zones/:id/dns_records）

Hermes / Cron

  • cronjob(action='list') — 列出所有排程
  • cronjob(action='update', job_id=..., deliver=...) — 更新 delivery 目標
  • cronjob(action='create', name=..., schedule=..., prompt=...) — 建立新排程

🔧 對話：Gateway 基礎設施診斷與 Cron 排程管理

10:20–10:39 AM · Shawn 進行了一連串基礎設施維護：Cron 排程通知從 Telegram 遷移到 Discord、Gateway 崩潰根因分析、systemd 重啟機制深入調查

⚠️ 5/16 事故回顧：Gateway 從 5/16 13:44 到 5/17 10:07 關閉了將近 20 小時。原因是有人執行了 systemctl stop && sleep 3 && systemctl start，導致 Restart=always 被停用。本日對話的核心就是徹底理解這個事故的根因與預防方法。

💡 systemctl stop 會「管理員手動停止」標記，讓 Restart=always 失效

systemd 的 Restart=always 只在「非預期退出」時觸發。當你手動執行 systemctl stop，systemd 會標記此服務為「管理員主動停止」，從此不再自動重啟——直到下一次 systemctl start。如果 start 因為什麼原因失敗（例如 stop 還沒跑完），服務就永久停擺。這就是 5/16 gateway 崩潰 20 小時的根因。

# ❌ 危險做法 — 會讓 Restart=always 永久失效
systemctl --user stop hermes-gateway && sleep 3 && systemctl --user start hermes-gateway

# ✅ 安全做法 — 原子操作，不標記為「手動停止」
systemctl --user restart hermes-gateway

# 確認服務的 Restart 設定
systemctl --user show hermes-gateway | grep -E 'Restart=|ActiveState=|SubState='

# 如果已經被標記為手動停止，先 reset-failed 再 restart
systemctl --user reset-failed hermes-gateway
systemctl --user restart hermes-gateway

💭 原理：systemd 內部用 ActiveState=inactive + SubState=dead 記錄手動停止，這兩個狀態的組合會 suppress Restart=always。而 systemctl restart 本質是「先 stop 再 start」，但 systemd 將它視為一個原子操作——中間的 stop 不會寫入「管理員停止」標記。

💡 RestartForceExitStatus=75：應用程式用 exit code 告訴 systemd「這是計畫內重啟」

一般 process crash 時 exit code 是非零值（如 SIGKILL 的 137、SIGSEGV 的 139），systemd 的 Restart=always 會自動重啟。但如果應用程式「自己決定要重啟」（例如收到 SIGUSR1 後完成 graceful drain），它可以用一個特殊的 exit code（75 = EX_TEMPFAIL）告訴 systemd：「我沒壞，我只是需要重啟」。透過 RestartForceExitStatus=75，systemd 知道這個 exit code 也應該觸發自動重啟。

# systemd service unit 中的關鍵設定
[Service]
Restart=always
RestartForceExitStatus=75       # exit 75 也要觸發自動重啟
RestartSec=60                   # 重啟前等待 60 秒
TimeoutStopSec=210              # stop grace period 最長 210 秒
KillMode=mixed                  # 先 SIGTERM main process，逾時才殺 cgroup
ExecReload=/bin/kill -USR1 $MAINPID  # reload = 發送 SIGUSR1 訊號

💭 原理：RestartForceExitStatus 是 systemd 的「白名單」——預設只有 exit code 0（成功）不會觸發重啟。你可以透過這個設定把特定的 exit code 加入「視為正常重啟訊號」的清單。75（EX_TEMPFAIL）來自 sysexits.h，原意是「暫時性失敗，稍後重試」，恰好對應 graceful restart 的語意。

💡 SIGUSR1 優雅重啟機制：drain → exit 75 → systemd 接管

Hermes Gateway 的 /restart 指令不會直接砍掉 process，而是：先發送 shutdown 通知給所有活躍 session → 等待 drain timeout（讓 agent 完成進行中的工作）→ 標記中斷的 session 為 resume_pending（下次啟動自動恢復）→ 殺掉 tool subprocess → 中斷所有 adapter 連線 → 用 exit code 75 退出 → systemd 偵測到 exit 75 → 自動重啟。偵測是否在 systemd 下運行是透過 INVOCATION_ID 環境變數。

# 從 CLI 觸發優雅重啟（等同於 /restart slash command）
hermes gateway restart

# 檢查是否在 systemd 下運行（Python）
import os
under_systemd = "INVOCATION_ID" in os.environ
# under_systemd = True → 使用 exit(75) 路徑，讓 systemd 重啟
# under_systemd = False → 使用 detached subprocess（setsid + bash）

💭 原理：這是一個經典的「協商式重啟」模式——應用程式不是被外部 kill，而是自己決定何時退出。SIGUSR1 是 POSIX 保留給應用程式自訂義的訊號，systemd 的 ExecReload 用它來觸發 graceful drain。整個流程中沒有一個「暴力 kill」環節，確保不會丟失進行中的 session。

💡 Gateway drain timeout：在重啟過程中保存進行中的 session

Gateway 重啟時不是直接砍掉所有連線，而是有一個可配置的 restart_drain_timeout。流程：通知所有活躍 session「Gateway 即將重啟」→ 給 agent 一段時間完成目前的工作 → 逾時後強制中斷 → 將這些 session 標記為 resume_pending，reason 記錄為 "restart_timeout" → Gateway 啟動後自動恢復這些 session。5/16 事故中 Gateway 花了 74 秒 drain，但 sleep 3 根本不夠。

# config.yaml 中設定 drain timeout
agent:
  restart_drain_timeout: 120  # 給 agent 最多 120 秒完成工作

# 觀察 Gateway 的 drain 行為（從 journal）
journalctl --user -u hermes-gateway --since "2026-05-16 13:44" --no-pager | grep -E 'drain|shutdown|restart|exit'

# 檢查 session 是否被標記為 resume_pending
grep -r "resume_pending" ~/.hermes/sessions/ | head -5

💭 原理：Drain timeout 在「使用者體驗」和「重啟速度」之間做取捨。太短 = agent 工作被中斷（使用者要重來）；太長 = 重啟等太久。120 秒對大多數 agent 任務足夠，但對長時間 build/deploy 任務可能仍不夠——因此才需要 resume_pending 機制讓這些 session 在重啟後自動接續。

💡 Cron 排程通知從 Telegram 遷移到 Discord：delivery 格式轉換

將三個現有 Cron Job（Uptime Watchdog、Prometheus Alert Checker、DevOps Daily Learning Doc）的通知從 Telegram 全部遷移到 Discord 的 #hermes-schedule 頻道。Telegram 的 delivery 格式是 telegram:chat_id:thread_id，Discord 則是 discord:channel_id。同一個 cron job 可以切換 delivery 對象而不影響排程本身。

# 查看目前所有 cron job
hermes cron list

# 更新 delivery target（以 DevOps Daily Learning Doc 為例）
# 從 Telegram:   deliver: "telegram:-1003966564424:652"
# 改為 Discord:   deliver: "discord:1505392265793765538"
hermes cron update 8b8efe7cf28e --deliver "discord:1505392265793765538"

# Discord channel ID 對照表（從 channel_directory.json 取得）
# 1505392265793765538 → #hermes-schedule
# 1505394329135349881 → #hermes-infra
# 1505393856235966475 → #hermes-general
# 1505394862722388109 → #hermes-research

💭 原理：delivery 是一個與 cron job 執行邏輯完全解耦的欄位。修改 delivery 只改變「結果送到哪裡」，不影響排程本身、不影響搜尋行為、不影響 prompt。這種解耦設計讓基礎設施變更（例如從 Telegram 搬到 Discord）可以最小化影響範圍。

💡 Cron job 錯過執行窗口的 grace period 與 fast-forward 機制

當 Cron Job 錯過排程時間（例如 5/17 03:00 的 DevOps 學習筆記因 Gateway 關閉 20 小時而錯過），排程器有一個 2 小時的 grace period。如果能在 2 小時內恢復，job 會補執行；超過 2 小時則 fast-forward 到下一個排程時間（5/18 03:00）。也可以手動用 hermes cron run 強制觸發補執行。

# 手動觸發錯過的 cron job
hermes cron run 8b8efe7cf28e

# 查看 cron job 的上次/下次執行時間
hermes cron list --verbose

# 典型情況：
# Last run: 2026-05-16 03:00 ✅（前一天正常）
# Next run: 2026-05-18 03:00（5/17 的 window 因 gateway down 錯過，已 fast-forward）
# → 手動 hermes cron run 可在當天補執行

💭 原理：Grace period 設計是為了解決「短暫故障後補救」。假設 gateway 重啟只花了 10 分鐘，那錯過 03:00 的 job 在 03:10 就能補執行。但如果 gateway 關了 20 小時（超過 2h grace），繼續補執行昨天的任務就沒意義了——昨天已經過了，不如等下一次排程。這是一個務實的 fail-forward 設計。

💡 Config YAML 的 ambiguous match 陷阱：patch 工具找出 3 個相同字串

嘗試用 patch 工具把 config.yaml 中的 free_response_channels: '' 改為 free_response_channels: '1505393856235966475' 時失敗了。原因：這個字串在 config.yaml 中出現 3 次（telegram、discord、mattermost 三個平台段落各一次），patch 工具無法判斷要改哪一個。解法：提供更多前後文讓匹配唯一，或改用 env var。

# ❌ 失敗的 patch — 因為 old_string 不唯一
old_string: "free_response_channels: ''"
new_string: "free_response_channels: '1505393856235966475'"
# → Error: Found 3 matches. Provide more context to make it unique.

# ✅ 解法 A：提供更多前後文確保唯一匹配
old_string: |
  discord:
    require_mention: true
    free_response_channels: ''
new_string: |
  discord:
    require_mention: true
    free_response_channels: '1505393856235966475'

# ✅ 解法 B：改用 env var（不碰 config.yaml）
echo 'DISCORD_FREE_RESPONSE_CHANNELS=1505393856235966475' >> ~/.hermes/.env
hermes gateway restart

💭 原理：這是 config-as-code 的常見陷阱——當多個段落共用相同的 key 名稱時，基於字串比對的 patch 會 ambiguous。避免方法：(1) 永遠提供足夠的上下文字串讓匹配唯一；(2) 優先使用 env var 做單一平台的設定覆蓋（env var 是 key-value，不存在 ambiguous）；(3) 考慮用結構化 parser（如 yq）而非文字 replace 來改 YAML。

💡 Discord free_response_channels：兩種設定方式，env var 比 config.yaml patch 更安全

讓 Hermes Bot 在 Discord 頻道中不需要 @mention 就能回應，有兩種方式：(1) 在 ~/.hermes/.env 中設定 DISCORD_FREE_RESPONSE_CHANNELS=channel_id；(2) 在 ~/.hermes/config.yaml 的 discord: 段落設定 free_response_channels: 'channel_id'。兩者效果相同，但 env var 更安全（不會有 ambiguous match 問題），改完後需要 hermes gateway restart 才會生效。

# 方法 1：env var（推薦 — 不會有 ambiguous match）
echo 'DISCORD_FREE_RESPONSE_CHANNELS=1505393856235966475' >> ~/.hermes/.env
hermes gateway restart

# 方法 2：config.yaml（需確保 patch 唯一）
# 在 discord: 段落中：
discord:
  free_response_channels: '1505393856235966475'  # #hermes-general 不需 @mention

# 多個頻道用逗號分隔
DISCORD_FREE_RESPONSE_CHANNELS=1505393856235966475,1505394862722388109

# 檢查是否生效
grep FREE_RESPONSE ~/.hermes/.env
hermes gateway restart
# 在 #hermes-general 中直接發訊息測試（不加 @mention）

💭 原理：Discord adapter 在收到訊息時會檢查：(1) 是否有 @mention → 永遠回應；(2) 是否在 free_response_channels 名單中 → 不需 @mention 也回應；(3) 是否在 auto_thread 頻道中且已在 thread 內 → thread 內的後續訊息不須 @mention。三者是 OR 關係，任一條件滿足即回應。

💡 Bash function 定義順序陷阱：rollback() 被呼叫時尚未定義

在 upgrade_tomcat.sh 中發現一個 bug：rollback() 函數定義在腳本底部，但在前面的 smoke test 失敗區塊就被呼叫了。Bash 是直譯語言，逐行執行——當執行到 rollback 呼叫時，函數尚未被解析。在 set -e 模式下這會直接報錯退出。解法：把 rollback() 定義移到所有呼叫點之前。

# ❌ Bug：rollback() 定義在底部，但 smoke test 區塊在前面就呼叫了
# Step 8: smoke test
if ! curl_test; then
    rollback  # ← 這裡呼叫 rollback，但函數定義在更下面！
fi

# ... 中間很多程式碼 ...

# Step 9: rollback 函數定義（太晚了！）
rollback() {
    echo "回滾中..."
    ln -sfn "$OLD_HOME" "$BASE_DIR/tomcat"
    su - $TOMCAT_USER -c "$OLD_HOME/bin/startup.sh"
}

# ✅ 修正：把函數定義移到所有呼叫點之前
rollback() {
    echo "回滾中..."
    ln -sfn "$OLD_HOME" "$BASE_DIR/tomcat"
    su - $TOMCAT_USER -c "$OLD_HOME/bin/startup.sh"
}

# ... 其他程式碼 ...

# Step 8: smoke test — 現在可以安全呼叫 rollback 了
if ! curl_test; then
    rollback
fi

💭 原理：Bash 不像 Python/JavaScript 有 hoisting——函數必須在「被呼叫之前」就被解析。當直譯器遇到 rollback 時，如果還沒讀到 rollback() { ... } 定義，就會報 command not found。在 set -e（遇到任何錯誤即退出）下，這等於腳本直接崩潰。好的習慣是把所有函數定義放在腳本最前面。

💡 Bash 變數命名一致性：TARGET_FOLDER vs NEW_HOME 的教訓

腳本中同時用了 TARGET_FOLDER（有時帶 fallback ${TARGET_FOLDER:-apache-tomcat-${TOMCAT_VERSION}}）和 NEW_HOME 來表示同一個概念：新版本的 Tomcat 目錄。兩個變數名稱不一致導致維護困難——改了一個忘了另一個。解法：統一使用 NEW_HOME 作為唯一名稱。

# ❌ 混亂：兩個變數指向同一個概念
TARGET_FOLDER="${BASE_DIR}/apache-tomcat-${TOMCAT_VERSION}"
NEW_HOME="${BASE_DIR}/apache-tomcat-${TOMCAT_VERSION}"

# ✅ 統一：只用一個變數
NEW_HOME="${BASE_DIR}/apache-tomcat-${TOMCAT_VERSION}"
OLD_HOME=$(readlink -f "${BASE_DIR}/tomcat")
BACKUP_DIR="/root/tomcat-backup-files/${TOMCAT_VERSION}"

# 養成好習慣：變數命名原則
# - 用 _HOME 後綴表示目錄路徑（如 NEW_HOME, OLD_HOME, BASE_DIR）
# - 用 _DIR 後綴表示備份/暫存目錄（如 BACKUP_DIR, LOG_DIR）
# - 用 _WAIT 後綴表示等待秒數（如 SHUTDOWN_WAIT, STARTUP_WAIT）
# - 用 _USER 後綴表示系統帳號（如 TOMCAT_USER）

💭 原理：Bash 沒有 compile-time type check，變數名稱的語意完全靠人維護。當兩個名稱指向同一個概念時，未來修改的人（很可能是 3 個月後的你自己）必須先理解「這兩個其實是同一個東西」才能安全修改。統一名稱等於幫未來的自己減少認知負擔。

💡 5-phase DevOps 部署工作流：從 bug fix 到 production deploy 的結構化路徑

從昨天的腳本最佳化到今天，形成了一個標準化的 5-phase 部署流程：Phase 1 (Fix Bugs) → Phase 2 (Customize) → Phase 3 (Secrets) → Phase 4 (Test) → Phase 5 (Deploy)。每個 phase 有明確的交付物，phase 之間有依賴關係（沒修完 bug 不該部署、沒設定 secrets 不該測試）。這是一個可套用到任何服務升級的通用框架。

# Phase 1: Fix bugs — 在部署前先把已知問題修掉
#  ☐ 移動 rollback() 定義到呼叫點之前
#  ☐ 統一 TARGET_FOLDER → NEW_HOME

# Phase 2: Customize for environment — 對應公司實際環境
#  ☐ 擴充 CUSTOM_JARS（目前只有 fontrip.jar）
#  ☐ 確認 HEALTH_URL、LOG_DIR、config 檔案清單

# Phase 3: Configure secrets — CI/CD 管線需要的認證
#  ☐ GitHub repo → Settings → Secrets:
#     VM_SSH_KEY  (私鑰)
#     VM_USER     (SSH 登入帳號)
#     VM_HOST     (目標主機 IP)

# Phase 4: Re-test in Docker sandbox
#  ☐ VERSION=9.0.113 docker compose up -d
#  ☐ curl localhost:8888 → 確認 HTTP 200
#  ☐ 測試版本切換（9.0.113 → 9.0.114）

# Phase 5: Deploy via GitHub Actions
#  ☐ Actions tab → "Upgrade Tomcat" → Run workflow
#  ☐ 輸入 tomcat_version / target_host
#  ☐ 觀察 9-step 輸出 → 確認 smoke test 通過

💭 原理：這個 5-phase 框架的核心原則是「每個 phase 出錯只需回頭修正那個 phase，不會汙染後續 phase」。例如 Phase 2 的 CUSTOM_JARS 沒列完整，你只需要回到 Phase 2 補，不需要重新設定 secrets 或重做 Docker 測試。這種「失敗隔離」設計大幅降低部署的認知負擔和回滾成本。

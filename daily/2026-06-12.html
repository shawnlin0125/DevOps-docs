💡 kubectl 看資源使用：top + describe node

用 kubectl 快速掌握叢集資源狀態：kubectl top nodes 看各節點即時 CPU/RAM 用量，kubectl top pods -A 看各 Pod 實際消耗，kubectl describe node 的 Allocated resources 區塊顯示 request/limit 佔比（scheduler 視角）。三者須搭配使用才能完整掌握資源壓力。

# 節點即時 CPU/RAM 用量
kubectl top nodes
# NAME       CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
# node-01    850m         21%    6144Mi           38%

# 各 Pod 即時用量（跨 namespace）
kubectl top pods -A

# Scheduler 視角的資源佔比（request/limit）
kubectl describe node node-01 | grep -A 8 Allocated
# Allocated resources:
#   Resource           Requests    Limits
#   cpu                1800m/4000m 2500m/4000m
#   memory             2.5Gi/8Gi   4Gi/8Gi
# ↑ Requests 是保證量，Limits 是上限

# 各 Pod 的 requests/limits 總覽
kubectl get pods -A -o custom-columns=\
'NAMESPACE:.metadata.namespace,\
POD:.metadata.name,\
CPU_REQ:.spec.containers[0].resources.requests.cpu,\
CPU_LIM:.spec.containers[0].resources.limits.cpu,\
MEM_REQ:.spec.containers[0].resources.requests.memory,\
MEM_LIM:.spec.containers[0].resources.limits.memory'

💭 原理：kubectl top 讀取 metrics-server 彙整的即時數據（基於 kubelet cAdvisor），反映當下使用率。describe node Allocated 則是看 Pod spec 中聲明的 requests/limits — scheduler 用 requests 決定 Pod 能否排入節點，K8s 用 limits 做 cgroup 配額控制。兩者分別給出「實際壓力」和「理論容量」兩個維度。

💡 k3s containerd 鏡像管理完整流程

k3s 預設使用 containerd 而非 Docker daemon，所以 docker build 後的鏡像不能直接用 imagePullPolicy: Always 推送到 registry。標準流程是：docker build → docker save → sudo k3s ctr images import → kubectl apply。使用 imagePullPolicy: Never 或 IfNotPresent 讓 k3s 從本地 containerd image store 拉取。

# Step 1: 建置 Docker image
docker build -t my-app:20260612 .

# Step 2: 匯出 tar 檔
docker save my-app:20260612 -o my-app-20260612.tar

# Step 3: 匯入 k3s containerd
sudo k3s ctr images import my-app-20260612.tar

# 確認匯入成功
sudo k3s ctr images ls | grep my-app

# Step 4: 部署（imagePullPolicy: Never）
# deployment.yaml:
# spec:
#   template:
#     spec:
#       containers:
#       - name: my-app
#         image: my-app:20260612
#         imagePullPolicy: Never
kubectl apply -f deployment.yaml

# Step 5: 重啟 Pod 載入新版本
kubectl rollout restart deployment/my-app -n 
kubectl rollout status deployment/my-app -n 

# 一次完成：build + save + import + deploy
docker build -t my-app:latest . && \
  docker save my-app:latest -o my-app.tar && \
  sudo k3s ctr images import my-app.tar && \
  kubectl apply -f deployment.yaml

💭 原理：k3s 內嵌 containerd 作為容器 runtime，不用 dockerd。containerd 有自己的 image store（通常在 /var/lib/rancher/k3s/agent/containerd/）。docker save 將 image 層打包成 OCI tar，k3s ctr import 解壓到 containerd store。imagePullPolicy: Never 告訴 kubelet 不要嘗試拉取遠端 registry，直接從本地 store 找 image。

💡 systemd 服務管理

systemd 是 Linux 標準 init 系統，控制所有服務的生命週期。常用操作包括：查看失敗服務、讀取服務日誌、重新載入設定檔。熟練 systemctl + journalctl 是 Linux 維運基本功。

# 查看所有失敗的服務
systemctl list-units --state=failed
# UNIT                   LOAD   ACTIVE SUB    DESCRIPTION
# nginx.service          loaded failed Failed The nginx HTTP server

# 查看特定服務的最近日誌
journalctl -u nginx -n 50 --no-pager
# -n 50: 只看最近 50 行
# --no-pager: 直接輸出不分頁
# -u nginx: 只過濾 nginx.service

# 持續追蹤日誌（類似 tail -f）
journalctl -u nginx -f

# 重新載入 unit file 變更
sudo systemctl daemon-reload

# 服務控制
sudo systemctl restart nginx      # 完整重啟
sudo systemctl reload nginx       # 不中斷連線的重載設定
sudo systemctl enable nginx       # 開機啟動
sudo systemctl status nginx       # 看狀態 + 最近日誌

# 查服務的 dependency 樹
systemctl list-dependencies nginx

# 查看 service unit 檔案內容
systemctl cat nginx

💭 原理：systemd 以 unit 為核心管理單位（.service、.timer、.socket 等）。list-units --state=failed 掃描所有 active unit 中 SUB=failed 的服務。journald 收集所有 systemd 服務的 stdout/stderr 加上 kernel log，-u 過濾特定 unit。daemon-reload 通知 systemd 重新掃描 /etc/systemd/system/ 下的 unit 檔案變更。

💡 網路排查四指令：curl / dig / ss / nc

四個指令分別對應 OSI 模型不同層級的網路診斷：curl 測試 HTTP(S)/TCP（應用層+傳輸層）、dig 查 DNS（應用層/DNS 專用）、ss 看 socket 與 port（傳輸層）、nc 測任意 TCP/UDP port 通不通。熟練這四者能覆蓋 90% 以上的網路問題場景。

# 1. curl -v: 看完整 HTTP request/response header
curl -v https://example.com
# * SSL certificate verify ok.
# > GET / HTTP/2
# > Host: example.com
# < HTTP/2 200
# < server: nginx
# -v 會顯示 SSL 握手、request header、response header 全過程
# 常見用法：
curl -v http://host:8080/healthz          # 測 HTTP 服務
curl -I https://example.com               # 只看 response header

# 2. dig +short: 簡潔 DNS 查詢
dig +short example.com
# 93.184.216.34       ← 只顯示 A record IP
dig +short MX example.com                # 查郵件交換記錄
dig +short NS example.com                # 查 Name Server
dig example.com ANY +noall +answer        # 看所有 record types
nslookup example.com 8.8.8.8             # 指定 DNS server

# 3. ss -tlnp: 看所有 listening TCP port（取代 netstat）
ss -tlnp
# State   Recv-Q  Send-Q  Local Address:Port  Peer Address:Port  Process
# LISTEN  0       511     0.0.0.0:80          0.0.0.0:*          users:(("nginx",pid=1234))
# LISTEN  0       128     0.0.0.0:22          0.0.0.0:*          users:(("sshd",pid=5678))
# -t TCP, -l listening, -n 數字格式, -p 顯示 process
ss -tlnp | grep :443                       # 443 port 是誰在聽？
ss -tup                                   # TCP+UDP 連線狀態
ss -s                                     # socket 統計摘要

# 4. nc -zv: 測 port 通不通
nc -zv example.com 443
# Connection to example.com (93.184.216.34) 443 port [tcp/https] succeeded!
# -z: scan mode（不發送資料）, -v: verbose
nc -zv 10.0.0.1 22                        # 測內部 SSH port
nc -zv 10.0.0.1 3306                      # 測 MySQL port 是否開放
nc -vz 10.0.0.1 1-1000                    # 掃描 port range

💭 原理：curl -v 輸出 SSL/TLS 握手細節和 HTTP headers，適合診斷 HTTPS 問題。dig 直接查 DNS 權威伺服器，+short 省略雜訊只給答案。ss 讀取核心 socket table（/proc/net/tcp），比舊 netstat 更快更完整。nc 做原始 TCP 連線測試，不依賴應用層協定，是判斷防火牆/port 是否開放的最直接工具。

💡 Helm 常用操作：生命週期管理

Helm 是 K8s 套件管理工具，release 是 Helm 部署的一個應用實例。常用維運操作包括：列出所有 release、查看版本歷史、退回舊版、查看當前 values 設定。搭配 rollback 可以在部署出錯時快速恢復。

# 列出所有 namespace 的 release
helm list -A
# NAME    NAMESPACE  REVISION  UPDATED                 STATUS   CHART
# my-app  default    3         2026-06-12 10:00:00     deployed app-1.2.0

# 查看特定 release 的版本歷史
helm history my-app -n default
# REVISION  UPDATED          STATUS     CHART         DESCRIPTION
# 1         Jun 12 09:00     deployed   app-1.0.0     Install complete
# 2         Jun 12 09:30     deployed   app-1.1.0     Upgrade complete
# 3         Jun 12 10:00     deployed   app-1.2.0     Upgrade complete

# 退回指定版本
helm rollback my-app 2 -n default
# 退回 revision 2（app-1.1.0），Helm 會做 diff 然後只更新變更部分
helm rollback my-app 1 --wait --timeout 5m  # 等資源就緒

# 查看目前生效的 values
helm get values my-app -n default          # 只看使用者自訂值
helm get values my-app -n default --all    # 含 chart 預設值
helm get manifest my-app -n default        # 看渲染後的 YAML

# 升級時測試（不實際部署）
helm upgrade --install my-app ./chart -f values/prod.yaml \
  --dry-run --debug

# 解除安裝 release
helm uninstall my-app -n default

💭 原理：Helm release 每次升級建立一個新 revision（版本號遞增），store 在 k8s Secret 中（helm list 會讀這些 Secret）。rollback 是用上一版本的 template + values 重新部署，等同於 helm upgrade --revision N。helm get manifest 可以看到最終渲染的 YAML，對 debug 非常有用。--wait 讓 helm 等待所有資源 Ready 才回傳。

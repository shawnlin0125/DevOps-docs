💡 kubectl 診斷 Pod 啟動失敗的完整流程

Pod 啟動失敗四步驟排查：kubectl get pods → describe pod → logs → get events。從 Status/Events 欄位判斷 ImagePullBackOff（鏡像不存在）、CrashLoopBackOff（容器不斷重啟）、OOMKilled（超過記憶體限制）、Pending（資源不夠排程）。describe 的 Events 段落記錄 kubelet 對 Pod 的每一個操作與錯誤原因，是最快定位問題的入口。

# 1. 看 Pod 狀態
kubectl get pods -n <namespace>

# 2. 看 Events 找錯誤原因
kubectl describe pod <pod-name> -n <namespace> | grep -A 10 Events

# 3. 看容器日誌
kubectl logs <pod-name> -n <namespace> --tail=50

💭 原理：Pod 的生命週期由 kubelet 管理，每個操作（拉取鏡像、掛載 Volume、啟動容器）都會寫入 Events 供診斷。

💡 k3s containerd 鏡像管理完整流程

k3s 用 containerd 而非 Docker daemon。離線部署流程：docker build 建置 → docker save 匯出 tar → k3s ctr images import 匯入 containerd → kubectl apply 部署。需設 imagePullPolicy: Never 避免 kubelet 嘗試遠端拉取。

# 建置並匯入 k3s containerd
docker build -t my-app:latest .
docker save my-app:latest | sudo k3s ctr images import -

# 確認已匯入
sudo k3s ctr images ls | grep my-app

# 部署時指定不遠端拉取
# imagePullPolicy: Never

💭 原理：k3s 內嵌 containerd 作為容器 runtime，沒有 Docker registry 環境時，需將鏡像直接匯入本地 containerd image store。

💡 查 OOM 紀錄：dmesg + exit code 137

OOM Killer 挑 oom_score 最高的行程終止。核心 OOM 紀錄用 dmesg -T | grep -i oom。exit code 137（SIGKILL）表示被 OOM 殺死。K8s 中 memory limits 總和超過節點 RAM 時 OOM 會連鎖殺 Pod。kubectl describe pod 的 Last State: OOMKilled 是 K8s cgroup 層級 OOM。

# 核心 OOM 紀錄
sudo dmesg -T | grep -i oom | tail -5

# K8s Pod OOM 判定
kubectl describe pod <pod-name> | grep -A 5 "Last State"

# 看節點記憶體壓力
free -h
kubectl top nodes

💭 原理：Linux OOM Killer 在系統記憶體不足時強制終止行程；K8s cgroup 層級的 OOM 則在 Pod 超過 memory limit 時觸發。

💡 GitHub PR 流程：gh CLI

gh CLI 簡化 PR 生命週期：開分支 → commit → push → gh pr create → merge → 刪除遠端分支。--squash 壓縮所有 commit 為一個，保持 main 歷史整潔。gh pr list 看待審核 PR，gh pr diff 看變更內容，gh pr checkout 切到 PR 分支。

# 完整 PR 流程
git checkout -b feature/my-feature
# ... make changes ...
git add . && git commit -m "feat: add awesome feature"
git push -u origin feature/my-feature

# 開 PR（自動填 title/body）
gh pr create --fill

# Merge 並清理
gh pr merge --squash --delete-branch
git checkout main && git pull

💭 原理：gh CLI 透過 GitHub REST/GraphQL API 操作 PR，用 --squash 合併讓 main 分支歷史保持線性且整潔。

💡 Cloudflare DNS 管理：Proxy vs DNS only

Proxy mode（橙色雲朵）讓流量經 Cloudflare CDN，隱藏 origin IP 並提供免費 TLS 終止；DNS only（灰色雲朵）直接解析到真實伺服器 IP。dig +short 回傳 Cloudflare IP 表示啟用 Proxy，回傳真實 IP 則是 DNS only。可透過 Cloudflare API 自動化管理 DNS records，適合 CI/CD 中動態更新 DNS。

# 確認是否啟用 Proxy mode
dig +short example.com
# 若回傳 Cloudflare IP（104.16.x.x / 172.64.x.x）= Proxy mode
# 若回傳真實伺服器 IP = DNS only

# Cloudflare API 更新 DNS（範例）
curl -X PUT "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records/$RECORD_ID" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"example.com","content":"1.2.3.4","ttl":120,"proxied":true}'

💭 原理：Proxy mode 利用 anycast 網路將流量導向最近的 Cloudflare edge，隱藏 origin IP 並防 DDoS；DNS only 則直接解析到原始 IP。

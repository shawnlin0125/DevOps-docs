📂 Next.js Docker 化 & K8s 部署

💡 Next.js standalone Docker 多階段建置

用 multi-stage Dockerfile：build stage 跑 npm ci + next build，runtime stage 只複製 standalone 輸出 + static 檔案，最終 image 72.9MB

# Dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=builder /app/public ./public
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
EXPOSE 3000
CMD ["node", "server.js"]

💭 build 階段包含 devDependencies（TailwindCSS 需要），runtime 只用 production deps + standalone 輸出，大幅縮小 image

Dockermulti-stageNext.js最佳化

💡 k3s containerd 鏡像匯入流程

k3s 使用 containerd 而非 Docker 的 image store；Docker build 後需手動匯入

sudo docker build -t korean-learning:latest .
sudo docker save korean-learning:latest -o /tmp/korean-learning.tar
sudo k3s ctr image import /tmp/korean-learning.tar
# 或用 pipe
sudo docker save korean-learning:latest | sudo k3s ctr images import -

💭 k3s 內建 containerd，不用 Docker registry；imagePullPolicy: Never 告訴 k3s 只用本地鏡像，不嘗試 pull

k3scontainerdDockerimagePullPolicy

💡 K8s Deployment + Service + Ingress 三層架構

Deployment 管理 Pod 生命週期，Service 提供穩定 ClusterIP，Ingress 處理外部 HTTP routing

kubectl create namespace korean-learning
kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml
kubectl apply -f k8s/ingress.yaml

💭 Deployment 提供 rolling update 和 self-healing；Service 的 ClusterIP 不隨 Pod IP 變動而變；Ingress 做 host-based routing 讓多個 domain 共用一組 ingress controller

KubernetesDeploymentServiceIngress

💡 K8s Pod 健康檢查：readiness probe

Deployment 設定 readiness probe 確保 Pod 真正 ready 後才接收流量

# deployment.yaml
spec:
  containers:
  - name: korean-learning
    readinessProbe:
      httpGet:
        path: /
        port: 3000
      initialDelaySeconds: 5
      periodSeconds: 10

💭 沒有 readiness probe 的話 Pod 一啟動就被 Service 加入 endpoint，但 app 可能還沒 ready（pending DB connection、warmup 等），造成 502 錯誤

Kubernetesprobereadinesshealth check

💡 Helm values 覆蓋：production vs staging 參數化

用 values/production.yaml 和 values/staging.yaml 區分環境設定，避免手動改 YAML

helm upgrade --install korean-learning ./helm/korean-learning -f values/production.yaml -n korean-learning
helm upgrade --install korean-staging ./helm/korean-learning -f values/staging.yaml -n korean-staging

💭 Helm values 分層：values.yaml（預設）← values/production.yaml（覆蓋），不用維護兩份幾乎一樣的 manifest

📂 ingress-nginx 部署與 port conflict

💡 ingress-nginx Helm 安裝 + port conflict 解決

Helm 安裝 ingress-nginx 時遇到 80/443 被 Zeabur 佔用、8080 被系統 Nginx 佔用，最終用 8880/8443 + hostNetwork DaemonSet

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install ingress-nginx ingress-nginx/ingress-nginx \
  -f k8s/ingress-nginx-values.yaml
# values.yaml:
controller:
  kind: DaemonSet
  hostNetwork: true
  hostPorts: {http: 8880, https: 8443}
  containerPort: {http: 8880, https: 8443}
  service: {enabled: false}
  admissionWebhooks: {enabled: false}

💭 hostNetwork + DaemonSet 讓 ingress controller 直接綁定 host port 而非透過 NodePort/LoadBalancer；非標準 port（8880）是不得已的選擇，後續清掉 Zeabur 後改回 80/443

ingress-nginxHelmDaemonSethostNetworkport conflict

💡 Zeabur ingress controller 佔用 port 80/443

伺服器上 Zeabur 的 ingress controller（DaemonSet + hostNetwork）佔用了 80/443 port，導致標準 ingress-nginx 無法綁定

kubectl get daemonset -A | grep zeabur
kubectl get pods -A | grep ingress
sudo ss -tlnp | grep ':80\|:443'

💭 Zeabur 是之前安裝的 PaaS，其 ingress controller 處理 *.onzeabur.com 流量，佔用標準 port。移除 Zeabur 或讓它改用其他 port 才能還 80/443 給 ingress-nginx

💡 Cloudflare Tunnel → Cloudflare Proxy 遷移策略

從 cloudflared tunnel 遷移到 Cloudflare DNS proxy（orange cloud），需要 Origin Rule 把流量導向正確的 origin port

systemctl status cloudflared
# 停用 tunnel 後改用 DNS proxy
# Cloudflare Dashboard → DNS → A record @ → 43.167.10.119 (proxied)

💭 Tunnel 是 application-layer tunnel，proxy 是 DNS-level 代理。Proxy 模式更簡單、不需額外 daemon；但 free plan 缺少 Origin Rules 使得非標準 port 有問題

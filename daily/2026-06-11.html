💡 Linux 資源監控三指令：uptime / free / df

三個指令快速掌握伺服器健康狀態：uptime 看 CPU 負載趨勢，free -h 看記憶體實際壓力，df -h 看磁碟使用率。特別注意 Linux 記憶體管理慣例——available 才是真正的可用量。

# CPU 負載：看 load average
uptime
# 輸出範例：load average: 2.15, 1.80, 1.25
# 解讀：三個數值分別代表 1/5/15 分鐘平均。超過 CPU 核心數表示排隊中

# 記憶體：看 available 不是 free
free -h
#               total  used  free  shared  buff/cache  available
# Mem:           31G   18G   2.1G   1.2G       11G        12G
# ↑ free=2.1G 但 available=12G（OS 會釋放 cache 給應用）

# 磁碟：看使用率
df -h /
# Filesystem  Size  Used  Avail  Use%  Mounted on
# /dev/sda1   196G  145G   42G   78%    /
# 通常建議監控 > 80% 預警，> 90% 緊急處理

# CPU 核心數（判斷 load 是否超標）
nproc

💭 原理：Linux 會拿閒置 RAM 做 page cache（buff/cache），應用需要時 OS 可立即釋放，因此 free 很低不代表記憶體不足。available 是 OS 估算的真實可用量（free + 可回收 cache）。load average 超過核心數時表示 CPU 成為瓶頸。

💡 Cloudflare DNS 管理：Proxy vs DNS only

Cloudflare DNS 有兩種模式：Proxy mode（橙色雲朵）隱藏真實 IP 並提供免費 TLS/SSL 加速；DNS only（灰色雲朵）只做 DNS 解析。透過 Cloudflare API 可以自動化批量管理 DNS 記錄。

# 兩種模式比較
# 🌤️ Proxy (orange cloud)：
#   - 隱藏 origin server IP（Cloudflare 做反向代理）
#   - 自動提供 SSL/TLS（Flexible/Full/Full Strict）
#   - 啟用 CDN 快取、DDoS 防護、WAF
#   - 缺點：Cloudflare 到 origin 的 latency 不可避免
#
# ☁️ DNS only (gray cloud)：
#   - 直接解析到 origin IP
#   - 無 CDN/SSL/DDoS 保護
#   - 延遲最低（使用者直接連線）
#   - 適合內部服務或已有自訂防護的場景

# 透過 Cloudflare API 管理 DNS 記錄
# 列出所有 DNS 記錄
curl -s -X GET "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" | jq '.result[] | {name, type, content, proxied}'

# 新增 A 記錄（Proxy mode: proxied=true）
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"www","content":"203.0.113.10","ttl":120,"proxied":true}'

# 更新現有 DNS 記錄
curl -s -X PUT "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records/$RECORD_ID" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type":"A","name":"www","content":"203.0.113.20","ttl":120,"proxied":false}'

💭 原理：Proxy mode 下，DNS 解析返回 Cloudflare Anycast IP（而非 origin IP）。所有流量先經過 Cloudflare 邊緣節點（反向代理），由 Cloudflare 處理 SSL 終止、DDoS 過濾後再轉發到 origin。DNS only 則直接返回 origin 的真實 IP。

💡 Git stash 暫存管理

git stash 可暫時儲存未 commit 的改動，讓工作區變乾淨，之後再還原。適合在切 branch、pull 更新、或應急修 bug 前使用。stash 用 stack 結構（LIFO）儲存多組暫存。

# 暫存目前所有未 commit 的改動（untracked 檔案不加 -u 不包含）
git stash
# 等於：git stash push -m "WIP: xxx"

# 包含 untracked 檔案
git stash -u

# 列出所有暫存（最新的在最上面）
git stash list
# stash@{0}: On feature/xxx: WIP: add search
# stash@{1}: On feature/xxx: fix type error

# 還原最新暫存（同時從 stash 移除）
git stash pop

# 還原特定暫存
git stash apply stash@{1}  # 保留在 stash list 中
git stash pop stash@{1}    # 還原後移除

# 刪除暫存
git stash drop stash@{1}   # 刪除特定
git stash clear            # 清空所有暫存

# 只看暫存的檔名列表
git stash show -p stash@{0}

💭 原理：stash 本質上是一個特殊的 commit 引用，存在 .git/refs/stash 中。多次 stash 形成 stack 結構（stash@{N}），最新 push 的在最上面（stash@{0}）。pop = apply + drop，因兩個操作很常一起做。

💡 Docker 多階段建置縮小 Image

Dockerfile 中用多個 FROM 指令區分 build stage（裝所有 deps 做編譯）和 runtime stage（只複製 artifacts）。Go 可以 FROM scratch（static binary），Node.js 用 standalone output。大幅減少最終 image 大小。

# Dockerfile：Go 多階段建置（最小 image：~15MB）
# Stage 1: Build
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server .

# Stage 2: Runtime
FROM scratch
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]

# Dockerfile：Node.js 多階段建置
# Stage 1: Build deps + compile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build  # Next.js standalone 等

# Stage 2: Runtime（只留必要檔案）
FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/public ./public
EXPOSE 3000
CMD ["node", "server.js"]

# 查看 image 大小
docker images | grep <name>

💭 原理：每個 FROM 開始一個新 stage。只有 COPY --from=builder 的檔案會進入最終 image。建置工具（gcc、go toolchain、npm）留在 builder stage 不佔空間。Go 的 CGO_ENABLED=0 產生純靜態二進位，FROM scratch 即可執行。

💡 Helm values 分層覆蓋原則

Helm values 有三層覆蓋：Chart 內 values.yaml（預設值）← -f 載入環境檔案 ← --set CLI 覆蓋。後面的層級 merge 覆蓋前面的同名 key。用 helm get values 查看目前生效值。

# 分層覆蓋示範
# 1. values.yaml（Chart 內建，提供合理預設值）
# replicaCount: 1
# image:
#   tag: latest
# service:
#   port: 80

# 2. values/production.yaml（環境專用，覆蓋部分值）
# replicaCount: 3
# image:
#   tag: v1.2.3
# resources:
#   limits:
#     memory: 512Mi

# 3. CLI 部署時合併所有層
helm upgrade --install my-app ./chart \
  -f values/production.yaml \
  --set image.tag=v1.2.4 \
  -n production

# 查看最終生效值
helm get values my-app -n production          # 只看自訂值
helm get values my-app -n production --all    # 含預設值，顯示每層來源

# 預覽 template 渲染結果
helm template my-app ./chart \
  -f values/production.yaml \
  --debug

💭 原理：Helm 用後寫入覆蓋前值（last-write-wins）策略，以 YAML 的深層合併（deep merge）方式覆蓋。--set 優先級最高（在 -f 之後套用），但容易因 typo 出錯。建議 production 使用 -f 載入正式檔案，--set 只用於臨時測試或 CI 中動態參數。

💡 kubectl exec 進 Pod 內排查：env、nc、resolv.conf 三招

用 kubectl exec -it <pod> -n <ns> -- sh 或 bash 進入容器內互動排查。常用三指令：env | grep -i 確認環境變數是否正確設置、nc -zv <service> <port> 測試 TCP 連線是否通、cat /etc/resolv.conf 確認 Pod 內的 DNS 設定（nameserver/search domain）。

# 進 Pod 互動排查
kubectl exec -it  -n  -- sh

# Pod 內常用：確認環境變數
echo $ENV_VAR
env | grep -i KEYWORD

# Pod 內常用：測試 TCP 連線
nc -zv myservice.default.svc.cluster.local 8080

# Pod 內常用：確認 DNS
cat /etc/resolv.conf

# 檢查網路路由
ip route

💭 原理：exec 本質是向 kube-apiserver 發送 'attach' 請求，kubelet 在節點上用 crictl exec 建立容器內 process。nc -zv 發送 SYN 並等 ACK 確認連通性；cat resolv.conf 檢查 kubelet 基於 Pod spec 的 dnsConfig 注入的搜尋域和 nameserver。

💡 Docker 多階段建置縮小 Image（Multi-stage Build）

多階段建置將 Dockerfile 分為 builder stage（安裝編譯工具、下載 dependencies、編譯）和 runtime stage（只複製編譯後的 artifacts），大幅縮小 final image。Go 可 FROM scratch（靜態 binary 約 10MB），Node.js 用 alpine + standalone output。

# 多階段建置範例 Dockerfile
FROM golang:1.21 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o app

FROM alpine:3.18
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/app /app
CMD ["/app"]

# 查看 image 大小
sudo docker images | grep myapp
sudo docker image history myapp:latest

💭 原理：Docker image 由唯讀 layer 疊加而成。多階段建置的關鍵是 COPY --from=builder 只複製 artifacts，前一階段的所有工具 layer 都捨棄，最終 image 只有 runtime 所需的最小檔案。FROM scratch 連 shell 都沒有，最安全也最小。

💡 OOM Killer 診斷：dmesg + exit code 137 + kubectl describe

sudo dmesg -T | grep -i oom 查看核心 OOM Killer 記錄（含 oom_score 和被殺 process）。Exit code 137 = 128 + 9 (SIGKILL) 表示 process 被 kill。K8s 中 kubectl describe pod 的 Last State: OOMKilled 表示 cgroup 層級 OOM（Pod memory limits 觸發），而 dmesg OOM 是系統層級（節點實體記憶體不足）。

# 查系統 OOM 記錄
sudo dmesg -T | grep -i oom | tail -20

# K8s 看 Pod 是否 OOMKilled
kubectl describe pod  -n  | grep -A 5 "Last State"

# 看 exit code
kubectl get pods -n  -o wide

# 查看 oom_score（每個 process）
cat /proc//oom_score

💭 原理：Linux OOM Killer 在系統記憶體耗盡時啟動，根據 oom_score（基於 memory usage + oom_score_adj 加權）選擇分數最高的 process 殺掉。K8s 的 memory limits 透過 cgroup memory.max 控制，超限時直接 OOM kill 該 Pod 的 container 而非整個節點。Exit code 137 (128+9) 因 SIGKILL 無法被捕捉。

💡 GitHub PR 流程：gh CLI 終端機完整操作

用 gh CLI 在終端機完成 PR 全流程：git checkout -b feature/xxx → git commit → git push -u origin feature/xxx → gh pr create --title "..." --body "..." → gh pr merge --squash --delete-branch。不必開瀏覽器就能審查和合併。gh pr list 看所有 PR、gh pr checkout 切換到 PR branch、gh pr diff 看 diff。

# gh CLI PR 完整流程
git checkout -b feature/xxx
git commit -m "feat: ..."
git push -u origin feature/xxx
gh pr create --title "feat: xxx" --body "Closes #123"

# 審查
gh pr list
gh pr checkout 42
gh pr diff

# 合併
gh pr merge 42 --squash --delete-branch

# 回到 main 更新
git checkout main && git pull

💭 原理：gh CLI 使用 GitHub REST API v3 操作 PR（POST /repos/{owner}/{repo}/pulls）。--squash merge 將所有 commits 壓成一個 commit 到 main，保持線性歷史。--delete-branch 自動刪除遠端合併後的分支。gh 會自動設置 remotes 和 authentication。

💡 Helm values 分層覆蓋機制：values.yaml → 環境檔案 → --set

Helm values 有三層覆蓋鏈：values.yaml（chart 預設值）← values/production.yaml（環境覆蓋檔案）← --set key=value（CLI 參數）。後面層級 merge 覆蓋前面的同名 key。helm get values -n 可以看到合併後的最終 values。--set 方便快速測試但容易因 typo 出錯（Helm 不檢查 key 是否有效）。

# Helm values 分層覆蓋範例
helm install myapp ./chart -f values/production.yaml --set image.tag=v1.2.3

# 查看最終合併的 values
helm get values myapp -n production

# 查看 revision 歷史
helm history myapp -n production

# Helm 升級
helm upgrade myapp ./chart -f values/production.yaml --set replicas=5

# 回退
helm rollback myapp 3 -n production

💭 原理：Helm 使用 Go template + sprig functions 渲染 templates，values 合併使用 Helm 的 merge algorithm（deep merge）。--set 的 key 支援 dot notation（如 image.tag），但 Helm 不做 schema validation，typo 只會導致 template 渲染失敗（或變數被忽略）。建議 production 環境用檔案而非 --set。

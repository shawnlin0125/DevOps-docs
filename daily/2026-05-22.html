💡 kubectl 資源用量診斷 — top nodes / top pods / describe node Allocated 三層視角

診斷 K8s 資源瓶頸有三個層次：kubectl top nodes 看即時用量（CPU/RAM 百分比）、kubectl top pods -A 找吃資源最多的 Pod、kubectl describe node | grep -A 8 Allocated 看 scheduler 視角的 request/limit 佔比。三者互補：top 是即時快照、Allocated 是容量規劃。

# 節點即時用量
kubectl top nodes

# 所有 Pod 用量排序（找出資源大戶）
kubectl top pods -A --sort-by=memory | tail -10

# Scheduler 視角：request/limit 佔比
kubectl describe node k3s-master | grep -A 8 "Allocated resources"

💭 原理：top 讀的是 cgroup 的即時 metrics summary API（類比 Linux 的 top），describe Allocated 則是 scheduler 計算 request 總和除以節點 allocatable 容量（類比容量規劃報表）。兩者可能不同步 — top 顯示 30% 用量但 Allocated 可能已 95%（很多 Pod 設了 request 但實際沒用滿）。

💡 Docker 多階段建置縮小 image — build stage vs runtime stage、FROM scratch

多階段建置（multi-stage build）把編譯依賴留在 build stage，runtime stage 只複製最終 artifacts，大幅縮小 image。Go 靜態編譯甚至可以 FROM scratch（< 10MB）。Node.js 可用 standalone output + node:alpine。查看 image 大小：docker images | grep name。

# Go 多階段建置範例
FROM golang:alpine AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o server .

FROM scratch  # 或 alpine:3.21
COPY --from=builder /app/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]

💭 原理：Docker 的每一層 layer 都是唯讀的，build stage 的編譯工具鏈（golang:alpine ~300MB）在最終 image 中不需要 — 多階段建置讓這些 layer 不和最終 image 一起出貨。FROM scratch 是完全空的 filesystem，適合 static binary。

💡 Linux 資源監控三指令 — uptime / free -h / df -h 的正確讀法

快速診斷 Linux server 健康的三指令：uptime 看 load average 是否超過核心數（超過表示 CPU 排隊）、free -h 看 available 而非 free（Linux 會用閒置 RAM 做 cache）、df -h / 看磁碟使用率。三者 5 秒內就能判斷瓶頸方向。

# Load average vs 核心數
uptime
# 輸出: 03:00:00 up 10 days, 0.55, 0.40, 0.35
# → 核心數: nproc → 若 load > 核心數表示 CPU 忙碌

# 記憶體：看 available 不是 free
free -h
#               total   used   free   available
# Mem:          7.5Gi   3.5Gi  1.2Gi  4.0Gi
# → 真正可用 4.0Gi（含可回收的 cache/buffer）

# 磁碟使用率
df -h /
# Filesystem  Size  Used  Avail Use%
# /dev/sda1    50G   35G   15G  70%

💭 原理：Linux kernel 積極利用閒置 RAM 做 page cache 加速 I/O，所以 free 欄位低不代表不夠 — 需要時 kernel 會回收 cache。load average 是 runnable + uninterruptible sleep 的平均數（不只 CPU 排隊，還包含 I/O 等待），超過核心數 1~2 倍還可接受，超過 5 倍通常有問題。

💡 Git stash 暫存管理 — stash / stash pop / stash list

git stash 把目前的改動暫存到一個 LIFO stack 上，恢復乾淨 working tree。需要切 branch 但不想 commit 時很好用。還原用 git stash pop（取出並刪除 stash）或 git stash apply（取出但保留 stash）。git stash list 看所有暫存。

# 暫存目前所有改動（含 staged 和 unstaged）
git stash

# 暫存時加訊息（推薦）
git stash push -m "WIP: halfway through refactoring auth"

# 查看所有 stash
git stash list
# stash@{0}: On main: WIP: halfway through refactoring auth

# 還原最近一個 stash 並從 list 中刪除
git stash pop

# 還原但不刪除
git stash apply

💭 原理：git stash 本質上是把 working tree + index 的 diff 存成一個臨時 commit object（在 .git/refs/stash），然後 reset working tree 到 HEAD。因為是 commit，所以即使是 stash pop 後的衝突也能用 git 標準方法解決。

💡 Helm values 分層覆蓋 — values.yaml ← values/production.yaml ← --set

Helm 的 value 覆蓋順序：values.yaml（預設值）← values/production.yaml（環境覆蓋）← --set key=value（CLI 動態覆蓋）。後面的層級 merge 並覆蓋前面的同名 key。多個 -f 檔案從左到右，--set 永遠最後贏。注意 --set 不會檢查 typo，打錯 key 會默默新增一個無效設定。

# 預設值在 chart/values.yaml
# replicas: 1

# 環境覆蓋在 values/production.yaml
# replicas: 3

# CLI 動態覆蓋（最終贏）
helm upgrade my-app ./chart   -f values.yaml   -f values/production.yaml   --set replicas=5   -n production

# 查看最終合併後的 values
helm get values my-app -n production

💭 原理：Helm 用 YAML merge 策略（recursive merge），同名 key 後面的值覆蓋前面的，同層級不同名 key 會合併。分層設計讓團隊可以共用同一份 chart（values.yaml 是 baseline）、不同環境有自己的覆蓋檔（staging.yaml / production.yaml）、CI/CD 還可以用 --set 注入 build-specific 的值（如 image tag）。

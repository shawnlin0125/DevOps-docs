💡 kubectl exec Pod 內排查：env、nc、resolv.conf 三招

當 Pod 已經 Running 但行為異常時（連不上資料庫、DNS 解析失敗、環境變數不對），進到容器內部排查是最直接的方法。用 kubectl exec 開一個互動 shell 進去，然後用三招快速診斷。

# 進入 Pod 內部
kubectl exec -it <pod-name> -n <namespace> -- sh

# 第一招：確認環境變數
env | grep -i <KEYWORD>

# 第二招：測試連線
nc -zv <service-host> <port>

# 第三招：確認 DNS
cat /etc/resolv.conf
nslookup <service-name>

💭 原理：Pod 內的網路命名空間與 host 隔離，從外部用 curl/dig 測不到 Pod 的 /etc/resolv.conf 和環境變數。exec 進 Pod 等同於在容器內操作，能驗證 Service Discovery、環境配置和 network policy 是否正確。nc -zv 的 -z 模式只測連線不發資料，適合快速健康檢查。

💡 systemd 服務管理：systemctl、journalctl、daemon-reload 三指令

Linux 系統服務由 systemd 管理，三個指令涵蓋 90% 的日常維運需求：看失敗服務、查日誌、重載設定。

# 查看所有失敗的服務
systemctl list-units --state=failed

# 查看特定服務的最近日誌
journalctl -u <service-name> -n 50 --no-pager

# 即時追蹤服務日誌（類似 tail -f）
journalctl -u <service-name> -f

# 修改 unit file 後重載設定
systemctl daemon-reload

# 查看服務狀態與最近日誌
systemctl status <service-name>

💭 原理：systemd 是所有服務的 init 系統（PID 1），服務用 unit file 描述。修改 unit file 後必須 daemon-reload 讓 systemd 重新讀取，否則 restart 仍用舊設定。journalctl 讀取 binary journal（/var/log/journal/），比文字 log 更省空間且支援 structured metadata（_PID、_COMM 等過濾器）。

💡 GitHub PR 流程：gh CLI 完整操作與實用技巧

GitHub CLI（gh）讓 PR 流程全在 terminal 完成，不用開瀏覽器。從開分支、創建 PR、到 merge 清理，一條龍。

# 完整 PR 流程
git checkout -b feature/my-feature
git add . && git commit -m "feat: add new feature"
git push -u origin feature/my-feature
gh pr create --title "feat: add new feature" --body "What this PR does..." --reviewer @username

# 查看 PR 列表
gh pr list --state open

# 查看 PR diff
gh pr diff <number>

# Merge（squash 保持歷史乾淨）
gh pr merge <number> --squash --delete-branch

# 切到 PR 的本機 branch 做 review
gh pr checkout <number>

💭 原理：gh CLI 用 GitHub REST API / GraphQL 操作 PR，但 git push 仍用 git protocol。gh pr create 會自動從當前 branch 建立 PR，--fill 可從 commit message 填充 title/body。gh pr checkout 自動建立 local tracking branch，無需手動 git fetch + checkout。merge --squash 把 PR 的所有 commits 壓成一個，保持 main 歷史線性。

💡 Helm values 三層分層覆蓋：預設值 → 環境值 → CLI 覆蓋

Helm values 有三層覆蓋機制，後面的層級 merge 覆蓋前面的同名 key。善用這個機制可以讓同一個 chart 部署到不同環境。

# 三層架構
# Layer 1（最底層，chart 內建預設值）
cat chart/values.yaml

# Layer 2（環境特定覆蓋）
helm install my-release ./chart -f values/production.yaml

# Layer 3（CLI 即時覆蓋，最高優先）
helm install my-release ./chart \
  -f values/production.yaml \
  --set image.tag=v1.2.3 \
  --set replicaCount=5

# 驗證渲染結果（不實際安裝）
helm template my-release ./chart \
  -f values/production.yaml \
  --set image.tag=v1.2.3 \
  --debug

💭 原理：Helm 用 Go template 引擎將 values 填入 template。--set 的 key 用 a.b.c 路徑語法（如 image.tag），Helm 會自動建立 nested map。--set 很方便但 typo 不報錯（因為 Go template 的 default 函式會補空值），建議先用 helm template --debug 驗證再安裝。後層 merge 是同層覆蓋，不是 deep merge。

💡 網路排查四指令：curl / dig / ss / nc 對應 OSI 四層

網路問題從應用層到實體層都有，四個指令分別對應 OSI 不同層次，從上到下逐一排除。

# 應用層（L7）：看完整 HTTP 請求和回應
curl -v http://example.com

# DNS 層（L7 DNS）：查詢 DNS 解析
dig +short example.com
nslookup example.com

# 傳輸層（L4）：看 listening port 與 process
ss -tlnp

# 傳輸層連線測試（L4）：測 TCP port 通不通
nc -zv example.com 443

# 完整路徑：從 URL 開始測
curl -v https://my-service.example.com/api/health \
  && dig +short my-service.example.com \
  && nc -zv my-service.example.com 443

💭 原理：curl -v 顯示 SSL 握手、request header、response header，看 HTTP status code 和 TLS 憑證問題。dig +short 跳過冗餘訊息只回 IP。ss 取代老舊的 netstat，-tlnp = TCP、Listening、Numeric、Process（需 sudo）。nc -zv 的 zero-I/O 模式只做 TCP handshake 就斷開，純測連線不發 payload。

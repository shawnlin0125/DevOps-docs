💡 kubectl 診斷 Pod 啟動失敗的完整流程

Pod 無法啟動時，按 get pods → describe pod → logs → get events 的順序逐層排查。從 STATUS 和 Events 欄位判斷是 ImagePull 失敗、CrashLoop 崩潰、OOMKilled 記憶體不足、還是 Pending（資源不夠排程）。

# 第一步：看整體狀態
kubectl get pods -A | grep -E "Error|CrashLoop|Pending|OOM"

# 第二步：深入特定 Pod
kubectl describe pod <pod-name> -n <ns>
# 重點看 Events 欄位最後幾行，會寫明失敗原因

# 第三步：看容器 log
kubectl logs <pod-name> -n <ns> --tail=50
kubectl logs <pod-name> -n <ns> --previous  # 看上次崩潰的 log

# 第四步：看 cluster 層級 events
kubectl get events -n <ns> --sort-by='.lastTimestamp'

💭 原理：K8s 的排錯資訊是分層的 — Pod STATUS 給快速概覽，describe Events 記錄 kubelet 的動作（拉鏡像/掛載/啟動），logs 看應用層錯誤，cluster events 補足 namespace 視角看不到的全域事件。

💡 k3s containerd 鏡像管理完整流程（免 registry）

k3s 內建 containerd 而非 Docker daemon，因此 docker build 產生的 image 需要透過 docker save 匯出後再 k3s ctr images import 匯入 k3s 的 containerd image store。搭配 imagePullPolicy: Never 讓 Pod 直接使用本地鏡像。

# 完整流程：build → save → import → deploy
sudo docker build -t myapp:latest .
sudo docker save myapp:latest | sudo k3s ctr images import -

# 確認 image 已匯入 containerd
sudo k3s ctr images ls | grep myapp

# 部署（imagePullPolicy: Never）
kubectl apply -f k8s/deployment.yaml
kubectl rollout restart deployment/myapp -n myns

💭 原理：k3s 為了輕量化而使用 containerd，它的 image store 和 Docker 完全獨立。docker save 把 image 序列化成 tar stream，pipe 給 k3s ctr images import 寫入 containerd。這讓單節點 k3s 不需要搭建 private registry。

💡 Linux 資源監控三指令：uptime / free / df 的正確讀法

快速判斷主機資源狀態的三個核心指令：uptime 看 CPU 排隊（load average vs CPU 核心數）、free -h 看記憶體（重點是 available 而非 free）、df -h / 看磁碟使用率。

# CPU 排隊狀況：load average > CPU 核心數 = CPU 不夠用
uptime
# 輸出: 03:00:00 up 30 days, 1.23, 0.89, 0.72
#        load 1min/5min/15min

# 記憶體：看 available 不是 free！
free -h
# Linux 會拿閒置 RAM 做 disk cache，free 低但 available 夠就沒事

# 磁碟使用率
df -h /
# Use% 超過 90% 要警覺，95% 以上危險

💭 原理：Linux 的記憶體管理策略是「不浪費任何 RAM」——閒置記憶體自動變成 buffer/cache 加速 I/O，當應用程式需要時會釋放。所以 free 欄位低不代表記憶體不足，available 才是真正可用的量。

💡 Git 復原操作：reset / restore / reflog 何時用哪個

三種常見的 Git 復原場景：git reset --soft HEAD~1 退回 commit 但保留 staged（改完再 commit）、git restore <file> 丟棄工作區改動、git reflog 查看所有 HEAD 移動記錄，可救回誤刪的 commit 或 branch。

# 場景一：commit 了但想改 message 或補檔案
git reset --soft HEAD~1   # 回到 staging 狀態，檔案保留
git commit -m "更好的 message"

# 場景二：工作區改爛了，想回到上次 commit 的狀態
git restore file.py        # 丟棄特定檔案的改動
git restore .              # 丟棄所有改動

# 場景三：誤刪 branch 或 reset 過頭，救回 commit
git reflog                 # 看所有 HEAD 移動歷史
git checkout <commit-hash>  # 回到那個 commit
git switch -c recovered-branch  # 建立新 branch 保留它

💭 原理：Git 的 reflog 記錄了所有 HEAD 指針的移動（commit/checkout/reset/rebase），預設保留 90 天。只要 commit 曾經存在過，reflog 就能找到它的 hash，所以「誤刪的 commit」幾乎都能救回來。

💡 Helm 常用運維操作：list / history / rollback / get values

Helm 日常運維最常用的四個指令：helm list -A 看所有 release、helm history 看版本歷史、helm rollback 退回舊版、helm get values 確認目前設定值。

# 所有 namespace 的 release 狀態
helm list -A

# 特定 release 的部署歷史（含 revision 編號）
helm history my-release -n myns

# 退回指定版本（緊急復原！）
helm rollback my-release 3 -n myns

# 查看目前生效的 values（含預設值 + 覆蓋值）
helm get values my-release -n myns --all

💭 原理：Helm 把每次 install/upgrade 存成一個 revision（secret 物件），rollback 就是取出舊 revision 重新部署。helm get values 可以看到實際 render 時用了哪些參數，方便確認覆蓋是否如預期。

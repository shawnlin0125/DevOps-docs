💡 kubectl 診斷 Pod 啟動失敗的完整流程

Pod 啟動失敗時遵循四步驟排查：kubectl get pods 看狀態 → kubectl describe pod 看 Events 區段 → kubectl logs 看容器輸出 → kubectl get events 看全集群事件。從 Status/Events 欄位快速判斷問題類型：ImagePullBackOff（鏡像名稱錯誤或不存在）、CrashLoopBackOff（容器啟動後不斷崩潰重啟）、OOMKilled（超過 memory limit 被 cgroup 殺掉）、Pending（資源不夠排程，通常是 request 總和超過節點容量）。

# 1. 查看所有 Pod 狀態
kubectl get pods -A | grep -v Running

# 2. 查看特定 Pod 的詳細 Events
kubectl describe pod <pod-name> -n <ns> | grep -A 20 Events

# 3. 看容器 stdout/stderr
kubectl logs <pod-name> -n <ns> --tail=100

# 4. 全集群異常事件
kubectl get events -A --sort-by='.lastTimestamp' | tail -20

💭 原理：describe 的 Events 段落記錄了 kubelet 對 Pod 的每一個操作與錯誤原因（從 scheduler 指派→pull image→create container→start），是最快定位問題的入口。logs 看容器內部，events 看集群層級。

💡 k3s containerd 鏡像管理完整流程

k3s 不使用 Docker daemon，而是內建 containerd 作為容器運行時。部署新 image 的完整 pipeline：docker build（在開發機上建置）→ docker save（匯出 tar）→ sudo k3s ctr images import -（匯入 k3s 的 containerd namespace）→ kubectl apply 更新 manifest → kubectl rollout restart 觸發重建。因為 k3s 不走 registry，所以 Deployment 需設 imagePullPolicy: Never，避免 kubelet 嘗試從遠端拉取。

# 完整部署流程（在開發/管理機上執行）
docker build -t myapp:20260622 .
docker save myapp:20260622 | sudo k3s ctr images import -
kubectl apply -f deploy.yaml
kubectl rollout restart deployment/myapp -n <ns>

# Deployment 需設 imagePullPolicy: Never
# spec.template.spec.containers[].imagePullPolicy: Never

# 檢查鏡像是否已匯入
sudo k3s ctr images ls | grep myapp

💭 原理：k3s 的 containerd 使用獨立的 image namespace（預設為 k8s.io）。docker save 匯出的 tar 檔透過 k3s ctr images import 匯入 containerd 的 image store，kubelet 直接從本地 containerd 讀取鏡像。

💡 查 OOM 紀錄：dmesg + exit code 137

當系統或 cgroup 記憶體不足時，Linux OOM Killer 會挑選 oom_score 最高的行程終止（通常是 RSS 用最多的）。查詢方式：sudo dmesg -T | grep -i oom 看核心 OOM 紀錄。被 OOM 殺掉的行程 exit code 為 137（128 + 9，SIGKILL 訊號）。K8s 中，Pod 超過 memory limits 時被 cgroup OOM Killer 殺掉（非節點層級），kubectl describe pod 的 Last State 欄位會顯示 OOMKilled。節點 OOM 與 K8s cgroup OOM 的差別：前者殺整台機器的行程（可能包含 kubelet），後者只殺該 Pod。

# 查核心 OOM 紀錄（含時間戳）
sudo dmesg -T | grep -i oom

# K8s Pod 被 OOM 殺掉的判別
kubectl describe pod <pod-name> -n <ns>
# → Last State: Terminated / Reason: OOMKilled / Exit Code: 137

# 檢查節點記憶體壓力
free -h
# available 欄位低於 10% 時 OOM 風險高

# 查看 Pod 的 memory limit 設定
kubectl get pod <pod-name> -n <ns> -o yaml | grep -A 4 resources

💭 原理：OOM Killer 是核心最後一道防線。K8s 中 memory limits 總和 > 節點實體 RAM 時，OOM 會連鎖殺 Pod。可用 memory request 保證排程，limit 防止某個 Pod 吃掉所有記憶體。

💡 GitHub PR 流程：gh CLI

GitHub CLI (gh) 提供完整的 PR 生命週期操作，無需離開終端機。流程：建立分支 → commit → push → gh pr create 開 PR → review → gh pr merge --squash 合併 → 刪除分支。實用子指令：gh pr list 看所有 PR、gh pr diff 看變動、gh pr checkout <number> 切到該 PR 分支、gh pr review --approve 核准。使用 --squash 壓縮所有 commit 為一個，保持 main 歷史整潔。

# 完整 PR 流程
git checkout -b feature/my-feature
git add . && git commit -m "feat: add my feature"
git push -u origin feature/my-feature

# 開 PR（自動填入 title/body）
gh pr create --fill

# Review 與合併
gh pr review --approve
gh pr merge --squash --delete-branch

# 合併後更新 main
git checkout main && git pull

# 實用工具
gh pr list --state open
gh pr diff <number>
gh pr checkout <number>

💭 原理：gh 透過 GitHub REST API（/repos/{owner}/{repo}/pulls）操作 PR。--squash 合併時，GitHub 在服務端建立一個包含所有變更的 squash commit，不會保留分支上個別 commit 的歷史。

💡 Cloudflare DNS 管理：Proxy vs DNS only

Cloudflare DNS 有兩種模式：Proxy mode（橙色雲朵）流量經 Cloudflare CDN 代理，隱藏 origin 真實 IP，提供免費 TLS/SSL 終止和 DDoS 防護；DNS only（灰色雲朵）只做 DNS 解析，流量直達 origin server。用 dig +short 查詢：回傳 Cloudflare IP 區段代表是 Proxy mode，回傳真實伺服器 IP 代表 DNS only。可透過 Cloudflare API 程式化管理 DNS records，適合自動化部署腳本。

# 判斷 DNS 模式
dig +short example.com
# → 104.21.x.x（Cloudflare IP，表示 Proxy mode）
# → 你的真實 IP（表示 DNS only）

# Cloudflare API 管理 DNS record
ZONE_ID="your-zone-id"
API_TOKEN="your-api-token"

curl -s -X GET "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" | jq '.result[] | {name, type, content, proxied}'

# 新增 A record（proxied: true = Proxy mode, false = DNS only）
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"type":"A","name":"www","content":"1.2.3.4","ttl":120,"proxied":true}'

💭 原理：Proxy mode 下，Cloudflare 是反向代理，流量先到 Cloudflare Edge（隱藏 origin），再由 Argo Smart Routing 到 origin server。這也意味著 SSL 在 Cloudflare ↔ browser 之間是加密的，但 Cloudflare ↔ origin 之間取決於是否啟用 Full (strict) 模式。
